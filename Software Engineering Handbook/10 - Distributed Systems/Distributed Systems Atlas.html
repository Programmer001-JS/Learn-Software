Software Engineering Handbook · 10 Distributed Systems · eight sheets

Atlas of a Distributed System

One order, placed once, and everything that happens to it after the user stops waiting. Sheet 1 is the route that order travels; every other sheet magnifies one stretch of it — the shape of the application, the caches in front, the pipes behind, the workers at the end. The moment work leaves a single process it can be lost, delayed, reordered or done twice, and every mechanism in this folder exists to answer one of those four.

Sheet 1

The Order Line

Transit diagram Covers · Message Queues · Event Driven Architecture · Background Workers · Microservices · Caching

One order, one route, twenty stops. The user waits for seven of them. Stop 06 is the most important line of code in the folder — the order and the intent to publish commit together or not at all — and stop 13 exists because every message after it may arrive twice.

Step key — every stop on this sheet, and what it does

01Place order

A POST with a cart, a payment method and an identity. It is the only moment on the whole map where a person is waiting for a response.

02The gateway

Authentication, routing and rate limiting, and a trace ID stamped on the request. That ID is the only thread that will tie the next eighteen stops together during an incident.

03Load balancer

Any instance can take the request because instances hold no state. That is what lets a monolith scale horizontally exactly like any other service.

04Order module

The request enters through a module's public interface, never its internals. In a modular monolith a lint rule enforces that; in microservices the network does.

05Stock check

Inventory answers from tables it owns. A function call measured in nanoseconds inside one process, or a network call that can fail, retry and time out between services.

06BEGIN … COMMIT

The order row and an outbox row are written in one transaction. Either both exist or neither does, which removes the "order saved, event never published" bug entirely.

07201 returned

Around 30 ms after the click. Nothing downstream has run yet; the response promises only that the order is recorded and the work is durably queued.

08The relay

A separate process reads unsent outbox rows, publishes them and marks them sent. It can crash and publish twice, so publication is at-least-once — never exactly-once.

09The broker

Kafka, RabbitMQ or EventBridge receives OrderPlaced — a past-tense fact, not an instruction. It cannot be refused, because it already happened.

10Fan-out

Every interested service receives its own copy. Adding loyalty points next year means writing one new consumer; the order service is never touched.

11The queue

Each consumer's copy waits durably until acknowledged. Its depth and the age of its oldest message are the two numbers that reveal a backlog before users do.

12A worker

A separate process, scaled on queue depth rather than request rate, taking a small number of messages at a time so a crash strands little work.

13Seen it before?

The idempotency check. Redelivery is normal operation — a worker can finish the work and die before acknowledging — so the first thing a consumer does is ask whether it already did this.

14Do the work

Load the entity fresh by its ID, never trust a serialised copy, and run under a timeout so one hung job cannot hold a worker forever.

15Ack

Acknowledge only after success. Acknowledging on delivery is how a worker crash silently loses the job — the default in more than one framework on sheet 6.

16Inventory reserves

Around 200 ms later, in its own database, then publishes StockReserved. For that window, the order exists and the reservation does not.

17Payment charges

The card is charged, or the charge fails and PaymentFailed is published. There is no distributed transaction to roll back; the failure is just another event.

18Shipping, email

Each reacts to the events it subscribes to, independently. The flow exists only as the sum of subscriptions — which is why choreography is hard to follow on sheet 7.

19Analytics counts

Two seconds after the order. Until this point different services held different versions of reality, and none of them was wrong: the system is eventually consistent.

20The dashboard

The user sees the outcome seconds after the 201. The interface must have been designed for that gap, with a pending state rather than a missing order.

ARolled back

If the transaction at 06 fails, neither the order nor its outbox row exists, so no event is ever published about an order that does not exist.

BAlready processed

A duplicate recognised by its idempotency key is acknowledged and dropped. That is the practical meaning of "exactly once": at-least-once delivery with idempotent effects.

CThe cache branch

Before the click, the product page was answered by whichever layer had a fresh copy — browser, CDN, proxy, local memory or Redis. Sheet 3 opens every layer.

FThe failure loop

A throwing job retries with exponential backoff and jitter, then lands in a dead-letter queue with an alert. Without the DLQ, a poison message is retried forever.

The response is not the outcome

A 201 at stop 07 means "recorded", not "done". Everything from 08 to 20 can be delayed, reordered, duplicated or fail — and none of it produces an error the user or the API ever sees. If you monitor only HTTP status codes, this entire map is invisible to you.

Sheet 2

The Architecture Ladder

Ladder plate Covers · Monolith · Modular Monolith · Microservices

Seven ways to grow an application, drawn in the order you should reach for them. The first five keep one deployment and one transaction; the last two start paying for the network. Traffic almost never forces you up this ladder — teams that cannot deploy independently do, and that is the only honest reason to reach the top rung.

Step key — the rungs and their vocabulary

01Vertical scaling

A bigger machine. Unfashionable, immediate, and far more effective than its reputation — Stack Overflow served enormous traffic from a handful of servers.

02Horizontal scaling

More identical copies behind a load balancer. Works for a monolith exactly as for any service, provided no instance holds state the others lack.

03Caching

Remove most reads from the database. The cheapest scaling available, and a hidden dependency the day the cache is cold at peak — sheet 3.

04Read replicas

Send read traffic to copies of the primary. The database is usually the real bottleneck in either architecture, which is why this rung comes long before splitting.

05Modular monolith

One deployment, strict modules: a public interface each, owned tables, and boundaries enforced by tooling that fails the build. Conventions without enforcement decay within months.

06Extract one component

Lift out the single part with a genuinely different scaling profile. A targeted decision about one module — not the adoption of microservices.

07Microservices

Independently deployable services, each owning its data. Their real purpose is organisational: many teams releasing without coordination. Every technical claim is achievable lower down.

08The network tax

Function calls become fallible network calls, transactions become sagas, stack traces become trace IDs, joins become API calls. A permanent cost, paid on every request.

09Distributed monolith

Services that share a database or must ship together. All of the operational complexity, none of the independence — the most common way the pattern is adopted in name only.

10The honest test

Multiple teams blocked by one pipeline, boundaries drawn by business capability, and CI, logging, tracing and orchestration in place first. All three, or a modular monolith.

11Extraction path

A module with its own interface, its own tables and explicit dependencies can be lifted out. A big ball of mud cannot — it must be untangled first, which is where most "we'll split it later" plans die.

12Bounded context

The best guide to where module or service lines belong. A boundary is right when most changes touch one side of it; if a typical feature needs four coordinated releases, it is wrong.

Boundaries are not security walls

Module boundaries are enforced by the build, not the operating system: a compromised code path can call anything in the process. And the internal network between services is not a perimeter either — authorise in every service, use mTLS, and give each service its own least-privilege credentials.

Sheet 3

The Cache Stack

Cutaway section Covers · Caching

Branch C of sheet 1, cut open. On one server a cache is an optimisation; across many it is a distributed system with copies of the truth at different ages in different places. Every layer answers faster than the one below it and is harder to invalidate — and the two ways a cache takes a system down, the stampede and the cold start, both happen at the moment it stops answering.

Step key — every layer and failure on this sheet

01Browser cache

Zero milliseconds, no network at all, one copy per user. The most underused layer, and the one you can never purge — only let expire.

02CDN edge

About 10 ms, one copy per region. The highest-leverage layer and the one most often left unconfigured. Purging is eventually consistent and takes minutes.

03Reverse proxy

Nginx or Varnish in front of the application, about 1 ms, scoped to a data centre and easy to purge.

04Application memory

Around a tenth of a microsecond and scoped to one instance. Correct on one server; ten different answers on ten.

05Redis

A shared cache across every instance, about 1 ms away. Invalidation is easy and immediate, which is why it is the authoritative copy when local caches disagree.

06Database buffer pool

The database's own memory cache. You tune it rather than invalidate it, and it is what makes a warm database fast and a restarted one slow.

07Disk

Where the answer actually lives. Every layer above is a copy of it, made at a different time.

08Local-memory trap

In-process caches across many instances produce inconsistent answers depending on routing. Accept bounded staleness deliberately, move to a shared cache, or invalidate over pub/sub with a TTL as the backstop.

09Cache stampede

A popular key expires and thousands of concurrent requests miss together, all querying the database, which saturates, times out, and causes retries that miss again. Also called the thundering herd.

10Locking

The first miss acquires a lock and regenerates the value; the others wait briefly and read it. The database sees one query instead of ten thousand.

11Stale-while-revalidate

Serve the expired value while a single request refreshes it in the background. No user waits, which is what makes news and shop pages feel instant under load.

12Jittered TTL

Expire at 300 s plus or minus a random 60, so keys written together do not expire together. One line of code that removes the synchronised version of the stampede.

13Cold cache

A flush or restart drops the hit rate from 95% to zero and sends the database 20 times its normal load at once. A system that only survives warm has a load-bearing cache.

14Cache-Control

immutable for hashed assets, max-age with stale-while-revalidate for semi-dynamic pages, private and no-store for anything authenticated. Standard headers everyone has and few use fully.

15Versioned key

entity · id · variant · schema version, as in user:42:profile:v3. Bumping the version orphans every old entry with no purge, no scan and no race — the cheapest invalidation there is.

16Consistency model

Write-through, invalidate-on-write (the usual correct choice), TTL only, or pub/sub invalidation. Each is a statement about how stale an answer is allowed to be.

17Poisoning and deception

A shared cache storing one user's response under a key that does not include the user serves it to the next visitor. Unkeyed headers, a wrong Vary, or a path that looks static all cause it.

Permissions live in the cache too

When a user's access is revoked, every cached copy of what they could see is still valid until it expires. Purge on permission change, keep authenticated responses out of shared layers entirely, and never let a cache key omit the thing that makes a response private.

Sheet 4

Queue, Stream or Broadcast

Decision tree Covers · Message Queues · RabbitMQ · Kafka · Redis Streams · AWS SQS

Stops 09 to 11 of sheet 1, as a choice. Before naming a broker, decide what the pipe must do: hand each message to one worker, announce it to whoever is listening, or keep it so anyone can read it later. Choosing the wrong shape produces either lost work or duplicated work, and no amount of tuning the right brand fixes the wrong shape.

Step key — the nodes, the leaves and the guarantees

01Work to hand off

Something one part of the system produces and another must act on — an instruction to a known recipient, or a fact nobody is addressed by.

02Result needed now?

If a person is waiting for the answer, it is a synchronous call. A queue makes the work durable, not faster for the one who asked.

03Synchronous call

The honest answer for work whose result the user needs immediately. Queuing it only adds eventual consistency to something that needed an answer.

04Under ~50 ms?

Enqueue, serialise, poll, deserialise and acknowledge cost more than a short, reliable function call. Queue slow, retryable or externally dependent work.

05Call the function

Trivial work stays inline. Putting it behind a broker adds a failure mode and buys nothing.

06One consumer, or all?

"Send this email" must happen exactly once, by one worker. "A user signed up" may matter to many services. The single most consequential question on this sheet.

07Modest volume, on Postgres?

If the data already lives in Postgres and volume is modest, a new broker may be unnecessary infrastructure.

08SKIP LOCKED

SELECT … FOR UPDATE SKIP LOCKED distributes work correctly, and the job is enqueued in the same transaction as the data change. pg-boss, Graphile Worker and Hangfire use this shape.

09On AWS, zero ops?

A managed queue removes clusters, patching, failover and capacity planning. The absence of operational work is worth a great deal.

10AWS SQS

Effectively unlimited scale, hidden-not-deleted delivery, dead-letter queues and redrive built in. Standard queues duplicate and reorder by design. Sheet 5, panel D.

11Route by content?

When different consumers need different subsets — by region, by event type — the broker's routing model starts to matter.

12RabbitMQ

Exchanges route by key to queues; each message is acknowledged individually and gone once acked. The classic task queue. Sheet 5, panel A.

13Whichever you run

With no routing needs and no managed option, the best broker is the one you already operate: RabbitMQ, or Redis Streams if Redis is already in the stack.

14Late readers see it?

Must a subscriber that was restarting, or one added next month, still receive the event? That is the line between broadcast and log.

15Pub/Sub

Fire and forget to every current subscriber. No persistence, no acknowledgement, no replay — an offline subscriber simply misses the message.

16Replay for weeks?

Retention for days or weeks on disk, millions of events per second, reprocessing after a bug fix — the requirements that justify Kafka's operational cost.

17Kafka

A partitioned, replicated, retained log where each consumer group tracks its own offset. Not a task queue, and not a beginner's default. Sheet 5, panel B.

18Redis Streams

Most of Kafka's model — persistence, consumer groups, per-entry acknowledgement, replay — as long as retention fits in RAM. Sheet 5, panel C.

19Three shapes

Queue distributes work to one consumer until acknowledged; pub/sub broadcasts to whoever is listening; a stream retains events for every group to read from its own offset.

20Delivery guarantees

At most once loses; at least once duplicates; exactly once does not exist end to end, because a consumer can finish the work and crash before acknowledging.

21Idempotency

An idempotency key, or an insert that ignores conflicts, makes a second run a no-op. At-least-once plus this is how real systems get exactly-once effects.

A message is untrusted input

Anyone who can reach the broker can enqueue anything. Authenticate producers and consumers, validate every payload against a schema, publish identifiers rather than personal data, and remember that the dead-letter queue holds real payloads — usually in the least protected corner of the system.

Sheet 5

Four Brokers, Opened

Exploded parts Covers · RabbitMQ · Kafka · Redis Streams · AWS SQS

The leaves of sheet 4, taken apart. Each broker answers the same question — what happens to a message a consumer took and never finished? — with a different part. RabbitMQ waits for an ack, Kafka waits for an offset commit, Redis Streams keeps a pending list someone must reclaim, and SQS simply makes the message visible again. Learn that one part per broker and the rest of its behaviour follows.

Step key — the parts of four brokers

01Routing key

The producer publishes with an address such as order.eu.created and knows nothing about who consumes it.

02Exchange

Direct matches exactly, topic matches wildcards, fanout copies to every bound queue, headers routes on headers. A topic exchange covers almost every real need.

03Binding and queue

order.# for auditing, order.eu.* for regional processing: each queue receives its own copy, and each copy goes to one consumer.

04Manual ack

Acknowledge after processing; nack to requeue or dead-letter; a crash without an ack redelivers elsewhere. The whole point of choosing RabbitMQ.

05Prefetch

How many unacked messages a consumer may hold. Unbounded is the most common misconfiguration; small for slow tasks, larger for fast ones.

06Dead-letter exchange

Rejected or expired messages route to a DLQ for inspection and replay. Combined with a TTL queue that has no consumer, it also implements delayed retry.

07Partition key

hash(key) picks the partition, so every event for one order_id lands in the same one and stays in order.

08Partition

An append-only, ordered sequence. Ordering exists within it and never across; the partition count is the parallelism ceiling.

09Consumer group

Each partition goes to one consumer in the group. More consumers than partitions means idle consumers; rebalancing pauses processing.

10Offset

Each group's own read position per partition — billing at 15,000, analytics hours behind at 12,300, all on the same events.

11Replay and retention

Events stay for 7 days, 100 GB, or compacted per key, regardless of who read them. Fix a consumer bug, reset its offset, reprocess — nothing else is affected.

12XADD and trimming

Appends an entry with an ID such as 1699123456789-0. Streams live in RAM, so MAXLEN or MINID belongs on every stream from the first line of code.

13XREADGROUP

Delivers each entry to one member of a consumer group, with BLOCK so workers wait without polling.

14Pending entries list

Every delivered, unacknowledged entry with its idle time, visible through XPENDING. What makes Streams reliable — and the part people forget.

15XACK

Confirms the work and removes the entry from the pending list. Reliable only together with claiming.

16XAUTOCLAIM

A periodic loop reassigns entries idle longer than, say, 60,000 ms to a live worker. Without it, a crashed worker's entries are delivered to nobody, forever.

17Visibility timeout

ReceiveMessage hides a message, 30 s by default, rather than deleting it. If processing outlasts the timeout the message reappears and a second consumer takes it.

18DeleteMessage

The only thing that removes a message. Forget it and the message simply comes back.

19Standard vs FIFO

Standard is effectively unlimited and duplicates and reorders by design. FIFO orders within a group and deduplicates within 5 minutes, at 300–3,000 messages per second.

20Long polling and batching

WaitTimeSeconds=20 and batches of 10 cut the request count you are billed for, and lower latency too. Payloads over 256 KB go to S3 with a pointer.

21maxReceiveCount and redrive

After 5 receives without deletion a message moves to the DLQ; once the bug is fixed, redrive returns it to the main queue — a feature self-hosted setups usually build themselves.

Every retained message is a data store

Seven days of Kafka events, a day of Redis Stream entries and a dead-letter queue full of failed payloads are all personal data with the same obligations as a database — including deletion requests, which an immutable log makes genuinely hard. Publish identifiers, not personal fields, and decide this before you build.

Sheet 6

The Job Circuit

Closed circuit Covers · Background Workers · Message Queues · Celery · BullMQ · Hangfire

Stops 12 to 15 of sheet 1, as the loop a worker runs forever. Six steps, the same in every language and framework. Workers fail silently — nobody receives a 500, the work simply does not happen — so the circuit is only safe with an ID instead of an object, an idempotency check, a timeout, an ack after success, and an alert on the age of the oldest message.

Step key — the circuit, the rules and the frameworks

01Enqueue an ID

Pass { video_id: 42 }, not the file or a serialised object. The API responds in about 50 ms and the task stays small, current and safe across model changes.

02A worker takes it

A separate process with its own resource profile, holding one message at a time for long tasks so a crash strands little work.

03Load fresh by ID

Read the row now, not as it was when enqueued. A task carrying a whole object acts on data that may be minutes old.

04Already done?

Check the idempotency key or the status first. If the work happened, acknowledge and stop — the duplicate was normal delivery, not a failure.

05Do the work

Encode, send, sync — always under a timeout. A task with no timeout that hangs holds a worker forever and slowly drains the pool.

06Ack only now

Update status, notify, then acknowledge. Acknowledging earlier turns every worker crash into silently lost work.

07Backoff with jitter

Retry at 1, 2, 4, 8, 16 seconds with randomness added, so a downstream outage is not hit by every failed task at the same instant.

08Dead-letter queue

Where a job goes after its last attempt: inspected, fixed, redriven. It turns a poison message's infinite loop into one alert.

09Oldest message age

The clearest backlog signal, alongside depth, p95/p99 duration, DLQ size and liveness. A queue with zero errors can still be doing nothing.

10Scheduled jobs

Cron on every replica runs the job N times. Use one scheduler that enqueues, an orchestrator CronJob, or a framework that stores the schedule centrally.

11Fan-out

One task per user instead of one task for 50,000. Each retries alone, progress is visible, and a failure at user 30,000 does not resend the first 30,000.

12The six rules

Idempotent, small payloads, timeouts, retries with backoff, a dead-letter path, and graceful shutdown that finishes the current task on SIGTERM.

13acks_late

Celery acknowledges on receipt by default. Set acks_late=True so a task is acknowledged only after it succeeds — the setting behind the most common Celery incident.

14Prefetch multiplier

Celery's default of 4 lets one worker hoard long tasks while others sit idle. Set it to 1 for long-running work.

15removeOnComplete

BullMQ keeps completed and failed job records in Redis indefinitely unless told otherwise. A busy queue will consume all available memory.

16Concurrency is not parallelism

concurrency: 5 runs five jobs on one Node event loop — fine for I/O, still blocking for CPU. CPU work needs sandboxed processors or more processes.

17Transactional enqueue

Because a Hangfire job is a database row, it commits with the business write: both or neither. The same benefit pg-boss and Graphile Worker give Node.

18Dashboard security

Hangfire's dashboard, Bull Board and Flower expose payloads and allow retries and deletes. Each needs real authorisation, not an IP restriction.

Workers are not internal

They usually run with broader permissions than the API — database writes, file access, third-party credentials — and their input arrives from a queue, which is a trust boundary. Validate payloads, never deserialise untrusted data (pickle is remote code execution), give each worker only the credentials its jobs need, and keep authorisation in the service layer so a worker cannot bypass a rule the API enforces.

Sheet 7

Events and Sagas

Swimlane chart Covers · Event Driven Architecture · Microservices

The return line of sheet 1, drawn against the clock with one lane per service. An event is a fact about the past; nobody is told what to do, and nobody holds the whole flow. Decoupling is real and so is its price: for the shaded seconds the services disagree about reality, and a failed payment is undone not by a rollback but by new events that compensate.

Step key — the lanes and the patterns

01Commit with outbox

The order and an outbox row carrying OrderPlaced are written in one transaction. The event exists exactly when the order does.

02201 in ~30 ms

No downstream service was called or awaited. Producer latency improves because the order service stopped waiting for anyone.

03Publish

The relay publishes OrderPlaced to the broker. The order service does not know, and does not care, who subscribes.

04Inventory reserves

Around 200 ms later, in inventory's own database, followed by StockReserved. For that window the reservation does not yet exist anywhere.

05Payment fails

The charge is declined. There is no distributed transaction to abort — each service committed its own local transaction already.

06Email queues

A confirmation is queued independently of payment. A consumer that reacts too early is a design question, not a bug in the broker.

07Analytics counts

Two seconds after the order. A slow consumer never slows the order, and a broken one never fails it — that isolation is the point of events.

08PaymentFailed

The failure becomes a published fact. Every service that must react subscribes to it, and each reaction is its own local transaction.

09Compensation

Inventory releases the stock it reserved. A new action that undoes the effect, not a rollback of the old one.

10Order marked failed

The order service consumes the same event and updates its own state. Every consumer on this chart is idempotent, because redelivery is normal.

11Dashboard updates

The user sees the result seconds after the 201. The interface needs optimistic updates or an explicit pending state to survive that gap.

12Outbox pattern

Business write and event in one transaction, then a relay publishes. Without it, a crash between commit and publish loses events silently — the most skipped detail in event-driven systems.

13Choreography

Each service reacts to events with no central control. Maximum decoupling, and a flow that exists only as the sum of who subscribes to what. Good for simple fan-out.

14Orchestration

A coordinator — often Temporal or Camunda — drives the steps explicitly. Easier to read and debug, at the cost of a dependency. Better for multi-step business processes.

15Saga

A long process modelled as local transactions with compensating actions. Money is refunded, not un-charged; an email cannot be unsent — some steps have no compensation at all.

16Event vs command

OrderPlaced is a fact that cannot be refused; SendEmail is an instruction to a known recipient. A command disguised as an event is an RPC without error handling.

17Event versioning

Add optional fields only; never remove, rename or change meaning; run v2 beside v1 during transitions. A schema registry catches breaks at build time.

18Eventual consistency

For a window, services disagree about reality and none is wrong. The user will see it, so the interface must be designed for it rather than surprised by it.

Do not adopt this by default

Events turn a readable function call into a distributed flow with no stack trace; debugging becomes "which of eleven consumers did not react, and why?". Use them when several independent things must happen in response to one occurrence and consumers are added over time — and, inside one application, prefer in-process domain events.

Sheet 8

The Serverless Meter

Instrument panel Covers · Serverless · AWS SQS

The worker of sheet 6 with no fleet to run: the platform starts an instance per event, runs the handler, and bills by the millisecond. There are still servers; you just do not manage them. Three gauges decide whether that is a bargain — the cold start, the database connection limit, and the point on the cost curve where a flat-priced container becomes cheaper.

Step key — the gauges and their vocabulary

01Provision

No warm instance is free, so the platform creates an execution environment. The part you cannot optimise, only avoid by keeping instances warm.

02Load the runtime

The language itself starts. Go and Rust take 10–100 ms, Node.js and Python 100–500 ms, Java and .NET 1–3 s unless compiled ahead of time.

03Code and dependencies

Usually the largest slice and the one you control. A large dependency tree matters far more here than in a long-running service.

04Initialise

Database connections, framework boot, configuration. Done once per instance, then reused by warm invocations.

05Handler

Your code finally runs — about 5 ms on a warm instance. Everything to its left is the cold start users feel on scale-up.

06Connection problem

A thousand instances each open a connection to a database capped at 100. Fix with a proxy such as RDS Proxy or PgBouncer, an HTTP database, or a different deployment model.

07Cost curve

Serverless cost is linear in invocations; a container's is flat. Low, spiky traffic is near free, high steady traffic costs several times more. Model the crossover on real traffic.

08SQS triggering Lambda

The canonical serverless worker: no broker, no fleet, consumers scaled by the platform — with visibility timeout, DLQ, concurrency limit and idempotency still yours.

09Fit

Event processing, scheduled jobs, webhooks, glue and spiky traffic fit. Steady load, work past 15 minutes, WebSockets, latency-critical paths and heavy database use do not.

10Security surface

Fine-grained IAM per function is a genuine advantage; readable environment variables, public URLs, runaway scaling and leftover /tmp data are the liabilities.

11Memory and CPU

CPU allocation scales with configured memory, so a function given twice the memory may finish in under half the time — and duration is what you are billed for.

12Serverless containers

Fargate and Cloud Run run an ordinary container scaled to zero, with no 15-minute limit. Less discussed than functions, and a better fit for more real workloads.

Automatic scaling is also automatic billing

An unauthenticated function can be invoked until it is expensive, and a burst of 10,000 events scales straight past whatever the database behind it can take. Set concurrency limits and rate limits before launch — the platform will happily scale faster than anything downstream of it.
