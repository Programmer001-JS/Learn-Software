The Request Line

One click, one route, twenty-four stops. Every station says what happens there and what is waiting for you. Two stations let the journey end early — and almost all performance work is the effort to end it at one of them. The zones say who owns the ground: two of the six are rented, and exactly one door separates them from the machine you actually run.

The figure above is the shape. This is the same journey written out, one stop at a time, in the order a single request meets them. The chip on the left says whose machine you are standing on — and that, more than anything else on this poster, decides what you are allowed to fix.

  1. 00not on the line

    Your laptop — where the code is written

    uvicorn main:app --reload · 127.0.0.1:8000 · no nginx, no TLS, no Cloudflare

    What it is
    The same FastAPI application and the same uvicorn that will run in production — and nothing else from this poster. There is no edge, no firewall, no reverse proxy and no second machine.
    Get the words right
    What you call “running the server locally” is uvicorn. FastAPI is the library uvicorn loads; it never opens a port itself. You are running stations 10 to 16 and skipping every other one.
    It breaks when
    You deploy. Everything between 02 and 09 exists only in production, so TLS, real client IPs, forwarded headers, body-size limits, timeouts and gzip are all untested until that moment. This is the whole of “it works on my machine”.
    The fix
    Keep a docker compose that runs nginx in front of uvicorn locally too, with the same config file. Then the only thing production adds is Cloudflare.
  2. 01their device

    The click

    Chrome · Safari · your JavaScript calling fetch()

    What it is
    Their browser runs your front-end code and builds a request. Nothing has touched the network yet.
    You control
    Only what you shipped. Disable the button and show a loading state the moment it is pressed.
    It breaks when
    The main thread is blocked, so the page freezes before the request is even sent — and the user clicks three times, giving you three of them.
  3. 02Cloudflare

    DNS — turning a name into an address

    Cloudflare authoritative DNS · udp/53 · also DoH over :443

    What it is
    The browser asks “what is the address of api.example.com?”. With Cloudflare in front, the answer is Cloudflare’s anycast address — one IP that exists in every city at once. Your server’s real address is never given out.
    You set
    The record itself, the TTL, and above all whether the record is proxied (orange cloud) or DNS only (grey cloud).
    It breaks when
    A grey-clouded record publishes your origin IP to the entire internet, and every protection you bought becomes optional. A long TTL means a failover takes as long as the TTL.
  4. 03the network

    TCP and TLS — opening the connection

    tcp/443 · TLS 1.3 · about one round trip each

    What it is
    A connection is opened and encryption is agreed. On the poster this is TLS 1: the browser’s encrypted conversation is with Cloudflare, using their certificate.
    You set
    Minimum TLS version, HTTP/2 or HTTP/3, HSTS. All of it in the Cloudflare dashboard, not on your box.
    It breaks when
    A certificate expires — one of the most common self-inflicted outages there is. Or connections are not reused, so you pay both round trips on every single request.
  5. 04their device

    The HTTP request itself

    method · path · headers · cookies · body

    What it is
    The actual message: GET /orders/17, an Authorization header, a cookie, perhaps a JSON body.
    Remember
    Every byte of it is written by someone you have never met. There is no such thing as a field the client cannot change — not the price, not the role, not the user id.
    You set
    An idempotency key on anything that spends money, so a retry cannot charge twice.
  6. 05nobody’s

    The public internet

    roughly 10–15 ms per 1000 km, plus queueing and loss

    What it is
    Cables, exchanges and other people’s routers. The one part of the journey nobody can tune.
    What you do about it
    Shorten it. That is precisely what the next station is for: answer near the user instead of travelling to Frankfurt.
    It breaks when
    There is packet loss — which presents as inexplicable slowness, never as an error you can catch.
  7. 06Cloudflare

    The edge — Cloudflare’s network, in front of everything

    their machines in ~330 cities · :443 · you cannot ssh into any of it

    What it is
    A global network that answers on your behalf. You point DNS at it, and from that moment it is the only address the world has for you. Every request arrives here first, and it decides whether your server ever hears about it.
    Why take it
    Four things at once: it hides your origin, absorbs attacks before they cost you anything, ends TLS near the user, and answers cached requests without waking your machine. The free tier already does most of this.
    What you can put in it
    DNS · the proxy (orange cloud) · CDN cache and cache rules · WAF with managed rulesets · rate limiting · bot management · Turnstile instead of a captcha · DDoS mitigation (always on) · page rules and redirects · Workers — your own code at the edge · KV and R2 for storage with no egress fee · Load Balancing across regions · Zero Trust Access, which puts an entire admin panel behind a login before it reaches you · Tunnel, so your server needs no inbound port at all · analytics and logs.
    You set
    SSL mode Full (strict), what may be cached and for how long, which paths are rate-limited, and which countries or ASNs are allowed near you at all.
    It breaks when
    A personalised page gets cached and served to everybody — a data leak dressed as an optimisation. Or the SSL mode is Flexible, which leaves the last hop in plaintext.
    What it costs
    Mostly a flat price, and egress to users from the cache is free — which is the largest single line item it removes from your bill.
  8. 07your account

    Your cloud — a Hetzner project, or an AWS account

    an account, not a computer · everything in it is either a machine, or a rule about machines

    What it is
    The place where you press “create server”. It holds the things that stand beside your machine rather than on it, and it is the layer where you decide who may reach it.
    What lives here
    The firewall (Hetzner Cloud Firewall, an AWS security group) · the private network, 10.0.0.x between your own boxes · a floating or elastic IP you can move to another machine in seconds · volumes, which are extra disks · snapshots and images of the whole machine · a load balancer once you have two servers · object storage for uploads · any other machines — a second app box, a separate database box · and the boring but decisive ones: the bill, the API token, and who is allowed to log in.
    Hetzner or AWS
    The same idea at different depth. A Hetzner project is a short list at a flat monthly price. An AWS account is a hundred metered services and a VPC you must design. Start with the short list; move a piece at a time when a piece actually hurts.
    The test
    If it survives you deleting the server, it belongs to the cloud account. If it disappears with the server, it was on the machine.
    It breaks when
    The firewall allows :443 from the whole world instead of only Cloudflare’s ranges — and every control at station 06 can then be walked around. Or the database is reachable from the internet at all.
  9. 08rented, in your account

    The load balancer — optional, and not on your server

    Hetzner Load Balancer · AWS ALB · :443 → your machines

    What it is
    A separate appliance you rent by the hour. It health-checks two or more machines and sends each request to one that answers. That is its entire job.
    Do you need one
    Only once you have more than one machine. With a single box you have none — Cloudflare is already in front, and nginx already forwards. Do not add it out of habit.
    Not to be confused with
    nginx at station 09, which is a process on your server, and Cloudflare at 06, which is in front of everything. All three are proxies; only one of them is yours to log into.
    It breaks when
    The health check runs a database query. One slow query and it removes every backend at once, turning a degradation into a total outage that cannot recover.
  10. 09your machine

    nginx — the web server, and the first thing that is actually yours

    nginx or Caddy · listens on :80 and :443 · one process, thousands of connections

    What it is
    A program whose job is HTTP and the outside world. It accepts the connection, ends TLS 2 using the origin certificate, and then either answers from a file on disk or hands the request onwards. It is written in C and holds idle connections for almost nothing — which is exactly what a slow mobile client is.
    What you put here
    The origin certificate · static files and uploads, served without waking Python · client_max_body_size · read and send timeouts · gzip or brotli · real_ip from CF-Connecting-IP, or every log line you own will say “Cloudflare” · a cheap rate limit · /healthz · and finally proxy_pass to 127.0.0.1:8000.
    Could you skip it
    Technically yes, and you will regret it at the first large upload, the first slow client and the first static file.
    It breaks when
    The body-size limit rejects uploads with an unhelpful error, or there are too few worker connections, so requests queue invisibly before your code has run at all.
  11. 10your machine

    uvicorn — the application server, the thing that runs Python

    uvicorn or gunicorn · 127.0.0.1:8000 · one process per CPU core

    What it is
    A server whose job is your code. It takes the HTTP request nginx forwarded, turns it into a call into Python over the ASGI protocol, waits for your function, and turns the result back into a response.
    How many
    One worker process per core, because one Python process uses one core. Four cores, four workers, supervised by systemd or gunicorn.
    You set
    The bind address — 127.0.0.1, never 0.0.0.0, so nothing but nginx can reach it · the worker count · graceful shutdown on SIGTERM so a deploy drains instead of dropping.
    It breaks when
    One blocking call — a synchronous database driver, a requests.get with no timeout — stalls the event loop and every other request on that worker with it.
  12. 11FastAPI

    Middleware — the chain every request passes through

    CORS · GZip · your own request-id middleware

    What it is
    Code that runs before and after every single handler, in the order you registered it. The first place where the request is your problem rather than a protocol.
    The one thing to do here
    Create a request id and attach it to every log line, then return it in a response header. It costs an hour and it is the difference between reading logs and guessing.
    It breaks when
    The order is wrong — logging before authentication strips nothing, so tokens and passwords end up in your log storage forever.
  13. 12FastAPI

    Routing — which function answers this path

    APIRouter · @app.get("/orders/{id}") · path and query parameters

    What it is
    The match from method and path to one of your functions, with the parameters parsed and typed on the way in.
    Keep it thin
    The handler should read the input, call one service function, and return. Nothing else.
    It breaks when
    Business logic and database queries live in the handler, where nothing can test them and nothing else can reuse them.
  14. 13FastAPI

    Authentication — who are you?

    Depends(get_current_user) · a session cookie or a JWT · Argon2 or bcrypt

    What it is
    Proving identity, once, and turning the proof into a user object the rest of the request can trust.
    You choose
    A stateless token, which is fast and cannot be revoked, or a session in Redis, which costs a lookup and can be. Short-lived tokens plus a refresh token is the usual compromise.
    It breaks when
    The password hash is fast — MD5, SHA-256 — so a leaked table is an immediate mass takeover. Use Argon2id or bcrypt, which are slow on purpose.
  15. 14FastAPI

    Authorisation — may you?

    Depends(...) · scopes and roles · a WHERE clause with the tenant in it

    What it is
    A different question from the last one, asked about this object: you are logged in, but is order 17 yours?
    Where it must live
    In the query, not in an if after it. SELECT … WHERE id = :id AND owner_id = :me cannot be forgotten the way a check can.
    It breaks when
    You change the id in the URL and get somebody else’s data. The most common serious application flaw in existence, and the easiest one to test for — go and try it now.
  16. 15FastAPI

    Validation — is this input even sane?

    Pydantic models · request and response schemas

    What it is
    The boundary where untrusted text becomes typed objects. FastAPI does most of it for you, which is the single best reason to be using it.
    What Pydantic will not do
    Decide what a field is allowed to mean. A valid integer price sent by the client is still a price you must never trust — look it up server-side.
    It breaks when
    SQL is built by string concatenation; a URL is fetched without an allowlist; a file is trusted by its extension; a role arrives in the request body and is believed.
  17. 16FastAPI

    Your business logic — the only part nobody else can write

    a service layer, called by the router, testable without HTTP

    What it is
    The reason the other twenty-three stations exist. Everything before it was plumbing; everything after it is delivery.
    The rule for every call that leaves this box
    A timeout and a fallback on every single one. A dependency that hangs rather than refuses will hold your workers until none are left, and one non-essential feature takes the whole service down.
    Anything slow
    Does not belong here. Put it on the queue at station 21 and answer the user now.
  18. 17your machine

    The cache — Redis, the second place the journey can end

    Redis · 127.0.0.1:6379 · memory is about a hundred times faster than disk

    What it is
    A store of answers you have already worked out. A hit here means the database is never touched — which is the second dashed branch on the figure.
    You set
    maxmemory and an eviction policy, or it will eventually take the whole machine · a TTL on every key · and a key that includes the user or tenant.
    It breaks when
    The key has no tenant in it, and one customer is served another customer’s data. Also: caching used to hide a query that simply needed an index.
  19. 18FastAPI

    The ORM — objects turned into SQL

    SQLAlchemy · an async session · a connection pool in front of it

    What it is
    The translation layer. Convenient, and the single easiest place in the whole system to be accidentally slow.
    You set
    Eager loading where you know you will need the relation, and a pool size that matches what Postgres will actually accept.
    It breaks when
    The N+1 query: one query, then one more per row — four hundred round trips for one page, created by a lazy relation touched inside a loop. Log your query count in development.
  20. 19your data

    PostgreSQL — the truth, and the end of the outbound line

    :5432 · on the same box, or its own · the only thing you cannot rebuild

    What it is
    The terminus. Everything from here on is the way back.
    You set
    Indexes for the queries you actually run · max_connections and a pool that respects it · a statement timeout · and backups that leave the machine.
    It breaks when
    A missing index turns 40 ms into 4 s. The connection pool is exhausted, so a healthy database looks down. A long transaction holds locks and everything queues behind it.
    Never forget
    Replication is not a backup, and a snapshot is not a backup until the day you have actually restored one.
  21. 21the branch

    Queue and worker — the work that does not belong in a request

    Redis or Postgres as the queue · a worker process beside the app · fig. 5

    What it is
    Anything slow: email, PDFs, video, an AI call, a third-party sync. The request writes a message and returns; the work happens afterwards.
    The non-negotiable
    It must be idempotent, because the same message will arrive twice. And it needs a dead letter queue, or failures vanish silently for months.
    You alarm on
    Queue depth and the age of the oldest message. Never on worker CPU.
  22. 22FastAPI

    The response is built

    response_model · a status code that means something

    What it is
    Your objects become JSON and a status code. FastAPI’s response_model also decides what is left out — which is how a password hash stops being in an API response.
    It breaks when
    A stack trace or an internal version leaks in an error. Or 200 OK is returned with an error inside the body, so nothing can ever alert on it. Or a list is unpaginated and grows with your success.
  23. 23your bill

    Back out — and this is metered

    nginx → Cloudflare → the user · billed per GB by your provider

    What it is
    The bytes leaving your machine. Cloudflare does not charge you for what it sends to the user from cache; Hetzner or AWS charges you for what your server sends to Cloudflare.
    The big win
    Never proxy a large file through your application. Hand out a signed URL to object storage and let the user fetch it directly.
    It breaks when
    Nothing is cacheable, so every response pays full egress — on AWS this is the line item that surprises people.
  24. 24their device

    The render — where the user finally sees something

    the browser paints · this is the number that matters

    What it is
    The end of the clock that started at station 01. Your 45 ms API can still sit inside a four-second page.
    It breaks when
    Images have no dimensions and the layout shifts under their finger. One blocking third-party script holds the paint. The API was fast and nobody measured the page.
    The lesson of the whole line
    The user does not experience your architecture. They experience this station, and everything else is how you got here.

Four concerns keep reappearing along the line, and every time somebody asks “where does caching go?” the honest answer is “at six places, and they do different jobs”. Each layer is cheaper and blunter than the one behind it. Work from the outside in: the earlier you can answer, refuse or store something, the less of the line it costs you.

Your cloud — the account

Hetzner Cloud, an AWS account, DigitalOcean. Not a computer.

  • What it is. The place where you press “create server”. It holds rules and resources that sit beside your machine rather than on it.
  • What lives there. Firewall rules, the private network, floating IPs, extra volumes, snapshots, object storage, a load balancer once you need one, and any other machines.
  • Hetzner or AWS? Same idea, different depth. A Hetzner project is a handful of things at a flat price; an AWS account is a hundred services, each metered. Start with the short list.
  • The useful test. If it survives you deleting the server, it belongs to the cloud account. If it disappears with the server, it was on the machine.

nginx — the web server

A program whose job is HTTP and the outside world.

  • Definition. A server that accepts connections from the internet, terminates TLS, and either answers from a file on disk or hands the request to something else.
  • It knows about connections, certificates, headers, files, timeouts and body sizes. It knows nothing about your objects, your database or your users.
  • Written in C and it holds thousands of idle connections for almost nothing — which is exactly what a slow mobile client is.
  • Skip it? Technically yes. You will regret it at the first large upload, the first slow client, and the first static file.

uvicorn — the application server

A program whose job is to run your code.

  • Definition. A server that takes an HTTP request, turns it into a call into your language, waits for your function to return, and turns the result back into a response.
  • It knows about Python processes, the event loop, and the ASGI protocol. It does not serve files and it should never face the internet.
  • How many. One process per CPU core, because one Python process uses one core. Four cores, four workers, supervised by gunicorn or systemd.
  • Skip it? No. Something has to run Python. Without it, nginx has nothing to forward to.

FastAPI — neither of the two

A framework. A library your code imports.

  • Definition. Not a server at all — it never opens a port and cannot listen for anything. uvicorn imports it and calls into it.
  • What it actually is. Stations 11 to 16: the middleware chain, the router that matches a path, the dependencies that authenticate and authorise, the Pydantic models that validate, and your own functions.
  • Why the confusion. uvicorn main:app looks like starting FastAPI. It is starting uvicorn, and handing it your FastAPI object.
  • The same shape elsewhere. Express needs node; Django needs gunicorn; Spring needs Tomcat; Rails needs Puma. Framework and server are always two things.

Note Three different things are called a proxyand one thing on the line is not a proxy at all

06 · the edge proxy

Cloudflare. Rented, global, in front of everything.

  • Whose machine. Theirs, in the city nearest the user. Your DNS record points here, so this is the only address the world has.
  • What it does. Ends the user’s TLS, answers from the CDN cache if it can, filters with the WAF, and absorbs an attack before it reaches your bill.
  • Where the request goes next. Out of Cloudflare, across the internet again, to one address you told it about — your load balancer, or your server directly.

08 · the load balancer

A Hetzner Load Balancer or an AWS ALB. Rented, in your account.

  • Whose machine. Its own — a separate appliance you pay for by the hour. It is not installed on your server, and you do not ssh into it either.
  • What it does. Health-checks two or more machines and sends each request to one that answers. That is its whole job.
  • Do you need one? Only once you have more than one machine. With a single box, skip it — Cloudflare is already in front, and nginx already does the forwarding.
  • The trap. A health check that queries the database: one slow query and it removes every backend at once. Station 08 on the hazard board.

09 · the reverse proxy

nginx or Caddy. On your machine — the same box as FastAPI.

  • Whose machine. Yours. It is a process on your server, started by systemd, listening on :80 and :443.
  • What it does. Terminates the origin TLS, serves static files and uploads without waking Python, enforces body size and timeouts, restores the real client IP, and then proxy_passes to 127.0.0.1:8000.
  • Why not point Cloudflare straight at uvicorn? Because uvicorn is not built to face the internet: no static files, no TLS you control, no request limits, and one slow client can hold a worker.

10 · not a proxy

uvicorn / gunicorn — the app server. This is where your code lives.

  • What it is. The process that actually runs Python. It speaks ASGI to FastAPI and HTTP to nginx, and it should bind to 127.0.0.1 so that nothing but nginx can reach it.
  • How many. Several worker processes, roughly one per core, supervised by gunicorn or by systemd — because one Python process uses one core.
  • FastAPI itself. Not a server at all. It is stations 11 to 16: the middleware chain, the router, the dependencies that authenticate and authorise, the Pydantic models, and your own functions.

Key How to read the linefive symbols, and each one means something

Stop

The request passes through and something happens to it. It cannot be skipped.

Interchange

A cache. The journey may end here and return immediately — stations 06 and 17.

Shortcut

A cache hit dropping straight to the return line. Free, fast, and where all the wins are.

Junction

Work leaves the line here and finishes later, on the branch line — station 16.

Terminus

The end of a leg: the click (01), the database (19), the product (24).

Zone

Who owns this ground. Cooler is further from you; warmer is more yours, and costs more.

Rented

You pay for it and depend on it, but you do not run it. No shell, no patching, no kernel — Cloudflare’s edge.

Demarcation

Where responsibility changes hands. Right of it: your machine, your patches, your backups, your pager.

Cloudflare — you rent it

In front of station 06. Their hardware, their kernel, their bill.

  • DNS and anycast. Your name resolves to their address, in a city near the user. Your own address is never published.
  • TLS ends here. The certificate the browser sees is theirs. The hop from the edge to your box is a second, separate connection.
  • Filtering. WAF rules, bot scores, rate limits per IP or per path, and a volumetric attack absorbed before it costs you a byte.
  • Cache. A hit is answered without your server ever waking. Cache rules, TTLs, and — carefully — what must never be cached.
  • What it is not. Not a backup, not a database, not your logs. If the origin is down, a cache hit still works and everything else returns an error.
  • The bill. Mostly flat, and egress to users from cache is free — which is the largest single line item it removes.

The door — the whole boundary

Five rules. Get these wrong and the column to the left is decoration.

  • The origin IP must not be reachable. Firewall inbound 443 to Cloudflare’s published ranges only — or run a Tunnel and open no inbound port at all.
  • The IP must not be discoverable either. Old DNS records, certificate transparency logs, and mail sent directly from the box all leak it.
  • Full (strict), always. An origin certificate on nginx and validation on. Flexible mode leaves the last hop in plaintext across the public internet.
  • Restore the real client IP. CF-Connecting-IP → nginx real_ip → your logs. Otherwise every request you own appears to come from Cloudflare, and rate limiting by IP bans everyone at once.
  • A shared secret header. Injected at the edge, checked at the origin, rejected if absent. It survives the day someone finds your address.

Your server — you run it

Stations 09 to 19 all live here. This is the box in fig. 3.

  • You patch it. Kernel, OpenSSL, nginx, the runtime, the database. Nobody else will, and “it has been up for 400 days” is not a boast.
  • You back it up. Off the box, encrypted, and restored on purpose at least once. A provider snapshot in the same account is not a backup.
  • You are paged for it. Disk percentage, memory, load, certificate expiry, and whether the process is actually answering — not merely running.
  • It is one machine. Which means one blast radius. That is an acceptable trade for a very long time — provided a replacement is one script away.
  • The bill does not move. A flat monthly price cannot be turned into a financial attack. Metered compute can.

One machine is a completely respectable architecture, and it will carry more traffic than most products ever see. It cannot survive the failure that takes the machine itself — so the only real questions are how quickly you can build a new one, and when you last restored the backup.

Beneath every station — the floor

CPU · RAM · SSD · kernel · syscalls · scheduler · context switching · memory management · file systems

This is not a station; it is the ground all twenty-four stand on, and it is why the advice above is true rather than arbitrary. Caching works because memory is about a hundred times faster than disk. An event loop stalls because of how the scheduler hands out time. A container starts in milliseconds because it shares a kernel instead of booting one. You can build a system without this layer. You cannot debug the strange ones. On a rented machine this floor is not underneath your responsibility — it is inside it: it is the bottom two layers of fig. 4, and you are the one who patches it.

Audit these five this week — and test them, do not reason about them

  1. Station 14 · missing authorisation. Change an id in a URL. Does it work? Go and try it now, on your own system.
  2. Station 17 · a cache key without a tenant. Read one cache key out loud. Whose data can it return?
  3. Station 21 · a non-idempotent money handler. What happens if this message arrives twice?
  4. Station 18 · an N+1 query. Count the queries your busiest page issues. Does the number grow with rows?
  5. Station 08 · a health check that is too deep. Does it fail when the database does? Then it can remove every backend at once.

In short The whole line in seven sentences

  1. A click becomes a network request, and DNS, TCP and TLS all happen before one byte of it reaches you.
  2. It should be answered as early as possible — at the edge or in the cache — because everything past there costs money.
  3. In front of all of it sits rented ground you do not run, and behind it exactly one machine you do — keep the door between them the only way in, or everything the edge does for you becomes optional.
  4. Your application asks three questions in order: who are you, may you, is this valid — and only then does your product.
  5. The database is almost always the real bottleneck, standing on a floor of CPU, memory, disk and kernel.
  6. Anything slow does not belong in the request at all; it goes on a queue, and then it must be idempotent.
  7. All of it is wrapped in four things that are not stations: identity, observability, reliability and cost.
