The Request Line

One click, one route, twenty-four stops. Every station says what happens there and what is waiting for you. Two stations let the journey end early — and almost all performance work is the effort to end it at one of them.

Key How to read the linefive symbols, and each one means something

Stop

The request passes through and something happens to it. It cannot be skipped.

Interchange

A cache. The journey may end here and return immediately — stations 06 and 17.

Shortcut

A cache hit dropping straight to the return line. Free, fast, and where all the wins are.

Junction

Work leaves the line here and finishes later, on the branch line — station 16.

Terminus

The end of a leg: the click (01), the database (19), the product (24).

Zone

Who owns this ground. Cooler is further from you; warmer is more yours, and costs more.

Beneath every station — the floor

CPU · RAM · SSD · kernel · syscalls · scheduler · context switching · memory management · file systems

This is not a station; it is the ground all twenty-four stand on, and it is why the advice above is true rather than arbitrary. Caching works because memory is about a hundred times faster than disk. An event loop stalls because of how the scheduler hands out time. A container starts in milliseconds because it shares a kernel instead of booting one. You can build a system without this layer. You cannot debug the strange ones.

Shaded rows are the five that cause most real damage. None of them are exotic.
StopStationWhat waits there
01browserA blocked event loop freezes the page before the request is even sent. No loading state, so the user clicks three times.
02DNSA time-to-live of hours, so failover takes hours too. A client library that resolves once and caches it forever.
03TCP + TLSAn expired certificate — one of the most common self-inflicted outages there is. No connection reuse, so you pay the handshake every time.
04the requestA session token in local storage, plus one cross-site scripting bug, equals account takeover. No idempotency key on a request that spends money.
05the networkPacket loss presents as inexplicable slowness. You cannot fix this layer, only design around it.
06CDN edgeNothing cached, so every request travels the whole route and you pay full egress. Worse: a personalised page cached and served to everyone.
07VPCA database reachable from the internet. A rule open to the whole world on an admin port. Everything in one availability zone.
08load balancerA health check so deep that one slow database removes every backend at once — a degradation becomes a total outage, and nothing can recover. Also: an idle timeout that cuts a long report; draining shorter than the slowest request; retries amplifying overload into collapse.
09proxyA body size limit rejecting uploads with an unhelpful error. Too few worker processes, so requests queue invisibly before your code runs.
10runtimeOne blocking call stalls everything. A thread pool eaten by a slow dependency, with nothing left for healthy requests. A leak that only shows after six hours.
11middlewareThe order is wrong and credentials end up in your logs. No request id created here, which makes every later investigation manual.
12routingBusiness logic and database queries living in the controller, untestable and unreusable.
13authenticationA long-lived stateless token, so logout does not actually work. A fast password hash, so a leaked table is an immediate mass takeover.
14authorisationChange the id in the URL and get someone else’s data. The most common serious application flaw in existence, and the easiest one to test for. Authentication was checked; authorisation was forgotten.
15validationTrusting a price or a role sent by the client. SQL built by concatenation. A URL the server will fetch without an allowlist. A file trusted by its extension.
16logicNo timeout on a downstream call — a dependency that hangs rather than refuses holds your threads until every worker is blocked, and one non-essential feature takes the whole service down. Also: a multi-step process with no compensation, leaving records half-finished.
17cacheA cache key without the user or tenant in it — a data leak dressed as an optimisation. Also: caching used to hide a query that simply needed an index.
18ORMThe N+1 query. One query, then one more per row: four hundred round trips for a single page, created by a lazy-loaded association inside a loop.
19databaseA missing index turning forty milliseconds into four seconds. Connection pool exhausted, so a healthy database looks down. A long transaction holding locks and blocking everything behind it.
—the floorCPU credits, disk throughput and memory limits produce throttling that looks exactly like slow code. Check the credit balance before you profile the query.
21queue, workerNot idempotent, so the customer is charged twice. Also: no dead letter queue, so failures vanish silently for months; a visibility timeout shorter than the job, so two workers do the same work.
22the responseA stack trace or internal version returned in an error. Two hundred OK with an error inside the body, so nothing can alert on it. An unpaginated list that grows with your success.
23egressLarge files proxied through your application instead of handed off with a signed URL. Full egress paid because nothing caches in front.
24the renderA forty-five millisecond API inside a four-second page. Unsized images causing layout shift. One blocking third-party script.
allacross the lineA destructive migration shipped with the code that needs it. One leaked long-lived credential. Backups in the same account, never once restored. Alerts nobody reads. A rollback path nobody has ever used.

Audit these five this week — and test them, do not reason about them

  1. Station 14 · missing authorisation. Change an id in a URL. Does it work? Go and try it now, on your own system.
  2. Station 17 · a cache key without a tenant. Read one cache key out loud. Whose data can it return?
  3. Station 21 · a non-idempotent money handler. What happens if this message arrives twice?
  4. Station 18 · an N+1 query. Count the queries your busiest page issues. Does the number grow with rows?
  5. Station 08 · a health check that is too deep. Does it fail when the database does? Then it can remove every backend at once.

In short The whole line in six sentences

  1. A click becomes a network request, and DNS, TCP and TLS all happen before one byte of it reaches you.
  2. It should be answered as early as possible — at the edge or in the cache — because everything past there costs money.
  3. Your application asks three questions in order: who are you, may you, is this valid — and only then does your product.
  4. The database is almost always the real bottleneck, standing on a floor of CPU, memory, disk and kernel.
  5. Anything slow does not belong in the request at all; it goes on a queue, and then it must be idempotent.
  6. All of it is wrapped in four things that are not stations: identity, observability, reliability and cost.
