Atlas of Agent Security

An AI agent is a new kind of insider. It holds credentials, it reads text written by strangers, and it acts on both without pausing to wonder which was which. This is not a model-safety problem. It is an authorisation and observability problem wearing a model-safety costume — and that mismatch is the whole opportunity.

Scope of this atlas

Everything here is written from the defender's side: what to instrument, what to constrain, what to record. The attacks are described at the level needed to design a control, which is the level a security engineer, an auditor and a buyer all need. Sheet 7 walks one chain end to end for exactly that reason — you cannot sell, or build, a control for a threat you cannot narrate.

Sheet 1

The Agent's Reach

Patch panel Covers · Authorization · Secrets Management · OWASP Top 10 · AI Agents

Before any attack, one question: what can this thing already touch on an ordinary Tuesday? A coding agent on a developer's laptop routinely holds more effective authority than any single employee — because it inherits every credential that laptop has ever been given, and uses all of them without a second thought.

Item key — the reach, term by term

01Effective authority

Not what the agent was granted, but everything reachable from where it runs: inherited sessions, cached tokens, config files, mounted drives, open VPN routes.

02Credential inheritance

An agent on a laptop uses the human's credentials because that is the path of least resistance. It is also why the audit trail names the human and not the agent.

03Blast radius

What one compromise reaches. For agents it is unusually wide, because the same process holds repository, cloud, data and communication access simultaneously.

04Standing privilege

Access that exists whether or not it is being used. Agents make it far more dangerous, because idle credentials are now continuously available to an automated process.

05Shadow agents

Agents employees run without approval — personal API keys, browser extensions, unsanctioned MCP servers. Usually the largest population, and entirely uninventoried.

06Human-in-the-loop, nominally

Approval prompts that appear so often they are cleared reflexively. A control that is clicked through two hundred times a day is not a control.

07Read is not safe

"Read-only" limits damage to the database and does nothing about disclosure: anything read enters the context window, and the context window leaves your network.

08Non-human identity

The category name for service accounts, tokens and now agents. They already outnumber human identities in most companies, and they are governed far more loosely.

09Confused deputy

A privileged component performing an action on behalf of a less privileged requester. Agents are confused deputies by construction, which is why sheet 2 is structural rather than incidental.

10Egress

Any path out: HTTP, DNS, a git push, an email, a ticket comment, an image URL rendered by a chat client. Bounding egress is the highest-value control on this atlas.

11Provenance

Knowing which input caused which action. Almost never recorded today, and the single thing every post-incident investigation will demand. Sheet 6.

12Agent sprawl

The rate at which agents, tools and integrations multiply inside a company once they start working. The inventory problem always arrives before the control problem.

Sheet 2

The Mechanism

Overlap diagram Covers · OWASP Top 10 for LLM Applications · Authorization · Secure Coding

Nearly every agent breach reported so far is the same shape, and it needs only three conditions to be true at once. Two of them are what makes an agent useful, which is why this cannot be fixed by writing a firmer system prompt — the fix has to remove an edge of the triangle, not reword it.

Item key — the mechanism, term by term

01Direct prompt injection

The user types the attack themselves — jailbreaks, "ignore your instructions". Mostly a brand and content problem, and the least interesting one for an enterprise buyer.

02Indirect prompt injection

The attack lives in content the agent reads on someone else's behalf: a ticket, a page, a file. The user is innocent, the agent is obedient, and this is the one that costs money.

03The three conditions

Untrusted input, private data access, and an outbound channel. Any two are survivable. All three, and exfiltration is a feature of the system rather than a flaw in it.

04Taint

Once untrusted text enters a context window, every later action in that session is influenced by it. Tracking that spread — and refusing privileged actions on tainted context — is a real, buildable control.

05Invisible payloads

Zero-width characters, unicode tag blocks, white-on-white text, text rendered only inside an image. The human reviewer sees a clean document; the model reads the instruction.

06Exfiltration channel

Any outbound path, including ones nobody classifies as network access: an image URL, a DNS lookup, a pull request body, a comment posted back to the ticket.

07Rendered-markdown exfiltration

The agent writes an image tag whose URL contains the stolen data. The chat client fetches it to render it. No tool call was needed and no proxy saw a request from the agent.

08DNS exfiltration

Data encoded into subdomains of a domain the attacker controls. Survives most HTTP egress filtering, because DNS is almost always allowed to leave.

09Confused deputy

The agent has authority the attacker does not, and the attacker supplies the instruction. Every prompt injection is this classic vulnerability in a new costume.

10Guardrail

A classifier on input or output. Useful, probabilistic, evadable. Treat it as one control among several, never as the trust boundary.

11Dual-agent pattern

A quarantined reader with no tools, and a privileged executor that only accepts a validated plan. Removes the overlap by construction rather than by persuasion.

12Capability, not intent

The design question is never "will it decide to do this?" but "can it, if instructed?". Intent is unenforceable; capability is a configuration you own.

The sentence to repeat to buyers

An agent cannot be trusted to decide what to obey, because it cannot tell your instruction from a stranger's. Therefore the only durable controls are on what it is able to do and where its output is able to go — and those are ordinary, provable, auditable engineering, which is exactly what a security team knows how to buy.

Sheet 3

The Development Line

Transit diagram Covers · CI CD · Git · GitHub Actions · Secure Coding · Secrets Management

Seventeen stops from a ticket to production, with an agent involved at nearly every one. Stops 02 to 07 happen on a laptop, hold the highest privilege on the line, and are covered by no security product category that exists today. That gap is the subject of this atlas.

Item key — stop by stop

01The ticket

The first untrusted input. In most companies, customers, contractors or anyone with a support form can put text into a system an agent will later read as if it were an instruction.

02The prompt

The one moment a human states intent. Everything after it is the agent's interpretation, and no later stage compares the outcome against what was actually asked.

03Context assembly

The agent reads rules files, configuration, environment files and source. Any of these can carry instructions, and the ones checked into the repository are editable by anyone with commit access.

04Tool calls

Shell, filesystem, network, git. The moment authority is exercised. Auto-approve settings turn a supervised assistant into an unattended process with a developer's rights.

05Dependency resolution

Models suggest package names that do not exist. Attackers register them. Installation runs code before any scanner sees the artifact.

06Code generation

Volume with plausible style. The risk is not that it writes something obviously wrong — it is that a deliberate weakening is indistinguishable from an ordinary refactor.

07Tests

The agent that wrote the code also maintains the tests. A test changed to match broken behaviour produces the same green tick as a bug that was actually fixed.

08Commit

Authored under the human's identity, with hooks skippable by a flag. The agent's involvement vanishes from history exactly where the audit trail begins.

09Push

Branch protection, required checks and signed commits are the first genuine controls on the line — seven stops after the interesting decisions were made.

10Pull request

Written by the agent, describing the agent's work, read by a human under time pressure. The summary is more persuasive than the diff, and it is what gets read.

11Automated review

An agent reviewing an agent. Useful for style and obvious defects, correlated in exactly the blind spots that matter, and reassuring in tone regardless.

12Merge

Auto-merge on green removes the last human. Worth deciding deliberately whether agent-authored changes are eligible for it — most teams never decide, they inherit the default.

13Build

Where the real secrets are. Any script introduced earlier now executes with deployment credentials, in an environment that is trusted by construction.

14Artifact

Signing and provenance attestation let you prove that what shipped is what was reviewed. Cheap to add, rare to find, and the only defence against tampering after review.

15Infrastructure as code

A plan file is a diff too, and a widened permission inside one is far easier to miss than the same change made by hand in a console.

16Deploy

The end of prevention. Everything after this is detection, containment and rollback — all of which need the evidence that stops 02 to 07 never recorded.

17The live agent

If the product itself contains an agent, the whole atlas applies again on the production side, with customers supplying the untrusted text this time.

Sheet 4

Inside the Coding Agent

Cutaway section Covers · AI Agents · Secure Coding · Secrets Management · Git

Stops 03 and 04 of sheet 3, opened up. Eight channels reach the model; seven tools reach your company. Between them sits a single undifferentiated stream of tokens in which your instruction and a stranger's sentence are stored identically — which is the entire vulnerability, drawn once.

Item key — the agent's anatomy

01Rules file

A file in the repository that agents read as standing instructions. Enormously useful, and a persistent injection vector that arrives through an ordinary pull request.

02Auto-approve

The setting that lets tool calls execute without confirmation. The single largest change in an agent's risk profile, made by a developer, unlogged, in a preferences pane.

03Approval fatigue

Interrupting a person for routine actions trains them to approve everything. Every security control that fires too often converts itself into a rubber stamp.

04Slopsquatting

Registering package names that models frequently hallucinate, so the invented import resolves to attacker code. A supply-chain attack created by a model's confidence.

05Postinstall execution

Package managers run scripts at install time. Code executes before any scanner examines the artifact, on the machine with the most credentials on it.

06Working-directory escape

Reads and writes outside the project: home directory, SSH keys, cloud credential files, another repository. Cheap to detect and rarely watched.

07Sandbox

Running the agent in a container or VM with mounted scopes. Good, underused, and frequently defeated by mounting the whole home directory for convenience.

08Egress allowlist

The set of hosts the agent process may contact. Absent by default in every tool shipped today, and the cheapest control with a real effect.

09Provenance

The record connecting a line of code to the session, prompt and inputs that produced it. Does not exist in git, and is what makes an agent-authored change reviewable.

10Session recording

The full, replayable trace of an agent task. The equivalent of a flight recorder — dull until the day it is the only evidence anyone has.

11Risk-scored interruption

Approving silently by default and interrupting only for high-risk actions. The design that keeps a human meaningfully in the loop without training them to ignore it.

12Deterministic replay

Re-running a recorded session against a policy to ask "would this control have stopped it?". How a security team evaluates a control before deploying it, and how you demo one.

Sheet 5

The Context Supply Chain

Supply chain Covers · AI Agents · Secure Coding · OAuth2 · Secrets Management

You audit the packages your code imports. Nobody yet audits the tools, servers, memories and other agents that write into your agent's context — and a tool description is executable text, delivered by a third party, that can change after you approved it.

Item key — the supply chain

01MCP

The standard way to expose tools and data to agents. Genuinely useful, adopted fast, and it turns tool descriptions written by strangers into text your model obeys.

02Tool poisoning

Instructions hidden inside a tool's description or schema. The agent reads them while deciding what to call, before any tool has actually run.

03Rug pull

A server that behaves during evaluation and changes after adoption. Defeated by pinning versions and diffing descriptions on every load — and by nothing else.

04Cross-server shadowing

One installed server influencing how the agent uses another. The security property you need is isolation between servers, which no client enforces today.

05Token brokering

Giving a tool server a short-lived, scoped credential minted per call rather than a standing OAuth grant. The difference between lending a key and lending the building.

06Memory poisoning

Writing an instruction into the agent's persistent notes so it executes in a later, unrelated session. Converts a single exposure into a standing order.

07Delegation

One agent invoking another. Without an attenuating token per hop, authority accumulates instead of narrowing, and attribution is lost at the first handover.

08Attenuation

Each hop receives strictly less authority than its caller. An old, well-understood capability-security idea, and the correct model for multi-agent systems.

09Agent SBOM

The inventory nobody has: which agents exist, which servers and skills they load, which versions, which credentials, which egress. Selling the inventory is how you get in the door.

10Description drift

The difference between the tool description reviewed and the one loaded today. Cheap to detect, invisible without instrumentation, and a clean alerting product on its own.

11Propagating injection

An instruction whose payload is to reproduce itself into other documents an agent can write. Worm behaviour without any code — plain text in a shared wiki is enough.

12Model supply chain

Weights, adapters and fine-tunes pulled from public hubs. The same provenance questions as any dependency, with far less tooling and far more trust extended by default.

Sheet 6

The Attribution Gap

Forensic plate Covers · Authentication · Authorization · JWT · OAuth2 · Secrets Management

An incident happens. Someone opens the logs and finds a person's name on an action that person did not take. This is not a logging bug — it is the direct result of agents borrowing human credentials, and it makes every investigation, every audit and every insurance claim harder than it needs to be.

Item key — identity and evidence

01Non-human identity

Service accounts, tokens, workloads and now agents. Already outnumbering human identities several times over in a typical company, and governed by a fraction of the process.

02Workload identity

Issuing short-lived credentials to a process based on where and what it is, rather than storing a secret. The mature pattern agents should inherit rather than reinvent.

03Credential minting

Creating a scoped credential at the start of a task and letting it expire at the end. Removes standing privilege without removing capability.

04Scope

The declared boundary of what an agent may touch. Only meaningful if something enforces it — a scope in a spreadsheet is a wish.

05Attenuation

Each delegation carries less authority than the one before. Prevents an agent chain from accumulating the union of everyone's permissions.

06Causal link

The record that this action followed that input. The single most valuable field in an agent log, and the one nothing writes today.

07Session record

One task, one replayable file: prompts, context, tool calls, diffs, network, approvals. The unit an investigation actually needs.

08Retention

How long you keep those records. Long enough to investigate, short enough to defend under data protection rules — and decided before an incident, not during one.

09Offboarding

When a person leaves, their agents, tokens and grants leave with them. The most commonly missed step, and the easiest audit finding to write.

10Inventory

The list of agents that exist. Almost every company's first honest answer is "we do not have one", which is why discovery is the natural first product.

11Attestation

Signed evidence that an action happened as recorded. Turns a log file into something usable in a dispute, a claim or a regulatory filing.

12Segregation of duties

The classic control: the party that proposes a change is not the party that approves it. Agents break it quietly, by writing the code, the tests, the description and the review.

One Kill Chain

Timeline Covers · OWASP Top 10 · CI CD · Secure Coding · AI Agents

One plausible chain, drawn end to end, with real timings. Nine steps, eleven minutes of machine time, no exploit, no malware, no stolen password — and every control a well-run engineering organisation already pays for lets it through.

On responsible detail

The chain above is deliberately described at design level: enough to build and test a control, not a recipe. That is the right altitude for a defender's document — and, incidentally, the right altitude for a sales conversation, where the goal is to make a risk legible rather than to teach an audience how to run it.

Sheet 8

The Control Plane

Layered schematic Covers · Authorization · Secrets Management · CI CD · Secure Coding

Five places to put a control, and a recorder underneath all of them. Every item here is deterministic — a rule about identity, authority or data flow — which means it can be tested, audited and trusted to behave identically tomorrow. Nothing on this sheet asks a model to be careful.

Item key — the controls

01Agent registry

The inventory: which agents exist, who owns each, what it is for, when it expires. The unglamorous first deliverable, and the one every buyer immediately understands.

02Scope declaration

A written statement of what an agent may touch, enforced at the credential and network layer rather than trusted to a prompt.

03Just-in-time credentials

Minted at task start, expired at task end. Removes standing privilege — the thing that turns a small mistake into a large incident.

04Hard budgets

Caps on spend, actions, data volume and wall time that stop rather than warn. An agent loop with an alert is still an unbounded loop.

05Source labelling

Recording where each piece of context came from. Everything downstream — taint, policy, forensics — depends on this one field existing.

06Sanitisation

Stripping invisible characters and flattening hostile markup on ingest. Cheap, worth doing, and never sold as the boundary.

07Taint-aware policy

Rules that tighten automatically once untrusted content enters the session: no writes to sensitive paths, no new hosts, no credential reads.

08Risk-scored approval

Silence for routine actions, an interruption for the rare dangerous one. The design that keeps a human meaningfully in the loop instead of nominally in it.

09Egress proxy

One recorded path out, default deny, allowlist per task. The highest ratio of protection to effort on this entire atlas.

10Provenance attestation

Signed evidence linking a change to the session and inputs that produced it, attached to the pull request where a reviewer will actually see it.

11Replay

Re-running recorded sessions against a candidate policy. Turns "would this help?" from a debate into a measurement, for you and for the customer.

12Agent red teaming

A standing suite of injections and exfiltration attempts run against your own agents on a schedule, because the attacks change faster than the architecture.

Sheet 9

Where the Money Is

Market map Covers · the commercial reading of sheets 1 to 8

Seven layers, four of them already crowded with funded companies, three of them close to empty. The empty ones are not empty because they are unimportant — they are empty because they only became buyable when agents got write access to real systems, which happened about eighteen months ago.

Item key — the commercial vocabulary

01The wedge

The smallest thing worth paying for that gets you installed. Here: read-only recording, because it answers a question the buyer is already being asked and cannot break anything.

02Land and expand

Sell evidence, then sell the controls the evidence justifies. Each stage funds and de-risks the next, and the customer's own data makes the case.

03Time to value

How long from install to the customer seeing something they did not know. Aim for one afternoon; anything measured in weeks dies in a pilot queue.

04Enforcement point

A place where you can actually stop an action — the tool boundary, the proxy, the credential. Products that only observe get renewed once; products that enforce get embedded.

05Platform risk

The chance that the agent vendor ships your feature. Mitigated by spanning several runtimes and by being independent of the thing you are recording.

06Friction budget

How much a developer will tolerate before disabling you. The scarcest resource in this category, and the reason risk-scored interruption matters more than coverage.

07Compliance pull

Demand created by auditors, questionnaires and regulation rather than by fear. Slower to start, far more durable, and it survives a budget freeze.

08Design partner

Two or three companies with real agent fleets who will let you record for free in exchange for the findings. Their recordings are your rule library and your first case studies.

09Proof by replay

Showing what your rules would have caught on the customer's own history. The most convincing demo available in this category, and one only a recorder can produce.

10Neutrality

Being independent of the agent vendor is a feature you can charge for, in the same way an auditor's independence is the point of an audit.

11Sequencing

Record, then bound egress, then interrupt, then mint credentials. Doing these in the wrong order produces a product that is correct and unsellable.

12The unfair question

"What did your agents do last week?" It is unfair because everyone should be able to answer it and nobody can. Build the answer, and the rest of the roadmap writes itself.

Where this atlas ends and judgement begins

Sheets 1 to 7 describe a threat model that is observable today and will not be argued with by anyone who runs agents at scale. Sheet 9 is a judgement about a market that is moving quickly: the bar lengths, the crowding and the sequencing are opinions, not measurements, and they should be re-checked against real conversations with real buyers before anyone spends a year building against them.
