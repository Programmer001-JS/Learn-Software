One URL, one page, and everything that has to happen between the first byte and a button that responds. Sheet 1 is the route a page load actually travels; sheets 2 to 4 open up the three machines inside the browser, and sheets 5 to 8 are the choices you make on top of them. The browser is fixed machinery with a 16.7 ms timetable — frontend engineering is the craft of cooperating with it instead of fighting it.

Sheet 1

The Page-Load Line

Transit diagram Covers · Browser Internals · HTML · CSS · DOM and CSSOM

One URL, one route, twelve stops. The server owns the first three; the browser owns everything after the first byte. Two stations stop the line on purpose — CSS holds back painting, a plain script holds back parsing — and stops 08 to 10 are drawn with a loop because a page is not rendered once, it is rendered sixty times a second.

Step key — every stop on this sheet, and what it does

01URL entered

A navigation starts: a typed address, a link, a redirect. Everything about a browser follows from what happens next — it is about to download and run code from a stranger.

02DNS, TCP, TLS

Resolve the name, open a connection, negotiate encryption. Several round trips before one byte of HTML exists, which is why connection reuse and CDNs matter. Drawn in full in folder 04.

03HTTP GET

The request for the document. Time to First Byte is the server's share of the load; everything after it belongs to the browser and to the code you sent it.

04HTML streams in

The parser builds the DOM incrementally as bytes arrive, so content can appear before the file finishes. The parser is extremely tolerant: malformed markup is repaired silently, not rejected.

05CSS found

A <link rel="stylesheet"> is fetched and parsed into the CSSOM. Rendering is blocked until it arrives, because no element can be drawn before its style is known. Keep critical CSS small and early.

06Script found

A plain <script> stops the parser while it downloads and executes, because it might change the document. defer and async remove that stall.

07Render tree

DOM and CSSOM combined: only visible elements, each with its computed style. display:none elements are left out entirely. Sheet 2 opens this stop up.

08Layout

Geometry: the exact position and size of every box. The most expensive stage, triggered again by any change to width, height, position, font size or DOM structure.

09Paint

Filling pixels: colours, text, shadows, borders. Cheaper than layout, still real work, and re-run whenever appearance changes.

10Composite

Painted layers are assembled on the GPU process. Changes that only touch transform or opacity start here, skipping 08 and 09 — the root of most animation advice.

11First pixels

Content on screen. Largest Contentful Paint measures when the main content finished painting; unreserved image space here becomes Cumulative Layout Shift a moment later.

12Interactive

DOM complete fires DOMContentLoaded; images and fonts finishing fires load. From now on every event is a task on the event loop — sheet 4.

AHTTP cache

The headers you set on the server decide whether stops 02 to 05 happen at all. A cached document or stylesheet costs no round trip and no bytes over the wire.

BRender blocking

CSS in the head deliberately holds back the first paint. Large or late stylesheets therefore delay everything the user sees, however fast the server was.

S1Plain script

Parsing stops, the file is fetched and run, then parsing resumes. One slow third-party script in the head can hold the whole page hostage.

S2defer

Downloaded in parallel with parsing, executed in order after parsing finishes. The right default for almost every script, and one of the two habits that fix most render-blocking problems.

S3async

Downloaded in parallel, executed the moment it arrives — interrupting the parser and ignoring order. Suits independent scripts such as analytics, nothing that depends on another file.

16.7The frame budget

At 60 frames per second the browser has 16.7 ms for script, style, layout, paint and composite together. A single long task blocks all of it, and users feel it as jank.

Nothing in the browser is trustworthy

Everything on this line runs on a machine you do not control. Browser validation, route guards, hidden elements and client state are conveniences; an attacker can skip the page entirely and call your server directly. Validate on the server, set CSP and cookie flags there, and keep tokens where scripts cannot reach them.

Sheet 2

The Pixel Pipeline

Cutaway section Covers · Rendering Engine · DOM and CSSOM · CSS

Stops 07 to 10 of sheet 1, opened up. Two trees go in, a frame comes out, and every change you make enters the pipeline at one of three doors. Each stage is more expensive than the one after it — so the question for any style change is not "does it work" but "which door did it come through".

Step key — the vocabulary of this sheet

01DOM

The live object tree built from HTML: every element, attribute and text node. Not slow to read — expensive only because changing it can trigger layout and paint.

02CSSOM

The parallel tree of style rules built from CSS. Rendering waits for it, which is why stylesheet size and placement in the head matter so much.

03Cascade

The rulebook for conflicts: importance first, then specificity, then source order. !important is shouting — it works once, then everyone shouts.

04Specificity

Inline 1000, id 100, class 10, element 1. #nav .item a scores 111 and beats .nav .item a at 21 regardless of intent. Keep it low and flat.

05Box model and layout

Content, padding, border, margin — with border-box set globally. Flexbox lays out one dimension, Grid two. Write mobile-first and add rules for wider screens.

06Render tree

Visible nodes with computed styles. display:none removes an element from it but not from the DOM, so hidden data is still delivered and readable.

07Style recalculation

Matching selectors to affected elements after a class or rule changes. Low to medium cost, made worse by deeply nested selectors on large trees.

08Reflow

Geometry changed — width, height, position, font size, DOM insertion, font loading. Layout re-runs for affected elements, then paint and composite follow. The expensive door.

09Repaint

Appearance changed without geometry — background colour, visibility, shadows. Layout is skipped; pixels are redrawn. Moderate.

10Composite only

transform and opacity on a layer: the GPU moves existing pixels. Two whole stages skipped, which is why smooth animation uses only these.

11Layout thrashing

Reading geometry after writing styles forces a synchronous layout; in a loop it happens every iteration. Batch all reads, then all writes.

12DocumentFragment

Build many nodes off-document and insert them in one operation: one layout instead of one per item. Frameworks do the equivalent for you.

13Compositor layer

An element promoted to its own GPU surface. Cheap to move, costly in memory — use will-change on the few elements that animate, never globally.

14Core Web Vitals

LCP, CLS and INP: paint time, layout stability and input responsiveness — rendering-engine behaviour turned into an SEO ranking factor.

The engine parses hostile input, in C++, at speed

Rendering engines are historically one of the largest sources of remote-code-execution bugs in consumer software, which is why renderers are sandboxed and browsers update aggressively. Your part: keep users on current browsers, set a Content Security Policy, and never let user-controlled styles in — CSS injection can exfiltrate data through attribute selectors and background URLs.

Sheet 3

From Source to Machine Code

Process plant Covers · TypeScript · JavaScript · JavaScript Engine

Stop 06 of sheet 1, opened up: what happens to your code between the editor and the CPU. Two plants joined by a network cable. The first plant checks your types and then throws them away; the second plant guesses them all over again from how the code behaves — and throws its own work away the moment a guess is wrong.

Step key — every stage and term on this sheet

01TypeScript source

JavaScript plus static types — interfaces, unions, optional fields. A superset: every JavaScript file is already valid TypeScript, which is why adoption can happen file by file.

02Type checking

tsc and the editor's language server catch the typo, the missing field, the possibly-undefined value before the code runs. Enable strict on day one; adding it later hurts.

03Type erasure

Annotations are stripped and plain JavaScript emitted. esbuild and swc do this fast by skipping the check entirely, so a build can be green while the types are wrong.

04Bundle

Vite, Rollup or esbuild combine and minify modules into the files users download. The only artifact of the build that users ever pay for.

05Parse

Source text becomes an abstract syntax tree. On large bundles and weak phones this alone costs real time before anything executes.

06Ignition

V8's bytecode interpreter. It starts running immediately and records what types and shapes each function actually sees — the evidence the optimiser needs.

07TurboFan

The optimising compiler. Hot functions become machine code specialised to the observed types, protected by guards that check the assumption still holds.

08CPU

Optimised code runs close to native speed. First runs of any path are slow — the warm-up — which is why cold benchmarks lie.

09Runtime validation

A typed API response is a claim. A schema library such as Zod, io-ts or Valibot checks the data at runtime and infers the type, so the claim becomes true.

10any and unknown

any switches checking off and infects everything derived from it; unknown forces narrowing first. Treat every explicit any and every as as needing a justification.

11Structural typing

TypeScript compares shapes, not declared names: an object with at least the required fields is assignable. A good fit for how JavaScript objects are really built.

12Hidden classes

Internal shapes that make property access a fixed memory offset. Objects created with the same fields in the same order share one; adding and deleting fields later forces new ones.

13Deoptimisation

When a guard fails — strings arrive where integers always did — the optimised code is discarded and execution falls back to bytecode. Performance becomes unpredictable, not wrong.

14Garbage collection

A young generation scavenged often and cheaply, an old generation marked and swept incrementally. Pauses are short, not zero, and leaks come from references you keep — listeners, detached nodes.

15Bundle cost

Every kilobyte is downloaded, parsed, compiled and held in memory. Route splitting and fewer dependencies beat any micro-optimisation of what remains.

16Language traits

Dynamic typing, one thread, event-driven, prototype-based, first-class functions and closures. Each trait explains a whole family of bugs and patterns elsewhere in this atlas.

17Quirks

Float arithmetic, typeof null, string sorting, loose-equality coercion — design decisions that can never be removed without breaking the web. Use ===, always.

Types are not validation, and the JIT is attack surface

Declaring a request body as LoginRequest checks nothing; an attacker sends whatever they like. On the engine side, eval and new Function with user input are remote code execution, prototype pollution changes behaviour application-wide, and every npm dependency runs with your page's full privileges. The renderer sandbox is the real defence — audit and pin what you install.

Sheet 4

One Thread, Three Queues

Closed circuit Covers · Event Loop · JavaScript · Browser Internals

What runs the page after stop 12 of sheet 1 — and what runs every Node.js server. One thread, one loop, four steps, forever. Nothing on this circuit can be interrupted: a task that takes 100 ms owns the thread for 100 ms, and clicks, frames and network callbacks all wait in line behind it.

Step key — the loop and its vocabulary

01Take one macrotask

The loop picks the next queued task — a timer that expired, an I/O completion, a user event — and only one per turn.

02Run to completion

The task's code runs on the call stack until it returns. There is no pre-emption: while it runs, the page cannot scroll, click or paint.

03Drain all microtasks

Every queued promise callback and await continuation runs before anything else — including microtasks queued by microtasks. Higher priority than macrotasks, always.

04Render if due

In the browser, a frame is produced if it is time: style, layout, paint, composite. Because it shares the thread, any long step above pushes it past 16.7 ms.

05Call stack

The functions currently executing. Synchronous code runs here immediately, which is why logs 1 and 4 print first.

06Microtask queue

Promise.then, await, queueMicrotask. Emptied completely every turn, so log 3 beats the timeout even though the timeout was scheduled first.

07Macrotask queue

setTimeout, setInterval, I/O and events. One per turn — so setTimeout(fn, 0) means "a future turn", never "now".

081, 4, 3, 2

Synchronous first, then all microtasks, then the next macrotask. Predict the output before running it; most developers get it wrong once.

09Host APIs

Web APIs in the browser, libuv in Node, epoll or kqueue underneath. They do the actual waiting elsewhere and hand back a callback — a few KB per operation instead of megabytes per thread.

10Web Workers

Real threads for CPU work — image processing, big sorts, encryption, large JSON — that talk by message passing and cannot touch the DOM. In Node: worker_threads, extra processes or a job queue.

11Async is not parallel

async/await creates no threads. One Node process uses one core, so run several behind a cluster, and handle every promise rejection.

12Blocking

A long synchronous task stops the loop: no events, no frames, no callbacks. In Node it stalls every user's request at once, and hostile input — ReDoS, huge bodies — can trigger it deliberately.

Sheet 5

The Render Cycle

Control loop Covers · React · DOM and CSSOM

How a framework re-drives stops 07 to 10 of sheet 1 every time data changes. You stop writing instructions for how to change the page and describe what it should look like now. "Re-render" means React called your function again — not that the browser repainted. Most of the loop is cheap JavaScript; only stop 07 ever touches the DOM.

Step key — the loop and its vocabulary

01Event

A click reaches an onClick handler through the event loop. React's work is still single-threaded JavaScript on the same thread that renders.

02setState

The only way to change state: pass a new value or a new object. Mutating the existing object in place gives React nothing to detect.

03Scheduled render

React batches several updates into one render and chooses when to run it, so three setState calls in a handler produce one pass, not three.

04Component runs

Your function is called again with current props and state and returns JSX. Its children re-render by default whether or not their props changed.

05Virtual tree

The returned description as plain JavaScript objects. Building and discarding it is cheap compared with touching the real DOM.

06Reconciliation

Diffing the new tree against the previous one by element type and key to find the minimum set of changes.

07DOM patch

Only differing nodes are updated. This is the single step that can trigger layout and paint — the costs drawn on sheet 2.

08Browser renders

Style, layout, paint and composite, only for what changed and only if something did. The frame budget from sheet 1 still applies.

09Re-render ≠ repaint

Calling ten component functions may patch one node and repaint a few pixels. Optimise only what the React Profiler shows; blanket memo adds work.

10Hooks

useState for local state, useEffect for syncing with systems outside React, useContext, useMemo/useCallback, useRef. Built on closures, bound by call-order rules that are easy to break.

11Props, state, key

Props flow down and are read-only; state changes and triggers renders; JSX compiles to React.createElement; key gives list items a stable identity.

12Declarative UI

UI as a function of state. You declare what each state looks like, so the number of transitions you write stops growing with every new flag.

13Recurring bugs

Mutated state, array index as key in reorderable lists, wrong dependency arrays, a second library editing the same nodes, and leaked references to removed elements.

14When not to

A mostly static site pays ~45 KB, a build step and hydration for nothing. Consider Svelte, Solid, Vue, or HTML with HTMX before defaulting.

Escaped by default, until you opt out

{userInput} is escaped automatically, which stops most XSS. dangerouslySetInnerHTML — like innerHTML — removes that protection, so sanitise with DOMPurify. href={userInput} allows javascript: URLs. Everything in the bundle, including build-time environment variables, is public, and client-side route guards are UX, not authorisation.

Sheet 6

Where the HTML Is Made

Decision tree Covers · Next.js · Frontend Architecture · React

Stops 03 and 04 of sheet 1 assume HTML arrives. This sheet decides which machine produced it, and when: a build server last Tuesday, a server a millisecond ago, or the user's own phone. Rendering strategy is an architectural decision made per page — and server components add a second one: which code is allowed to reach the browser at all.

Step key — the decisions and what follows from them

01Per-user content?

The first split. A page identical for every visitor can be produced ahead of time; a cart or account page cannot.

02Changes often?

For shared content: rarely changing pages are built once; catalogues and news need periodic regeneration.

03SEO or first paint?

For per-user content: if crawlers or slow phones matter, render on the server; if the page sits behind a login, the browser can do it.

04SSG

Static generation at build time. Plain HTML from a CDN — fastest, cheapest, indexes perfectly. Docs, blogs, marketing.

05ISR

Incremental static regeneration: built once, then refreshed in the background on a schedule. Static speed with bounded staleness.

06SSR

Server-side rendering on every request. Fresh and personalised, visible immediately, at the price of CPU per request and a server to run.

07CSR

Client-side rendering: an empty shell, then JavaScript builds the page. Simplest to deploy, fine behind a login, slow on mobile and poor for SEO elsewhere.

08Hydration

Attaching event handlers to server-rendered HTML so it becomes interactive. Content is visible before hydration; buttons work only after it.

09Server components

The App Router default: components that run only on the server, can query data directly and ship no JavaScript. 'use client' opts a component into the browser.

10Request flow

Middleware, cache check, server component, direct database query, streamed HTML, visible content, hydration, server action — R1 to R9 in the band above.

11A real backend

Route handlers and server actions talk to the database directly, so a small product may need no separate API service. It is still a server to operate.

12The boundary

NEXT_PUBLIC_ variables are public, server actions are public HTTP endpoints, and a client import ships its module. Authenticate and validate inside every action and handler.

13Alternatives

Vite + React for login-only dashboards, Astro for content with little interactivity, Remix, Nuxt and SvelteKit for their ecosystems. Complexity and caching confusion are Next.js's real costs.

Sheet 7

Where State Lives

Ladder plate Covers · State Management · React · Frontend Architecture

The data behind every re-render on sheet 5, and the question of where each piece of it belongs. Four rungs for data the browser owns, a separate tower for data the server owns. Most frontend complexity is state kept too high, kept twice, or kept in the wrong tool — and the most common mistake of all is treating a cache as a store.

Step key — the rungs and their vocabulary

01Local state

useState inside the component that uses it. Free, obvious, easy to delete, and it re-renders only that subtree. The right answer far more often than it is chosen.

02Lifting state

When a sibling needs the same value, move it to the nearest common parent and pass it down. Climb further only when the props travel four or more levels.

03Context

Shared values without prop drilling — theme, locale, current user. Every consumer re-renders on every change, so it is the wrong home for anything that changes rapidly.

04Global store

Zustand for minimal ceremony, Redux Toolkit for large apps with complex flows and time-travel debugging, Jotai for atoms. Selectors limit re-renders to the slice that changed.

05Server-state cache

TanStack Query, SWR or RTK Query for anything from an API: caching, deduplication, loading and error states, refetching and invalidation, all by default.

06Server vs client state

Server state is owned elsewhere, can go stale and needs caching; client state is owned by the browser and cannot. Using one tool for both is the most common mistake in this area.

07URL state

Query parameters for filters, tabs, pagination and search. Survives refresh, is shareable, and works with the Back button — for free.

08Optimistic update

Update the UI before the server confirms, send the mutation, then invalidate the query on success or roll back and show an error on failure.

09Single source of truth

Header, sidebar and checkout read the same cached query instead of keeping copies. Duplicated data is the direct cause of an interface that contradicts itself.

10Client state is public

Anyone can inspect and edit it. Never store secrets there, prefer HttpOnly cookies to tokens in localStorage, re-check every permission on the server, and clear persisted data on logout.

Persisted state outlives the session

State written to localStorage or IndexedDB survives logout unless you clear it deliberately — the next person on a shared machine inherits the last user's cached orders and profile. Persist only what is safe to leak, and make "clear everything" part of the logout path, tested.

Sheet 8

The Town Plan

Zoning plan Covers · Frontend Architecture · HTML · CSS · Browser Internals

The plan of the code that feeds every other sheet. Anyone can build one house; planning decides whether the hundredth still has road access and whether demolishing one brings down its neighbours. Organise by feature, let dependencies point one way, build shared UI on semantic HTML — and remember that everything above the network line is public.

Step key — the zones and the rules between them

01Pages / routes

Composition and routing only: which features appear on this URL. Each route is its own code chunk, so users download only the page they visit.

02Features

A business capability — checkout, orders, products — with its components, hooks, state and queries in one folder. Changing it touches one place; deleting it is one operation.

03Shared UI

Design-system primitives such as Button, Modal and Input, documented in Storybook. The only way twenty teams avoid twenty subtly different buttons.

04Lib / API

One HTTP client, formatting and runtime validation. Every feature reaches the network through it, so auth headers, errors and schemas live in one place.

05Backend

Below the network boundary: the only zone the user cannot read or modify. Every rule enforced in the client must be enforced again here.

06Folder structure

By type scatters one feature across components, hooks, utils and services. By feature keeps it together. The utils folder is where type-based structures go to die.

07Dependency rules

Page → feature and feature → shared are allowed; shared → feature inverts the hierarchy, feature → feature signals a missing shared module. Enforce with ESLint import rules or dependency-cruiser.

08Component design

Presentational components render props; container components fetch and hold state. Over ~200 lines, hard to name, or more than ~7 props: split it.

09Semantic HTML

Choose elements by meaning, then style them. <button> brings focus, keyboard, screen-reader and form behaviour for free; landmarks make the page navigable and indexable.

10Accessibility and forms

Alt text, labels, ordered headings, more than colour, full keyboard access. Input types give validation and keyboards — but only server validation is a control.

11Performance budget

Code splitting, server components, image optimisation, few dependencies, budgets checked in CI with Lighthouse CI or bundlesize. Architecture sets performance; micro-optimisation rarely does.

12Everything is public

Bundle, baked-in variables, endpoints, client state and CSS-hidden data are all readable. There is no client-side secret, and a route guard is not authorisation.

Do not copy a large company's town plan

Structure pays from the second developer or the second month — retrofitting boundaries later costs far more. But a five-layer architecture on a three-page site pays the cost of abstraction at every change and never collects the benefit, and micro-frontends and monorepo tooling solve organisational problems you may not have. Plan for the town you are building.
