Sheet 1

The Request Line

Transit diagram Covers · Cloud Fundamentals · AWS Architecture

One request to a typical SaaS on AWS: CloudFront, an ALB, containers in two AZs, a Multi-AZ database, S3 and a queue. Six services, thirteen stops. The database is one stop of thirteen, the IAM role at stop 07 is the real security boundary, and the most important branch on the map is the one nobody chooses — the path traffic takes when a data centre loses power.

Step key — every stop on this sheet, and what it does

01You

A browser with a URL and a session. Nothing about the request says "cloud" — which is the point: the user sees one hostname, and behind it sit a dozen metered services.

02Route 53

AWS's global DNS. Answers with the address of the nearest CloudFront edge, and can fail over between endpoints on health checks. One of the global services, like IAM and CloudFront.

03CloudFront edge

One of hundreds of edge locations. TLS is terminated near the user and the cache is checked. A hit ends the journey at exit A; a miss is forwarded to the region.

04The ALB

An application load balancer with a node in each of two public subnets. Terminates TLS again, and routes only to targets passing their health checks, in whichever AZ has one.

05Security groups

The stateful firewall on every network interface. The ALB's allows 443 from anywhere — the one place that is correct. Everything after it allows traffic only from the previous hop's group.

06ECS task

A container in a private subnet with no public address. Interchangeable with its siblings in the other AZ; any one of them can be killed without consequence.

07IAM role

The task assumes a role and receives temporary credentials from the container credentials endpoint. No access key exists anywhere in the image. This is the perimeter, not the network.

08Secrets Manager

The database password, fetched at startup through an interface endpoint and cached — never baked into an environment variable committed to a repository.

09RDS primary

Reached through RDS Proxy over TLS. A write commits only after the synchronous standby in AZ-b acknowledges it, adding 1–2 ms. The price of surviving an AZ failure.

10S3 via endpoint

A media file is written to S3 through a gateway endpoint. S3 lives outside the VPC; the endpoint keeps the bytes on the AWS network and off the NAT gateway's per-GB meter.

11SQS

A message for work that does not need to happen inside this request. The worker picks it up asynchronously — the start of the event branch drawn on sheet 4.

12CloudWatch

A latency metric and a structured log line carrying the request id generated at the edge. Shipped immediately, because the task that wrote it may not exist in an hour.

13The response

Returns through the ALB and CloudFront. Nothing about the return path is free: every byte leaving AWS is metered at stop 14.

ACache hit

Served from the edge with no origin traffic and no regional egress. The cheapest request in the system, and the reason CloudFront is also the cheapest way to cut a bandwidth bill.

BSilent drop

Traffic no security group allows gets no reply — the client sees a timeout. When A cannot reach B, check the target's security group first and the source subnet's route table second.

F1AZ-a goes dark

One availability zone loses power. AZs have independent power and cooling and sit single-digit milliseconds apart, which is exactly what makes this recoverable.

F2ALB drains it

Health checks fail; the load balancer stops routing to AZ-a within seconds. Tasks in AZ-b absorb everything — so AZ-b must already have tasks.

F3Standby promoted

RDS detects the failure and promotes the synchronous standby. 60–120 seconds on standard RDS, typically under 30 on Aurora. A new standby is built in the background.

F4DNS repointed

The application keeps using the same endpoint name; RDS repoints the record. RDS Proxy holds client connections through the flip, so the outage users see is shorter.

14Egress meter

Inbound data is usually free; outbound always costs, per GB, at a rate high relative to storage. Media, exports and cross-cloud sync can outspend the servers.

15CloudTrail

Every API call — who, what, when, from where — recorded to a log archive account the production account cannot delete from. Evidence that survives the actor.

16The bill

Compute per second, storage per GB-month, requests per call, egress per GB — and idle: a stopped instance still bills for its disk. Read it by service, monthly, out loud.

17Backups

RDS takes automated snapshots plus continuous transaction logs; S3 versions every object. Neither is a backup until someone has restored from it with a timer running.

Multi-AZ and multi-region are different engineering problems

The failover branch works because AZs are 1–2 ms apart, so one synchronous system can span them — close to a configuration flag. Regions are tens to hundreds of milliseconds apart, which forces asynchronous replication, conflict resolution and split-brain handling into the application itself. A team that says "we'll go multi-region later" is describing a rewrite.

Sheet 2

The Responsibility Line

Ladder plate Covers · IaaS PaaS SaaS · Cloud Fundamentals

IaaS, PaaS and SaaS are not three products — they are three positions of one line drawn across the same nine layers. Everything below the line the provider operates; everything above it someone on your team understands, patches, and is woken for. This is a staffing decision disguised as a technical one, and the right answer is the highest level that does not block you.

Step key — the service models and their vocabulary

01IaaS

You get a machine, a network and a disk; everything above the OS is yours. EC2 and VPC. Full control, lowest unit cost, and every patch and kernel upgrade on your rota.

02CaaS

A container scheduler — ECS or EKS. You own images, manifests and the cluster's health; the runtime travels inside your image. Where most mature product teams settle.

03PaaS

"Give us your code." Heroku, App Runner, Vercel. The platform builds and runs it, and logs are already there — until the knob you need does not exist.

04FaaS

"Give us a function." Lambda scales it to zero and back. You accept timeouts, cold starts and a provider-specific event model as architectural constraints.

05SaaS

A finished product: Gmail, Stripe, Datadog. You configure it and your data lives inside it. Nobody should build a helpdesk unless the helpdesk is the product.

06The line

The boundary between what the provider operates and what you operate. The three names are just popular positions of it; modern services sit anywhere along it.

07Shared responsibility

The provider secures the cloud — data centres, hypervisor, service internals. You secure what is in it — identity, network rules, encryption choices, patching, code, data. Managed never means secured.

08Managed service

PaaS wearing different clothes: RDS instead of an instance plus PostgreSQL plus backups plus failover. Roughly double the raw price, and the highest-value trade in the topic.

09Total cost

Infrastructure invoice plus engineer time plus the 3 a.m. incident nobody set up the standby for. Comparing only the first term is how teams talk themselves into work they cannot afford.

10Lock-in

A price with a number attached — weeks of migration — not a sin. Low for a Linux box, high for an event model, highest when your data is inside someone's product.

11Data gravity

Large data is slow and expensive to move, because egress is billed per GB. The form of lock-in that genuinely bites, and the one no portability layer removes.

12Deployment models

Public cloud almost always; private for regulatory or physical constraints; hybrid for a data centre you cannot leave yet; multi-cloud far more rarely than it is discussed.

13Multi-cloud

Usually a cost with no matching benefit: the lowest common denominator of both providers, egress between them, and two operational models to staff. The portability layer is itself a lock-in.

14The five properties

On-demand self-service, broad network access, resource pooling, rapid elasticity, measured service. Together: capacity as a reversible API call rather than an 18-month purchase guess.

15Resource pooling

Your VM shares a physical host with other tenants. The "noisy neighbour" on disk and network is real, invisible from inside, and why two identical instances can perform differently.

16Elasticity

The real innovation is the feedback loop, not the price: a wrong capacity decision costs minutes to correct instead of a purchase order. Reversible beats correct.

Lift and shift, then stop

Moving servers into the cloud without moving the assumptions buys cloud prices for data-centre architecture: instances sized for a peak that never comes, patched by hand, with no elasticity used. And for large, flat, predictable load, owned hardware is genuinely cheaper — the cloud is not a fix for an architecture problem either. A slow monolith is a slow monolith on rented hardware too.

Sheet 3

The Network Floor Plan

Cutaway section Covers · VPC · AWS Architecture · Cloud Security

Stops 04 to 10 of sheet 1, with the roof taken off. Three tiers of subnet across two availability zones, and a route table beside each tier. There is no "public" flag on a subnet: it is public if and only if its route table points at an internet gateway — and the data tier has no default route at all.

Step key — the flows and the parts of the network

01Internet gateway

The VPC's front door. Inbound traffic reaches only what sits in a subnet whose route table points here — in this plan, the ALB nodes and nothing else.

02ALB → private tasks

The load balancer forwards into the private tier. The task's security group allows traffic from the ALB's security group only, so the rule survives instances coming and going.

03Task → database

RDS sits in the data tier. Its group allows 5432 from sg-app and nothing else — no CIDR ranges, no "office IP" exception. It never has a public address.

04Gateway endpoint

A route-table entry sending S3 and DynamoDB traffic over the AWS network. Free, faster than NAT, and it lets a subnet that only needs S3 have no internet route at all.

05NAT gateway

Lets private instances reach out — a payment API, a package mirror — while nothing can reach in. Billed per hour per gateway plus per GB processed, and needed once per AZ.

06Synchronous standby

The RDS standby in the other AZ's data subnet. Every commit waits for it, adding 1–2 ms; it serves no reads and exists only to be promoted.

07Public subnet

Default route to the internet gateway. Holds load balancers and NAT gateways — and a bastion only if SSM Session Manager genuinely cannot do the job.

08Private subnet

Default route to a NAT gateway: outbound yes, inbound impossible. Where application servers, containers, caches and workers belong.

09Data subnet

No default route whatsoever. The database cannot reach the internet even if compromised, which is a far stronger statement than "outbound is restricted".

10Route table

The whole mechanism behind public and private. An instance in a "public" subnet with no public IP is unreachable; a "private" subnet routed to an IGW is not private at all.

11Security group

A stateful, allow-only firewall on each network interface. Its best feature is referencing other groups, which expresses intent rather than addresses. This is your real firewall.

12Network ACL

A stateless, numbered, subnet-wide rule list. Useful for blunt denials; misconfigured, it drops return traffic silently and produces outages that are miserable to diagnose.

13Interface endpoint

A private ENI with a DNS name inside your subnet, for ECR, Secrets Manager, CloudWatch Logs and most other services. Hourly plus per GB, and still cheaper than the NAT traffic.

14CIDR block

The VPC's address range, permanent once chosen. Pick a deliberate /16 such as 10.42.0.0/16, leave gaps between subnets, and remember each /24 gives 251 usable addresses.

15Flow logs

The record of accepted and rejected connections — at least rejected ones, shipped somewhere durable. After an incident, the only evidence of what traffic actually happened.

16Default VPC

Created for you with public subnets only; every instance launched into it gets a public address. It exists to make the first tutorial work, and is why databases end up on the internet.

Egress is the attacker's exit

Follow a compromise through this plan: the attacker exploits the app and lands on a task. Security groups deny the scan of the VPC. The database is reachable, because the app is allowed to reach it. Then data leaves through the NAT gateway, which permits it. What limits the blast radius is not the inbound rules everyone writes — it is egress filtering and endpoint-only subnets that nobody does.

Sheet 4

Fleet and Function

Closed circuit Covers · EC2 · Lambda · IaaS PaaS SaaS

Stop 06 of sheet 1 and the event branch off stop 11, opened up. Two ways to run code: a fleet of rented machines that an Auto Scaling Group keeps replacing, and functions that exist only for the milliseconds an event needs them. EC2's contribution was not virtualisation — it was making a server disposable. Lambda's was billing for work done instead of time held.

Step key — the fleet circuit and the function

01Launch template

What an instance should be: AMI, instance type, IAM role, user data. Ideally the AMI is built by a pipeline (Packer), never by hand, and carries no credentials.

02ASG launches

The Auto Scaling Group decides how many, in which AZs, and what healthy means. Minimum two, across two AZs, even for a fleet that never scales.

03Boot and credentials

30–90 seconds to reachable, plus your bootstrap. The instance asks IMDSv2 for temporary, auto-rotating credentials — enforce v2, because v1 hands them to any SSRF.

04Health check passes

The ALB starts routing to it. Reads go to RDS, media to S3 through the endpoint. Nothing is written to the local disk that anyone would miss.

05Marked unhealthy

Three failed health checks: a hung process, a full disk. The ALB stops routing and the ASG marks it for replacement — at 4 a.m., with nobody paged.

06Terminated and replaced

A new instance from the same template. No state lost, because none was stored locally. The test of cloud infrastructure is whether this step is boring.

07Instance family

t burstable, m general (1:4), c compute, r memory (1:8), i local NVMe, g/p GPU. Each size step doubles CPU, memory and price; newer generations are usually cheaper per unit of work.

08Purchasing models

On-demand at full price; Savings Plans up to ~70% for a 1–3 year commitment; Spot up to ~90% with a two-minute reclaim notice; dedicated hosts cost more, for licences.

09Spot

For anything interruptible and retryable — CI runners, batch, encoding, stateless web tiers. Handle the termination notice and make work resumable once; the saving is permanent.

10EBS versus instance store

EBS is network storage that survives stops, with gp3 IOPS and throughput provisioned separately from size. Instance store is fast local NVMe whose data vanishes on stop.

11CPU credits

Burstable t instances earn credits idle and spend them under load. At zero they are capped at baseline — normal-looking CPU, terrible latency. Check before blaming code.

L1Init phase

Runs once per execution environment: code download, runtime start, module scope. Put SDK clients, secrets and connection pools here, cached for every warm invocation.

L2Handler

Runs once per event, one event per environment, at most 15 minutes. Must be idempotent — dedupe on the event id — because retries and at-least-once sources deliver twice.

L3RDS Proxy

Lambda runs outside your VPC by default and cannot reach a private database. Attached to subnets, it needs a proxy so hundreds of concurrent functions share a bounded pool.

L4Dead letter queue

Where an async event goes after its automatic retries fail. With an alarm on its depth, a malformed file becomes a ticket; without one, it disappears silently.

L5Cold start

No warm environment exists, so download, runtime and init all run first: ~100–300 ms for Node or Python, seconds for a large JVM. Shrink the package before buying provisioned concurrency.

L6Hard limits

15 minutes, 10 GB memory, 6 MB synchronous payload, 250 MB unzipped package, 1,000 default concurrency. The 15-minute ceiling is architectural — split the job or leave Lambda.

L7Invocation modes

Synchronous callers get errors and no retry. Asynchronous events retry twice, then the DLQ. Poll-based sources retry the whole batch, so one poison message can stall a partition.

L8Reserved concurrency

A cap on simultaneous environments for one function. Protects the database from a burst and your budget from an attack; the excess waits in the retry queue.

L9The crossover

Lambda's economics come from idleness. At constant, predictable traffic a container on Fargate or EC2 is cheaper, faster at p99 and easier to debug.

Scaling to zero is also forgetting everything

Instances in an ASG and functions in Lambda share one rule: nothing on the machine is yours to keep. A pet instance with state on its disk cannot be replaced; a function that trusts /tmp or an in-process cache is relying on an environment that may be gone on the next event — and that /tmp persists across warm invocations, so never leave sensitive data there either. State belongs in RDS, S3 or a cache: sheet 5.

Sheet 5

The Data Vaults

Exploded parts Covers · S3 · RDS

Stops 09 and 10 of sheet 1 taken apart. Sheet 4 made compute disposable; this is where everything that must survive lives instead. The bytes live in S3, the knowledge of them lives in the database — and neither S3 as a filesystem nor a read replica as failover will do the other's job.

Step key — the parts of both vaults

01Upload request

The browser asks your application for permission to upload, not for a place to send the bytes. The file itself never passes through your servers.

02Presigned URL

A short-lived, signed permission for exactly one operation on exactly one key — typically a 5-minute PUT — issued only after the app has checked who is asking.

03Direct multipart upload

Parts uploaded in parallel straight to S3, resumable. Necessary above ~100 MB. Your application stays small and stateless, which is the whole point.

04Bucket

Objects plus metadata under keys in a flat namespace. Eleven nines of durability, strong read-after-write consistency since 2020, 5,500 GET/s and 3,500 PUT/s per prefix.

05ObjectCreated event

S3 emits an event through EventBridge; Lambda records metadata and enqueues processing. Delivered at least once, so the handler dedupes — sheet 4.

06CloudFront + OAC

Origin access control lets the CDN read a private bucket. Cheaper egress than S3 direct, cached at the edge, and no bucket ever needs to be public.

07Lifecycle rule

Moves objects to colder classes on a schedule and expires old versions. Without one, storage only ever grows — including every version you ever overwrote.

08Metadata row

The database records where the object is, who owns it and what state it is in. A file stored only in S3, with no row, is a file you will lose track of.

09RDS Proxy

Pools and multiplexes connections, and holds client connections through a failover so the visible outage shortens. It earns its cost twice.

10Primary

A standard PostgreSQL or MySQL engine in a private data subnet, encryption enabled at creation, TLS forced, deletion protection on, never publicly accessible.

11Multi-AZ standby

A synchronous copy in another AZ that serves no queries and exists only to be promoted automatically. Availability, not capacity.

12Read replica

An asynchronous, readable copy for reporting and read scaling. Lags under write bursts, and nothing promotes it on failure. Capacity, not availability.

13Automated backups

Daily snapshots plus continuous transaction logs, so you can restore to any second in the window. A restore always creates a new instance; it never rolls back the existing one.

14Storage classes

Standard, Intelligent-Tiering, Standard-IA, the Glacier tiers, Deep Archive. Intelligent-Tiering when you cannot classify access; explicit lifecycle to Glacier for logs and backups.

15Versioning and Object Lock

Every PUT creates a version and DELETE writes a marker, so accidents and ransomware are undoable. Object Lock protects backups even from a compromised administrator.

16Connection limits

Each PostgreSQL connection is a backend process of 5–10 MB. The most common way a healthy database appears down — fixed by pooling, not by a bigger instance.

17Aurora

AWS's reimplemented storage layer: six copies across three AZs, failover under 30 s, up to 15 replicas. Better and pricier; easy to move into, hard to move out. Start on standard RDS.

Two checkboxes behind a great many breaches

A bucket without Block Public Access and a database created with Publicly accessible: yes. The first is fixed in one step at the account level, before anything else in a new account; the second belongs in a private subnet with a security group that admits only the application's group. Snapshots are as sensitive as the database — never public, and encrypted when copied across accounts.

Sheet 6

The Gate

Decision tree Covers · IAM · Cloud Security

The strip running under every other sheet. The control plane is an internet-facing API that can create, read and destroy your entire estate, so there is no perimeter to be inside of. Identity is the perimeter: every call is judged by one literal rulebook where the default is deny and an explicit deny always wins — and real breaches are misconfiguration, not sophistication.

Step key — the gate, the accounts and the controls

01Explicit deny

Checked first, at every layer. If any applicable policy says Deny, the call is denied — no number of Allows anywhere else can overrule it.

02Service control policy

An Organizations guardrail applied above IAM, so even an account administrator cannot bypass it. Deny disabling CloudTrail, deleting log buckets, unapproved regions, root usage.

03Permission boundary

A ceiling on what a role can ever be granted. Lets teams create their own roles without being able to escalate beyond the boundary.

04Explicit allow

Some identity policy or resource policy must say yes. Otherwise the answer is no — the default is deny, and nothing is permitted until something says so.

05Cross-account access

Within one account either policy allowing is enough; across accounts both the role's policy and the resource's policy must allow — and the KMS key policy, the same trap one layer deeper.

06Role

Permissions plus a trust policy saying who may assume it. Instances, functions, CI via OIDC and humans via SSO all assume roles and receive credentials that expire in 15 minutes to 12 hours.

07Policy statement

Effect, Action, Resource, Condition — and Principal in resource policies. Resource is where least privilege lives; Condition (MFA, tags, TLS, VPC endpoint) is where it gets precise.

08Privilege escalation

Innocent-looking permissions such as iam:PassRole on * or iam:CreatePolicyVersion let a principal acquire more than it was granted. Scope PassRole to named roles, always.

09Root account

The one identity no policy can constrain. Hardware MFA, no access keys, a monitored mail alias — and then never used. Most catastrophic incidents involve root or a long-lived key.

10CloudTrail

The record of every decision, allowed or denied. Enabled in every region and delivered to a write-only, Object-Locked bucket in a separate account an attacker cannot reach.

11Account separation

AWS's strongest isolation boundary: a dev role cannot drop a production table that lives in another account, because there is no path. Far easier before resources exist than after.

12KMS key policy

A second authorisation layer that fails independently of IAM: an over-permissive IAM policy alone cannot decrypt the data. Also produces an audit trail of every decrypt.

13Encryption

At rest everywhere — SSE-S3 and default EBS encryption are free — and TLS in transit, including inside the VPC, enforced with aws:SecureTransport conditions.

14Detection

GuardDuty for anomalous credential use, Config for drift from rules, Security Hub to collect findings. Cheap relative to their value — if the alarm reaches someone.

15Least privilege, practically

Start with nothing, grant what the code needs, read the access-denied entries, add exactly those, and let IAM Access Analyzer generate the policy from real usage.

A1–A8The attack path

Based on the shape of the 2019 Capital One breach: SSRF towards the metadata service. IMDSv2, a narrow task role, egress filtering, detection and an untouchable trail turn it into an incident rather than a breach.

Buying tools is not fixing configuration

A scanner that reports the same eight findings for two years has not improved anything, and passing an audit overlaps only partly with being secure. The cheap parts — Block Public Access, MFA on root, CloudTrail to a separate account, default encryption, no long-lived keys — take under an hour on day one and touch everything if retrofitted later.

Sheet 7

The Instrument Panel

Instrument panel Covers · Cloud Monitoring · Cloud Fundamentals · AWS Architecture

The instance was replaced twenty minutes ago, the function lived for 300 ms, and the database host is invisible. You cannot ssh in, so everything you will ever know about the system must be shipped off it while it runs. The hard part is not collecting data — it is deciding what deserves to wake someone, and reading the bill as an operational metric.

Step key — the operating vocabulary

01Collector

An OpenTelemetry SDK, the CloudWatch agent or a vendor agent, shipping telemetry immediately and asynchronously. Costs a few percent of CPU; losing the logs with the instance costs the incident.

02Metrics

Numbers over time — cheap, aggregated, one-minute granularity by default. Where alarms and auto scaling live. Batch custom metrics rather than one call per event.

03Logs

Discrete, structured events with context: JSON with level, event, user, tenant, duration and request id. Queryable instead of greppable, and expensive at volume.

04Traces

One request's path across services with timing per hop. Essential once there is more than one service; sample in production and always keep the errors.

05CloudTrail

Audit, not monitoring: every API call, delivered to a separate account with Object Lock. Non-negotiable, and the first place to look when something changed.

06Alarms

Thresholds and composite alarms on user-visible symptoms — error rate, p99, queue age. Causes such as CPU and memory belong on dashboards, because possibly nothing is wrong.

07The page

SNS to PagerDuty or Opsgenie to a human with a runbook. It exists only if the event affects users, is actionable now, and is worth waking for.

08Incident reading order

Symptom alarm → dashboard of golden signals → trace to the slow hop → resource metrics → the change on the timeline. Events such as deployments turn guesses into correlations.

09Four golden signals

Latency (the tail), traffic, errors split by cause, saturation. Cloud additions: queue age, connection count, Lambda throttles, CPU credits, 429s from provider quotas, and cost.

10Percentiles

An average of 100 ms can hide a p99 of 4 seconds. p95 and p99 are the only honest latency measurements; averages hide everything that matters.

11Egress

Data out to the internet is billed per GB and is frequently the second line on the bill. Cross-AZ transfer is billed in both directions. Keep bytes in one region; front large content with a CDN.

12NAT and log ingestion

The two line items that catch nearly every team: a NAT gateway billed per hour and per GB, and CloudWatch Logs billed on ingestion, where one service at debug level can outrun compute.

13Billing alarm

Set at around 150% of a normal month, before the first surprise. A cost anomaly alarm has prevented more damage in more accounts than most technical alerts.

14Service quotas

Cloud services do not degrade gracefully — they return throttling errors at hard limits. Learn quotas before the load test, and treat retry with backoff as part of your performance.

15Synthetic check

A canary exercising a real user flow from outside, every minute. Catches DNS, certificate and CDN failures that every internal metric reports as perfectly healthy.

16Alert fatigue

The actual failure mode of monitoring, and self-inflicted. A monitoring system nobody trusts is worse than none, because it manufactures confidence. Delete alarms that never led to action.

The closing loop

Sheet 7's bill is what makes sheet 2's line worth redrawing; its alarms are what tell you sheet 1's failover branch actually ran; CloudTrail on sheet 6 is the evidence when sheet 3's egress was the exit. The cloud turned hardware problems into API calls and capacity into a reversible decision — but only a team that can see its system can take advantage of either.
