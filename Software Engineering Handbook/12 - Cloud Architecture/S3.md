# S3

> **In one line —** effectively unlimited, extremely durable storage for whole objects, which is not a filesystem no matter how much the console makes it look like one.

## 1. Short Definition

*What is it?*

S3 stores **objects** — a blob of bytes plus metadata, identified by a key — inside a **bucket**. You write a whole object and read a whole object. There is no append, no partial write, and no directory.

---

## 2. Problem

*What engineering problem does it solve?*

```text
Files on a server's disk
    ↓
The disk fills up
Only that one server can read them
The server dies and the files die with it
Backups are your problem
Serving them consumes your application's bandwidth
    ↓
Files do not belong on application servers
```

S3 answers all of it at once: unlimited capacity, reachable from anywhere with permission, durable without effort, and served independently of your compute.

> [!IMPORTANT]
> **S3's durability guarantee — eleven nines — is the number that changed architecture.** It means AWS replicates every object across multiple facilities automatically, so "did we back up the uploads?" stopped being a question. Once storage is that reliable and that cheap, the correct default becomes: files go to object storage, and application servers keep nothing.

---

## 3. Architecture Position

```text
Browser ──presigned PUT──────────────┐
                                      ▼
Application ──API call (IAM role)──> S3 BUCKET
                                      │  objects + metadata + versions
                                      │
    ┌─────────────────────────────────┼─────────────────────┐
    ▼                                 ▼                     ▼
CloudFront (CDN)              EventBridge → Lambda    Lifecycle → Glacier
serves to users               processes uploads       cold storage
```

S3 is **regional and outside your VPC** — it is reached by API call, not by a network route. That is why a private instance needs a gateway endpoint (free) or a NAT Gateway (charged per GB) to reach it.

---

## 4. It is not a filesystem

```text
LOOKS LIKE                       ACTUALLY IS
folders in the console           a flat key namespace; "/" is just a character
files                            immutable objects
rename                           copy + delete, and you pay for both
append to a log                  impossible — rewrite the whole object
directory listing                a paginated API scan, slow on large prefixes
```

> [!CAUTION]
> **Mounting S3 as a filesystem is the most common way to misuse it.** Tools that do this turn every read into an HTTP request and every write into a full object rewrite, then hide the latency behind familiar file APIs. The result is a system that works in testing and collapses under load. If your workload needs POSIX semantics, you need EFS or a disk — not S3 with a translation layer.

---

## 5. Storage classes

| Class | Use for | Retrieval |
|---|---|---|
| **Standard** | Active data | Immediate |
| **Intelligent-Tiering** | Unknown or changing access patterns | Immediate |
| **Standard-IA** | Accessed monthly | Immediate, higher per-request cost |
| **Glacier Instant** | Archives you occasionally need now | Immediate |
| **Glacier Flexible** | Real archives | Minutes to hours |
| **Deep Archive** | Compliance retention | Up to 12 hours |

> [!TIP]
> **Intelligent-Tiering is the correct default for anything you cannot classify confidently.** It moves objects between tiers based on real access patterns for a small monitoring fee, and it removes an entire category of guesswork. Reach for explicit classes only when you already know the access pattern — logs and backups, for instance, belong in a lifecycle rule to Glacier from day one.

> [!CAUTION]
> **The cold classes have minimum storage durations and per-object charges.** Moving millions of tiny objects to Glacier can cost more in transition requests and per-object overhead than it saves in storage. Archive large objects; for small ones, aggregate first.

## 6. Consistency and versioning

```text
Since 2020: STRONG read-after-write consistency for all operations
    → a PUT followed by a GET returns the new object, always
    → the old "eventual consistency" advice is obsolete; ignore it

VERSIONING (off by default — turn it on)
    every PUT creates a new version
    DELETE writes a delete marker; nothing is actually removed
    → recovery from accidental deletion and from ransomware
```

> [!IMPORTANT]
> **Versioning plus a lifecycle rule is the cheapest disaster insurance in AWS.** Without versioning, an overwrite is permanent and a `--recursive` delete is unrecoverable. With it, both are undoable. Add a lifecycle rule to expire non-current versions after 30–90 days so the storage cost stays bounded, and combine it with Object Lock where you need protection that even an administrator cannot bypass.

## 7. Presigned URLs — the pattern to internalise

```text
BAD                                    GOOD
browser → your server → S3             browser asks your server for a URL
          (file passes                 server checks auth, returns a
           through your                presigned PUT URL (5 min expiry)
           app, twice)                 browser uploads DIRECTLY to S3
    ↓                                       ↓
your bandwidth, your memory,           your server never sees the bytes
your timeouts, your scaling problem    S3 handles the scaling
```

> [!TIP]
> **Never proxy large files through your application.** A presigned URL is a short-lived, signed permission for exactly one operation on exactly one key. Uploads go straight to S3; downloads go straight from S3 or CloudFront. Your application stays small and stateless, which is the whole point.

---

## 8. What S3 costs

```text
STORAGE        per GB-month — cheap, and cheaper in colder classes
REQUESTS       per 1,000 PUTs and GETs — matters at high volume
EGRESS         per GB out to the internet — usually the largest item
TRANSITIONS    per object moved between classes
EARLY DELETE   penalty inside a class's minimum duration
```

> [!CAUTION]
> **Put CloudFront in front of anything served repeatedly.** Egress from S3 to the internet is billed at the standard rate; egress from CloudFront is cheaper *and* cached, so most requests never touch the bucket at all. A public bucket serving images directly to users is a bandwidth bill waiting to arrive.

## 9. Real World Example

- **User uploads** — images, documents, video; the canonical use.
- **Static site hosting** — a bucket plus CloudFront, and nothing to patch.
- **Data lakes** — Parquet in S3, queried in place by Athena or Spark.
- **Backups** — database dumps with lifecycle rules to Glacier; see [Backup Strategy](../14%20-%20Scalability%20and%20Reliability/Backup%20Strategy.md).
- **Event-driven pipelines** — an upload triggers processing; see [Video Processing Platform](../15%20-%20Real%20World%20System%20Design/Video%20Processing%20Platform.md).
- **Build and container artefacts**, and Terraform remote state.

## 10. Communication and Dependencies

- **[IAM](IAM.md)** — bucket policies plus role policies; both must allow the call
- **A VPC gateway endpoint** if private instances access it, to avoid NAT charges
- **CloudFront** for anything user-facing at volume
- **EventBridge or S3 notifications** to trigger work on upload
- **KMS** if you need customer-managed encryption keys
- **A lifecycle policy** — otherwise storage only ever grows

---

## 11. When To Use / When NOT To Use

> [!TIP]
> Use S3 for anything written once and read many times, for anything large, and for anything you would otherwise be tempted to store on an application server's disk. It is the default home for files, backups, artefacts and analytics data.

> [!CAUTION]
> - **Not as a database** — no queries, no transactions, no indexes
> - **Not for data mutated frequently** — every change rewrites the whole object
> - **Not for low-latency small reads** — tens of milliseconds per object
> - **Not where you need POSIX semantics** — use EFS or a block device
> - **Not as a queue** — listing a prefix to find work is a well-known anti-pattern
> - **Not for session state** — use a cache

---

## 12. Advantages and Disadvantages

**Advantages**
- Effectively unlimited capacity with no provisioning
- Eleven nines of durability, across facilities, for free
- Very low storage cost, lower still in archive classes
- Strong read-after-write consistency
- Versioning, lifecycle rules, replication and Object Lock built in
- Serves traffic independently of your compute
- Massive parallel throughput

**Disadvantages**
- **Egress cost is the dominant expense** for anything user-facing
- Not a filesystem, and painful when treated as one
- Per-object latency makes many small objects inefficient
- Listing large prefixes is slow
- No partial updates
- Permissions have several overlapping layers, which is where mistakes live

## 13. Performance Impact

| Aspect | Impact |
|---|---|
| **First byte** | Roughly 20–100 ms per object |
| **Throughput** | Very high in aggregate; parallelise, do not serialise |
| **Request rate** | 5,500 GET/s and 3,500 PUT/s **per prefix**, and it scales with prefixes |
| **Multipart upload** | Necessary above ~100 MB; parallel parts, resumable |
| **Byte-range GETs** | Read part of a large object without fetching all of it |
| **Many small objects** | Per-request overhead dominates — aggregate them |

> [!TIP]
> **Throughput is per prefix, so key naming is a performance decision.** All objects under one prefix share a request-rate limit. Spreading keys across prefixes — by hash, tenant or date — multiplies available throughput. This matters for data lakes and high-ingest pipelines, not for a few thousand uploads a day.

## 14. Security Considerations

> [!CAUTION]
> **The public S3 bucket is the most repeated breach in cloud history, and it is entirely preventable in one step: enable Block Public Access at the account level.** Once set, no bucket policy or ACL can accidentally expose data, and any genuine exception must be made deliberately and visibly. Do this before anything else in a new account.

- **Block Public Access at the account level**, not just per bucket
- **Serve public content through CloudFront with OAC**, keeping the bucket private
- **Presigned URLs with short expiry** instead of permanent public objects
- **Default encryption on** — SSE-S3 is free; SSE-KMS when you need key control and audit
- **Versioning plus Object Lock** for backups that must survive a compromised administrator
- **Access logging or CloudTrail data events** for sensitive buckets
- **Bucket policies denying non-TLS requests** (`aws:SecureTransport`)
- **Beware cross-account writes** — an object written by another account can have an owner you did not expect; enforce bucket owner ownership

## 15. Mental Model

> [!NOTE]
> **S3 is a very large, very reliable coat check.**
>
> You hand over a whole coat and receive a ticket. You can retrieve the coat or replace it entirely — you cannot reach in and change one button. There are unlimited hooks, the coats are copied to several buildings so they are never lost, and storing them costs almost nothing. Taking a coat out of the building, however, has a fee. That last detail explains most S3 bills.

## 17. Complete Request Flow

```text
User selects a 400 MB video in the browser
    ↓
Application authorises the user, generates a presigned multipart upload
    ↓
Browser uploads parts in parallel, directly to S3 — the app sees none of it
    ↓
S3 assembles the object, creates version 1, encrypts at rest
    ↓
EventBridge emits an ObjectCreated event
    ↓
Lambda records a metadata row in RDS and enqueues a transcode job
    ↓
A worker reads the object with byte-range GETs, writes renditions back
    ↓
─────────────── serving ───────────────
User requests playback → CloudFront edge → cache hit, bucket untouched
    ↓
─────────────── over time ───────────────
Day 90   → lifecycle moves the original to Glacier Flexible
Day 400  → moved to Deep Archive
Someone deletes the object by mistake
    ↓
Versioning wrote a delete marker; the version is still there
    ↓
Remove the marker → the object is back
```

## 18. Key Takeaway

> [!IMPORTANT]
> S3 is where files belong — private by default with Block Public Access on, versioned, uploaded directly via presigned URLs, served through CloudFront, and lifecycled to cold storage — and it is object storage, not a filesystem.

---

## 19. Common Mistakes

- **A public bucket** when CloudFront with OAC would serve the same content privately
- **Proxying uploads and downloads through the application** instead of presigning
- **Mounting it as a filesystem** and being surprised by the latency
- **No versioning**, so an accidental overwrite or delete is permanent
- **No lifecycle rules**, so storage and old versions grow forever
- **Serving user traffic straight from S3** and paying full egress on every request
- **Millions of tiny objects**, where per-request cost dominates
- **Using it as a work queue** by listing a prefix
- **Storing only the file in S3** and losing track of it because no database row records it
- **Relying on obsolete eventual-consistency workarounds**

                          └→ CloudFront → users   └→ lifecycle → Glacier

## 2. Request Flow

```text
Input       a whole object plus a key, written with signed permission
    ↓
Processing  replicated across facilities, versioned, encrypted, lifecycled
    ↓
Output      the whole object on request — served best through a CDN
```

## 3. Real-World Usage

S3 quietly underpins a large share of the internet: media, static sites, data lakes, backups and build artefacts. The architectural rule that has survived everywhere is the same — **the bytes live in S3, the knowledge of them lives in your database**, and neither should try to do the other's job.

## 4. Final Summary

| Question | Answer |
|---|---|
| **What is it?** | Durable, effectively unlimited storage for whole objects |
| **Why does it exist?** | Because files on application servers do not survive, scale or move |
| **Where does it belong?** | Beside your compute, not inside your VPC; behind a CDN when public |
| **When should I use it?** | Anything written once and read many times — and never as a filesystem or database |
