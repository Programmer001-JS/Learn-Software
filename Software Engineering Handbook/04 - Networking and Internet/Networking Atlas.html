Software Engineering Handbook · 04 Networking and Internet · six sheets

Atlas of the Internet

One URL typed into a browser, and the dozen independent systems that cooperate to answer it. Sheet 1 is the route that request travels; every other sheet magnifies one stretch of it — the wires underneath, the name lookup, the handshakes, the contract at the far end, and the choice of how to talk at all. Every stop costs a round trip, and a round trip is roughly a million times slower than reading RAM — so the whole discipline is crossing the network as rarely as possible.

Sheet 1

The Page Load Line

Transit diagram Covers · Internet Fundamentals · DNS · TCP IP · TLS SSL · HTTP HTTPS

One URL, one route, fifteen stops. The server — the part you actually wrote — is one of them. Four stations before it are pure setup, each costing a round trip, and the two fastest ways to serve a request are exits that leave the line before the network is ever touched.

Step key — every stop on this sheet, and what it does

01You type a URL

A scheme, a hostname and a path. The hostname is for humans; nothing on the network can route by it until stop 03 turns it into a number.

02Browser cache

If an earlier response said Cache-Control: max-age=3600 and the hour is not up, the browser answers itself. The cheapest request is the one never sent.

AExit · fresh in the cache

Nothing to the right runs: no lookup, no handshake, no server load. Correct cache headers are the most underused feature of HTTP.

03DNS lookup

Browser cache, OS cache, recursive resolver, then root, TLD and authoritative servers. 20–120 ms uncached, near zero cached. Sheet 3 draws the whole descent.

CHazard · DNS fails

No address, no connection. Many of the largest outages — Facebook, Slack — were DNS or routing mistakes, with every server perfectly healthy behind them.

04An address

93.184.216.34 is a location, not an identity. Not in the local subnet, so the packet goes to the default gateway and is routed hop by hop. Sheet 2.

05TCP handshake

SYN, SYN-ACK, ACK: one full round trip before any data moves — about 150 ms across an ocean — to get a reliable, ordered byte stream on port 443.

06TLS handshake

ClientHello, ServerHello plus certificate, key exchange. One round trip on TLS 1.3, two on 1.2, zero on a resumed session. After this, everything is encrypted.

DHazard · certificate rejected

Expired, wrong hostname, broken chain or a skewed clock. The client refuses — correctly. Certificate expiry is one of the commonest self-inflicted outages there is.

07HTTP request

Method, path, headers, optional body. Stateless, so the Authorization header travels with every single request; the server remembers nothing between them.

08CDN / reverse proxy

An HTTP cache placed near the user. If Cache-Control allows it, the edge answers and the request never reaches your origin.

BExit · served from the edge

Physics cannot be optimised away — light in glass sets intercontinental latency. CDNs exist to bring the data closer instead of making the network faster.

09Load balancer

Usually terminates TLS and forwards plain HTTP to backends inside the private network. Standard, and a reminder that internal traffic is plaintext unless you encrypt it too.

10Application server

Rate limit, authenticate, validate, authorise, execute, respond. The one stop you wrote, and the one sheet 5 opens up.

11The response

Status code, headers, body. ETag lets the next request ask If-None-Match and receive 304 Not Modified — a round trip with almost no bytes.

12Reassembled

The response left as independently routed packets. Some arrived out of order, some not at all; TCP reorders, discards duplicates and re-requests the missing ones.

13Parse, discover

The HTML reveals every other resource the page needs. Each new host restarts the line at stop 03 — the hidden multiplier on page load time.

14Keep-alive

The connection stays open, so the next request to this host starts at stop 07. Disabling keep-alive, or opening a connection per call, pays setup cost forever.

15Render

Layout and paint. What the user experiences as "fast" is mostly how many round trips happened before this stop, not how long the server took.

The network is not reliable, and it is not free

Every arrow on this sheet can lose packets, drop connections or time out, and every arrow costs a round trip. Chatty service-to-service calls, hard-coded addresses and missing timeouts are the three ways teams forget that — and "it works locally" is usually the network, not the code.

Sheet 2

The Wire Underneath

Cutaway section Covers · Internet Fundamentals · ISP Router Switch Modem · IP Addresses

Stop 04 of sheet 1, cut open. Above, the four envelopes every packet wears; across the middle, the physical boxes that open them one at a time. A switch works inside one network by MAC address, a router works between networks by IP address — and that single distinction explains NAT, subnets, VPCs and most "it works on my machine" mysteries.

Step key — the boxes, the envelopes and the addresses

01Your laptop

Holds a private address such as 192.168.1.7, handed out by DHCP, and a MAC address burned into its network card. Neither is visible, or reachable, from the internet.

02Switch

Delivers frames inside one network by MAC address, learning which device sits on which port. Its obsolete ancestor, the hub, copied every frame to every port.

03Router and NAT

Connects different networks and forwards each packet one hop closer. At home it also translates every device's private address to one shared public one and remembers which connection is whose.

04Modem

Modulator–demodulator: converts Ethernet into light for fibre, radio frequencies for cable or tones for DSL. Knows nothing about IP.

05ISP

Owns a piece of the network and sells access to it. Interconnects with other ISPs at peering points — which is what makes the internet one reachable network rather than islands.

06The backbone

Tier 1 networks, exchanges and undersea cables carrying most intercontinental traffic. Latency here is set by the speed of light in glass, so bandwidth cannot shorten it.

07Their router

The final routing hop. It uses ARP to find which MAC address owns the destination IP on its local network, then hands the packet down.

08Their switch

The same job as 02, inside a data centre or a cloud subnet. A VPC subnet is a switching domain you rent rather than wire.

09The server

The IP gets the packet to the machine; the port — 443 here — gets it to the process. The kernel's TCP stack reassembles the stream and hands it over through a socket.

10Encapsulation

Each layer adds its own header around the one above: HTTP inside TCP inside IP inside Ethernet. Link headers are rewritten at every hop; IP headers survive end to end, NAT aside.

11Forwarding and ARP

A router compares the destination against its table and takes the most specific matching prefix. On the final network, ARP turns the IP into a MAC. No match means a drop.

12CIDR

Splits an address into network and host bits. /24 is 256 addresses, /16 is 65,536, /32 is one host. Firewall rules, security groups and VPC subnets are all written this way.

13Private ranges and IPv6

10/8, 172.16/12 and 192.168/16 are reusable and unroutable. IPv4's 4.3 billion addresses ran out; IPv6's 128 bits make NAT largely unnecessary, and it now carries about half of traffic.

14Where it bites

NAT blocks inbound webhooks, MTU problems make large requests hang, forged X-Forwarded-For defeats IP rate limits, and SSRF abuses private ranges and the metadata address.

Sheet 3

The Name Tree

Descent diagram Covers · DNS · IP Addresses · Internet Fundamentals

Stop 03 of sheet 1, drawn in full. A name goes down past three caches and, only if all of them miss, into a tree where no server knows the answer — each only knows who to ask next. Caching is what makes DNS fast and exactly what makes it slow to change: the TTL you set today decides how long tomorrow's mistake stays live.

Step key — the lookup, and the vocabulary around it

01Browser cache

The browser keeps its own recent answers. A hit ends the lookup instantly — and is one reason your machine can disagree with everyone else's after a change.

02OS resolver cache

The operating system's shared cache, with /etc/hosts as a local override. Useful for testing, unmanageable as a way to run anything real.

03Recursive resolver

Your ISP's, or a public one such as 1.1.1.1 or 8.8.8.8, configured by DHCP or resolv.conf. It walks the tree for you and caches everything it learns.

04Root servers

The fixed entry point. They know nothing about example.com — only which servers are responsible for .com.

05TLD servers

The .com servers refer the resolver to the name servers registered for example.com. That delegation is the NS record you set at your registrar.

06Authoritative server

Holds the real records for the domain — BIND, PowerDNS, Knot, or your cloud provider's DNS. Every other layer only holds copies of what this one said.

07The answer

A record value plus a TTL, or NXDOMAIN. It is cached at 03, 02 and 01 on the way back, and each copy lives for the TTL regardless of what you change afterwards.

08Connect

Only now can the TCP handshake start. One extra round trip per distinct host, which is why fewer third-party domains on a page is a real performance win.

09Record types

A and AAAA for addresses, CNAME for aliases, MX for mail, TXT for SPF, DKIM and verification, NS for delegation, SRV for service discovery.

10TTL

How long resolvers may cache a record. 300 means quick changes and more lookups; 86400 means efficiency and a day-long migration. Lower it a day or two before any planned move.

11No fast failover

Caches, and resolvers that ignore short TTLs, mean a change can take minutes to hours to reach everyone. Use DNS for planned moves and a load balancer with health checks for failover.

12Attacks

Spoofing and cache poisoning (DNSSEC, DoH, DoT), subdomain takeover through dangling CNAMEs, data exfiltration through queries, and hijacked registrar accounts.

13DNS as a tool

Geographic answers route users to the nearest CDN edge, record changes drive blue-green switches, and CoreDNS lets Kubernetes services find each other by name instead of by IP.

Sheet 4

The Handshake Ladder

Ladder plate Covers · TCP IP · TLS SSL · Internet Fundamentals

Stops 05 and 06 of sheet 1, drawn to scale in time. Each rung is a packet crossing an ocean; each pair of rungs is a round trip nobody sees. A new HTTPS connection costs three round trips — about 450 ms — before the first byte of content, and all of it is saved by the one habit of reusing connections.

Step key — every rung, and the machinery beside it

01SYN

The client asks to connect and picks a random initial sequence number — random so that connections cannot be hijacked by guessing it.

02SYN-ACK

The server agrees, picks its own sequence number and allocates connection state. A SYN flood abuses exactly this allocation; SYN cookies avoid it.

03ACK + ClientHello

TCP is open after one round trip. The client immediately sends its TLS hello: supported versions and cipher suites.

04ServerHello + certificate

The server picks a cipher, sends its certificate as proof of identity, and completes its half of the key exchange. TLS 1.3 fits this into one round trip; TLS 1.2 needed two.

05Verify the certificate

Signature chain to a trusted root, hostname match, expiry, revocation. The whole authenticity guarantee lives in this step, which is why skipping it is never a fix.

06Finished + request

Both sides derive the same symmetric key. From here every byte is encrypted and tamper-evident, and the HTTP request goes out on the same flight.

07First byte

About 450 ms after the first SYN across an ocean, most of it waiting on light. The server's work is added on top of this, never instead of it.

08Reliability

Sequence numbers, acknowledgements, retransmission on timeout, reordering and de-duplication — plus flow control for the receiver and congestion control for the network.

09Ports

An IP address picks the machine, a port picks the program. 0–1023 well-known, 1024–49151 registered, 49152–65535 ephemeral for outgoing connections.

10TCP or UDP

TCP when every byte must arrive in order; UDP when timeliness beats completeness. HTTP/3 rebuilt reliability per stream on UDP to escape head-of-line blocking.

11Chain of trust

A root CA in the trust store signs an intermediate, which signs the site certificate binding a name to a public key. Certificate Transparency logs catch certificates that should not exist.

12Asymmetric then symmetric

RSA or ECDSA once, slowly, to agree a secret without sharing one in advance; AES or ChaCha20 for all the data, fast and hardware-accelerated. Together: confidentiality, integrity, authenticity.

13Failure modes

Disabled verification, silently expired certificates, SYN floods, missing timeouts, unpooled connections and plaintext behind the load balancer — the last answered with mTLS.

14Reuse

Keep-alive, connection pools and TLS session resumption all buy the same thing: skipping this ladder. Opening a connection per database query or API call is among the most expensive mistakes in backend code.

Sheet 5

The Request Counter

Process plant Covers · HTTP HTTPS · API Design

Stop 10 of sheet 1, the one stop you own. A request enters the counter and passes six checks, cheapest first, each with its own rejection chute and its own status code. The code behind the counter can be rewritten at will; the counter itself — its paths, codes, errors and versions — is a promise to strangers you can never take back.

Step key — the stations, the chutes and the contract

01The request

Method, path, headers and body, already decrypted by TLS. Identity, content type and an idempotency key all arrive as headers — nothing is remembered from last time.

02Rate limit

The cheapest check and the first line of defence. Rejected with 429 Too Many Requests and a Retry-After header well-behaved clients respect.

03Authenticate

Is the token valid, and who does it belong to? Failure is 401: "I do not know who you are". Confusing it with 403 makes client error handling impossible.

04Validate

Schema, types and ranges, at the boundary, for every client including your own. Failure is 422 with per-field errors. Bind only known fields — mass assignment lets a caller set is_admin.

05Idempotency

If this Idempotency-Key was seen, return the stored result instead of acting again. The difference between a retried payment and a double charge.

06Authorise the object

Not "is the user logged in" but "does order 12345 belong to them". Failure is 403, or 404 where existence itself is sensitive. Skipping it is OWASP's number one API flaw.

07Business logic

Services, rules, database — the part free to change. A failure here is 500, and the body must never carry a stack trace, SQL or file path.

08Respond

201 Created with a Location header and a body in the same shape as every other endpoint: one naming style, one ISO 8601 date format, everywhere.

09Anatomy and statelessness

Start line, headers, body, both ways. Because the server keeps no memory, any instance can serve any request — and sessions or JWTs are how state gets added back.

10Methods

GET is safe and idempotent, PUT and DELETE are idempotent, POST and PATCH are neither. Using POST for everything throws away both caching and safe retries.

11Status codes

2xx success, 3xx redirect, 4xx the client's fault, 5xx yours. Returning 200 with an error inside hides failures from clients, proxies and monitoring alike.

12Caching

max-age lets clients and CDNs skip the request entirely; ETag with If-None-Match turns a re-fetch into a near-empty 304. The highest-leverage web performance change available.

13Versions and HTTPS

HTTP/2 multiplexes streams on one connection; HTTP/3 runs over QUIC. Plain HTTP can be read and rewritten in transit, so redirect, set HSTS, and lock down CORS and cookies.

14The contract

Resources not actions, structured errors with a request id, cursor pagination from day one, /v1 versioning, additive changes only — and never the database schema as the API.

Authenticated is not authorised

Broken Object Level Authorization — GET /orders/12345 returning someone else's order because the endpoint only checked that a user was logged in — is the most common serious API bug there is. Station 06 has to run for every object, on every request, including the ones your own frontend never makes.

Sheet 6

Choosing the Wire

Decision tree Covers · API Design · gRPC · WebSockets · HTTP HTTPS

Before sheet 1 ever runs, someone decided what kind of conversation it would be. Six questions pick the protocol; the leaves say what each one costs you afterwards. The two questions that matter most are who is calling and whether the server must speak first — get those wrong and no amount of tuning recovers the difference.

Step key — the questions, the leaves and the machinery

Q1Who is calling?

Third-party developers and browsers expect REST and JSON and cannot easily use anything else. Your own services can agree on anything, including a binary contract.

Q2Must the server speak first?

HTTP cannot push: the client always asks. If updates must arrive without being requested, request/response alone will not do.

Q3Many client shapes?

Many different clients reading varied shapes of the same data is GraphQL's case. A single frontend on a well-designed REST API does not have that problem.

Q4Does the client push too?

Chat, collaborative editing, trading and multiplayer need both directions at low latency. Notifications, feeds and progress bars only need one.

Q5How often?

A connection held open for hours to deliver two messages is waste; poll. A steady server-to-client stream belongs on Server-Sent Events.

Q6Volume and streaming?

High call volume, polyglot services, or streaming justify gRPC's code generation and tooling. Two services at low volume do not.

AREST + JSON

The default for public and browser-facing APIs: universal, cacheable, debuggable with curl, described with OpenAPI. Its main risk is endpoint sprawl.

BGraphQL

An enforced schema where clients ask for exactly the fields they need. The price is hard caching and nested queries that can be arbitrarily expensive.

CPolling

Ask "anything new?" on a timer. Simple and wasteful — most answers are "no", each paying a round trip. Long polling holds the request open, which is better and still clumsy.

DServer-Sent Events

Server-to-client only, over plain HTTP, with automatic reconnection and no special proxy configuration. Simpler than WebSockets whenever the client does not need to push.

EWebSocket

A TCP connection that never closes, started as HTTP and upgraded. Tiny frames and true two-way messaging, in exchange for stateful servers and reconnection logic you write yourself.

FgRPC

Contract-first RPC with protobuf over HTTP/2: 5–10× faster to serialise, 3–10× smaller, four streaming modes, deadlines built in. Not human-readable, and browsers need gRPC-Web and a proxy.

GREST inside

For a small internal system the simplest answer still wins. Adopt gRPC when JSON overhead is measurable, not before.

01The upgrade

An HTTP request with Upgrade: websocket answered by 101 Switching Protocols. Validate Origin, use wss://, authenticate here and authorise per message.

02Scaling with pub/sub

A user on server 1 cannot be reached by server 2. Redis Pub/Sub or NATS fans messages out across instances; the load balancer must support upgrades and sticky routing.

03gRPC catches

Deadlines on every call, L7 load balancing because HTTP/2 reuses one connection, never renumbered protobuf fields, reflection off in production, mTLS inside the network.

The protocol is part of the contract

Moving a public API from REST to gRPC, or a polling client to WebSockets, is a breaking change for every consumer, and a stateful protocol changes how every server is deployed. Decide at the tree, deliberately — the choice outlives the code written on top of it.
