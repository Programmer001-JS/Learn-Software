Sheet 1

The Memory Ladder

Ladder plate Covers · How Computers Work · Registers · Cache Memory · RAM · SSD and HDD

The CPU does one tiny thing extremely fast; what it spends its life doing is waiting for data to arrive. Eight rungs, from a few bytes inside the chip to a warehouse in another city, span nine orders of magnitude. Performance is almost entirely about how far the data has to travel — every serious optimisation is an attempt to move work up this ladder.

Step key — every rung, and what lives on it

01Registers

A few dozen 64-bit slots of flip-flops wired straight into the execution units. The only place the CPU actually computes; everything below exists to feed them.

02L1 cache

32–64 KB per core, ~1 ns. Holds what the core touched a moment ago. The only memory registers exchange data with directly.

03L2 cache

256 KB to 2 MB per core, ~4 ns. The second place the CPU checks before giving up and walking to RAM.

04L3 cache

8–64 MB shared by all cores, ~40 ns. Helps multi-core work on common data, and forces cores to keep their caches coherent.

05RAM

Gigabytes of working memory at ~100 ns, the same speed for box 3 and box 3 billion — that uniformity is what "random access" means. Volatile.

06SSD

Flash cells at ~100 µs, permanent, no moving parts. Made random access affordable and changed how databases are built.

07HDD

Spinning platters at ~10 ms. Respectable for sequential reads, catastrophic for random ones, and ~10× cheaper per terabyte — backups, archives, video libraries.

08Network

Unlimited and 0.5–150 ms away. Object storage, other services, other continents. "Just one more network call" is never free.

09Locality

Temporal: used now, used again soon. Spatial: the neighbours are next. Both usually true, and the reason a cache the size of a few MB can hide a gap of 100×.

10False sharing

Two threads writing different variables that happen to sit on the same 64-byte cache line keep invalidating each other's cache. Correct code, mysteriously slow.

11Volatility and the page cache

DRAM forgets without constant refresh. The kernel lends idle RAM to cache file blocks, so high "used" memory is often healthy rather than a leak.

12Swap and the OOM kill

Out of RAM, pages go to disk at ~1,000× the cost, or a process is killed. In a container you get the kill: exit code 137, not a slowdown.

13Seek and rotation

An HDD read waits 5–10 ms for the arm and ~4 ms for the platter. An SSD's controller maps a logical block to a flash page electronically in ~100 µs.

14Wear levelling

Flash cells survive a limited number of rewrites and cannot be overwritten in place, so the controller spreads and erases. Also why "deleted" data lingers in cells nobody references.

The ladder has no free rungs

Going up costs money and capacity; going down costs time and, above the disk line, durability. RAM is not storage — anything not on a disk is gone after a restart — and a single disk is not a backup. RAID survives a dead drive, never a mistaken DELETE.

Sheet 2

The Instruction Cycle

Closed circuit Covers · CPU · Binary and Machine Code · Registers · How Computers Work

On the left, one line of code travelling down the toolchain until it is nothing but numbers in RAM. In the middle, the loop the CPU runs on those numbers, about three billion times a second. The CPU is not clever — it is a very simple machine repeated at an unimaginable rate, and it cannot tell an instruction from data unless someone else marks the difference.

Step key — the toolchain and the cycle

01Source

What a human writes. Python, JavaScript and Java all start here; whether they reach machine code by compiler, VM or JIT is a later decision.

02Parser

Turns text into an abstract syntax tree — the structure of the program, with the spelling thrown away.

03Compiler

Turns the tree into instructions for one CPU family. Register allocation — deciding which values earn a register — is among its biggest optimisations.

04Assembler

Maps each mnemonic to its bytes: "MOV eax, 5" is B8 05 00 00 00, "RET" is C3. An opcode says what to do; operands say to what.

05Linker

Combines object files and libraries into one executable in the platform's format: ELF on Linux, PE on Windows, Mach-O on macOS.

06Loader

The operating system maps the executable into memory and marks which pages may execute. That marking is a security control, not bookkeeping.

07CPU

The only component that decides anything. RAM and disks store, networks transport; the CPU reads instructions from memory, which is what makes a machine reprogrammable rather than rebuilt.

08Fetch

Read the instruction at the program counter — from L1 if lucky, from RAM if not, stalling ~300 cycles on a full miss.

09Decode

The control unit works out the opcode and operands and sets up the path the data will take through the core.

10Execute

The ALU performs one operation — add, compare, move, jump — and updates flags that the next instruction may test.

11Write back

The result lands in a register or memory, and the program counter advances. Then the clock ticks and the circuit runs again.

12Speculation

Pipelining, superscalar execution and branch prediction keep the core busy instead of waiting. Spectre and Meltdown turned that guessing into a way to read memory across boundaries.

13Registers and ALU

All real work happens between registers: load, load, add, store. Memory is only a place values are loaded from and stored back to.

14Interpretation

01000001 is 65, or 'A', or part of an instruction, depending entirely on what reads it. Type is convention, never a property of the bytes.

15Instruction set architecture

x86-64, ARM64, RISC-V: each defines its own registers and encodings. Machine code does not cross between them without recompiling or translating.

16DEP, ASLR, canaries

Three defences against one property — the CPU cannot tell data from code. Non-executable data pages, randomised addresses, and a tripwire value that detects an overwritten stack.

Sheet 3

Few Minds, Many Hands

Cutaway section Covers · GPU · CPU · RAM

Two processors opened side by side. The CPU spends its silicon on cleverness — prediction, reordering, big caches — so a handful of cores can handle anything. The GPU spends it on count. A GPU is fast only when the same operation is applied to thousands of independent items at once; for everything else, including the copy to reach it, the CPU wins.

Step key — the two processors and the bus between them

01CPU core

A powerful, general core with branch prediction, out-of-order execution and its own cache. Typically 4–64 of them. Unbeatable at sequential, branching logic.

02Shared L3

Megabytes of cache every core can use. Large caches are why a CPU copes with irregular memory access that would cripple a GPU.

03The copy

Data must travel from system RAM to VRAM over PCIe, and results must travel back. Ignoring this is the most common reason GPU code is slower than expected.

04GPU cores

Thousands of simple cores with weak prediction and tiny caches. Each is far dumber than a CPU core; together they do one thing twenty thousand times at once.

05VRAM

The GPU's own memory: separate from system RAM, much faster to feed the cores, and scarce. It is usually what limits the model, not compute speed.

06Kernel and SIMT

A small function executed by every GPU thread on its own element. Single Instruction, Multiple Threads — the shape of pixels, and of matrix multiplication.

07Branch divergence

Threads in one group run in lockstep. If they disagree about an if, the hardware runs both paths and throws half away. Branching costs a GPU what it never costs a CPU.

08Parallel-shaped work

Training and inference, video encoding, image processing, simulation. Many independent multiply-adds with no conversation between them.

09Wrong-shaped work

Branch-heavy code, small datasets, and I/O-bound services — which describes almost every ordinary web application. A GPU adds cost and latency there.

10Other accelerators

TPUs for tensor operations, NPUs in phones and laptops, FPGAs and ASICs for one fixed job. Faster and less flexible the further right you go.

11Tokenise on the CPU

The API server receives the request and turns text into a tensor. Ordinary CPU work — and if it is slow, the GPU sits idle.

12Copy to VRAM

The tensor crosses PCIe into GPU memory. No useful computation happens during the trip.

13Run the model

Thousands of cores perform the matrix multiplications of every layer. The only step on the line that actually needs a GPU.

14Copy back

The output tensor returns to system RAM, because the CPU cannot read VRAM directly on most machines.

15Decode and respond

The CPU converts the output back into text and writes the HTTP response. The GPU never touched the network.

16Batching

Grouping requests so the cores stay busy: 32 inputs together cost barely more than one. The main reason AI serving systems obsess over batch formation.

An idle GPU is an expensive space heater

Rented GPUs cost 10–40× a comparable CPU instance, and a forgotten one is the single most common cloud cost disaster. VRAM is not reliably cleared between tenants on every platform either — on shared GPU hosting, assume the previous workload's data may still be there.

Sheet 4

The Two Worlds

Transit diagram Covers · Operating Systems · Kernel · User Space · System Calls

One HTTP request, drawn as a line through three floors. Your code runs in user space with no access to hardware; the kernel runs with all of it; the CPU enforces the difference. Every real thing your program does — a byte read, a packet sent — is a system call, and every system call is a trip through a guarded gate that costs time and a copy.

Step key — the journey and the gate

01Network card

Hardware receives the packet. No user-space program can talk to it; only the kernel's driver can.

02Interrupt

The device signals the CPU, which switches to kernel mode and runs the handler. One of three ways into the kernel, with system calls and exceptions.

03Network stack

TCP/IP lives entirely in the kernel: reassembly, routing, sockets. High-throughput systems sometimes bypass it with DPDK or io_uring.

04Socket buffer

Bytes wait here until the process asks. The thread that was blocked in accept() or read() becomes runnable.

05Crossing up

read() returns: data is copied from kernel memory into your buffer and the CPU drops back to ring 3. Copying is pure overhead in I/O-heavy systems.

06User space

Routing, validation, business logic. Ordinary computation needs no kernel and runs at full speed. Almost everything you write — even PostgreSQL, Docker and Kubernetes — lives here.

07Crossing down

send() on the database socket. The program cannot choose where in the kernel it lands; the kernel does. That is what makes the gate safe.

08Blocked

The packet leaves and the thread waits. A blocked thread consumes no CPU — which is why "slow" and "CPU-busy" are different problems.

09Reply arrives

Another interrupt, another pass through the network stack, and the thread is made READY again, roughly 5 ms later.

10Crossing up again

The reply is copied into user space. Two crossings already, and the response has not been written yet.

11Build the response

Serialisation and templating: CPU work, still without the kernel. The only place where a faster language would help.

12Crossing down again

write() hands the response to the kernel. Unbuffered, one write per chunk would multiply this crossing.

13Transmit

The kernel's driver sends the packet. Every hardware effect of the request was performed by the kernel on your code's behalf.

14System call

Number and arguments in registers, a privilege switch, validation, the work, a copy back, and a return value or error code such as EACCES, ENOENT or EAGAIN. Roughly 100 ns – 1 µs each.

15Batched interfaces

epoll and io_uring service many operations per crossing; the vDSO answers clock_gettime without entering the kernel; DPDK and SPDK skip it for extreme throughput.

16Kernel as target

A kernel bug defeats user permissions, process separation and container isolation at once. seccomp narrows the gate; patching keeps it shut; eBPF offers verified in-kernel code without writing a module.

Most production mysteries live below your code

A container dies with exit code 137: the kernel's OOM killer. Only 1024 connections open: the file descriptor limit. Works locally, fails in Docker: a different kernel, different limits, a different file system. Check what the operating system says before debugging the application.

Sheet 5

The Address Plant

Process plant Covers · Memory Management · RAM · User Space

No process ever sees physical memory. Each is handed a private, clean, imaginary address space, and the kernel and the MMU quietly map it onto shared, fragmented RAM — in hardware, on every single access. Allocation is a promise, not a purchase: memory is only paid for when it is touched, and when the machine cannot pay, something is swapped or something is killed.

Step key — the plant and its vocabulary

01Virtual address space

Each process's private map, starting at zero and apparently contiguous. Identical addresses in two processes point at entirely different physical pages.

02Page table

The kernel's per-process mapping from virtual pages to physical frames. Consumes memory itself, and is swapped along with everything else on a process switch.

03MMU

The memory management unit in the CPU performs translation on every access, in hardware. Without it, isolation could not be enforced at useful speed.

04TLB

A small cache of recent translations. A hit makes translation nearly free; flushing it on a process switch is part of why those switches cost more.

05Frame

A 4 KB slice of physical RAM. Frames are shared, reused and fragmented; free ones are lent to the page cache until a process wants them.

06Swap

Disk space holding pages evicted from RAM. An emergency exit, not extra memory: a swapping application is effectively down while still appearing alive.

07Reservation

malloc or mmap reserves an address range and returns immediately. No physical RAM is used yet.

08First touch

The program writes to a page that has no frame behind it. This, not the allocation, is when memory is actually consumed.

09Page fault

The MMU cannot translate and traps to the kernel, which allocates a frame, loads the page from disk, or kills the process for an invalid access — a segmentation fault.

10Mapping

The kernel installs one 4 KB frame in the page table and retries the instruction. The program never sees any of it.

11Lazy allocation

Repeated page by page, only for pages actually touched. A 1 GB allocation that writes 10 MB costs 10 MB.

12Out of RAM

When touched memory exceeds physical RAM, the kernel swaps pages out or the OOM killer terminates a process. Exit code 137 is that decision, not an application crash.

13Copy-on-write

fork() gives the child the parent's pages read-only and copies a page only when either side writes. How Redis snapshots and pre-forked workers start in microseconds.

14Overcommit

Promising more memory than exists, betting it will not all be touched. Allocation succeeding does not mean usage will — set container limits knowing how they fail.

15Memory safety

Manual management invites overflows and use-after-free; garbage collection trades them for pauses; Rust checks ownership at compile time. ASLR and DEP/NX limit what a bug can become.

High memory usage is not the problem you think

The kernel deliberately fills idle RAM with page cache, so a busy server at 95% "used" is usually healthy. The real warnings are memory that climbs for an hour and never stabilises — a leak — and any sign of swapping. Stream large files and paginate large results rather than loading them whole.

Sheet 6

The Read Path

Sorting line Covers · File Systems · SSD and HDD · System Calls · Kernel

A program asks for "/var/app/config.json"; the disk only understands "block 88,213". Between them sits a sorting line that resolves names, checks rights, and above all tries not to touch the disk. The decisive station is the page cache: a hit costs about a hundred nanoseconds, a miss costs a thousand times more on an SSD and a hundred thousand times more on an HDD.

Step key — from a path to a platter

01open()

The first system call. Applications never talk to a disk; they name a path and ask the kernel.

02Path resolution

The virtual file system walks / → var → app → config.json one component at a time, routing to whichever file system owns each part.

03Permission check

The inode's owner, group and rwx bits are compared with the calling process's user and group. Failure returns EACCES.

04Inode lookup

Metadata for the file, usually already cached in RAM. Missing path components produce ENOENT here.

05File descriptor

A small integer naming the open file for this process. A real kernel resource with a real limit — leak them and new connections fail.

06read()

The second system call: descriptor 3, a buffer, 4096 bytes. Byte-at-a-time reads multiply this crossing and are a classic cause of slow I/O.

07Page cache check

Is the block already in RAM? The kernel keeps recently read file blocks in otherwise idle memory, so repeated reads usually never reach the disk.

08Cache hit

A memory copy into your buffer, around 100 ns. The fast path, and the common one.

09File system mapping

ext4, XFS or overlayfs translates the file offset into block numbers using the inode's block pointers.

10Block layer and driver

Requests are queued, merged and handed to the device driver in blocks, typically 4 KB, never individual bytes.

11Physical read

An SSD controller maps the block to a flash page in ~100 µs; an HDD moves an arm and waits for the platter, ~10 ms.

12Cache fill

The block is kept in the page cache, which is why the second read of a file is fast and why "used" RAM is often healthy.

13Delivered

read() returns the byte count. From the program's view, one line of code; from the kernel's, a dozen stations.

14Directory entry

A directory is a file whose contents map names to inode numbers. Two entries pointing at one inode is a hard link.

15Inode

Everything about a file except its name: owner, permissions, size, times, block pointers. You can run out of inodes while disk space remains — a baffling "disk full".

16Journal

Before changing structure, the file system writes down what it is about to do, and replays that after a crash. Protects the file system's integrity, not your unsynced data.

17fsync

write() means "in the page cache". fsync means "on the disk". Databases call it explicitly because they cannot let the kernel reorder or delay their writes.

18Path traversal

User input containing ../ reaching a file operation. Never build a path from unvalidated input; resolve it and confirm it stays inside the intended directory.

Sheet 7

Processes, Threads, and the Choice

Decision tree Covers · Processes and Threads · Process · Thread · Multithreading

A process is a company with its own locked office; threads are its employees sharing one filing cabinet. Processes buy isolation with overhead; threads buy speed with shared memory and the bugs that come with it — and the right choice is decided by whether the work is waiting or computing, long before anyone writes a lock.

Step key — units of execution, and how to choose

01Process

A running program with its own virtual memory, PID, file descriptors and permissions. The operating system's unit of isolation, created by fork() then execve().

02Shared state

Heap, globals and descriptors belong to the process, so every thread can reach them. Instant communication, and the source of every race.

03Thread

One line of execution inside a process with only a stack and a register set of its own. The kernel's schedulable unit.

04The cost gap

A process takes milliseconds and tens of megabytes to create; a thread, microseconds and a stack. Neither should be created per request — use a fixed pool.

05Non-atomic update

counter = counter + 1 is read, add, write. Interleave two threads between those steps and one write overwrites the other.

06Race condition

A result that depends on timing. Non-deterministic, load-dependent, often invisible on a fast laptop — and exploitable as TOCTOU when the race is between a check and an action.

07Deadlock

Two threads each waiting for a lock the other holds, forever. Prevented by always acquiring locks in the same order.

08Amdahl's law

The sequential fraction sets a hard ceiling: 10% sequential means at most 10×, even on 1,000 cores. Doubling threads almost never halves the time.

09Pool sizing

For CPU-bound work, roughly one thread per core; more only adds switching. For I/O-bound work with threads, higher counts help — but async helps far more.

10Processes for isolation

When one failure or one hostile input must not spread. Chrome and PostgreSQL pay the memory deliberately; a crashed worker is replaced, not fatal.

11Async for waiting

Concurrency is structure — dealing with many things at once. An event loop multiplexes thousands of I/O tasks on one thread with no context switches and no locks.

12Multiprocessing under a GIL

Python's global interpreter lock lets only one thread execute bytecode at a time. Threads still help I/O; CPU work needs separate processes.

13Multithreading for computing

Parallelism is hardware — many things genuinely at once. Worth it for CPU-bound, independently splittable work in languages without a GIL: Java, C#, Go, Rust, C++.

14Single-threaded, or distributed

If the pieces constantly share state, locks will serialise everything anyway. If one machine is not enough, distribute workers behind a queue.

In-memory locks do not protect money

Races in payment, inventory or balance logic cause real losses, and a mutex only protects one process on one machine. Anything that matters across workers or servers needs a database transaction, not a lock in application memory.

Sheet 8

The Scheduler and the Switch

Control loop Covers · Scheduler · Context Switching · Process · Thread · Registers

A laptop runs three hundred processes on eight cores by lying very fast. The scheduler hands each thread a few milliseconds, then a context switch saves everything it was doing and restores someone else. The paperwork costs microseconds; the cold caches afterwards cost more — which is why more threads is not more speed, and why async I/O exists at all.

Step key — the loop and the switch

01Admitted

fork and exec create the process and its main thread; the kernel sets up its control block and places it in the ready queue.

02Scheduled

The scheduler picks a READY thread and switches it onto a core. It runs this decision thousands of times per second so everything appears simultaneous.

03Preempted

A hardware timer interrupt lets the kernel take the core back when a slice expires or a higher-priority thread wakes. Every modern OS is preemptive; cooperative yielding is historical.

04Blocked

The thread waits on a socket, a disk or a lock and releases the core immediately. Not the scheduler's problem — and not using CPU.

05Woken

The I/O completes or the lock frees, and the thread returns to the ready queue to wait for a core again.

06Terminated

An exit code: 0 for success, 137 for SIGKILL (usually the OOM killer), 143 for SIGTERM. Handle SIGTERM, or be killed mid-work; reap children, or leave zombies.

07Save state

All registers, program counter, stack pointer and flags of the outgoing thread are written to its control block. Including any secrets they held at that instant.

08Accounting

The CPU time just consumed is recorded. Without it there is no fairness, no nice values and no container CPU limits.

09Pick next

Linux CFS runs the thread that has had the least CPU time, weighted by priority. Fair is not the same as low-latency: a sensitive task can still wait.

10Load state

The incoming thread's saved registers are restored into the core. Direct cost of the whole exchange: roughly 1–10 µs.

11Address-space switch

If the incoming thread belongs to another process, page tables change and the TLB is flushed, so memory access is slower until translations are cached again.

12Resume

Return to user mode; the thread continues as if it never stopped. It has no idea it was ever away.

13Cache pollution

The new thread's data is not in L1–L3, so it runs slowly while caches refill. Usually costlier than the switch itself, and invisible in profilers.

14User-space switching

Goroutines, async/await, fibers and Java virtual threads switch in ~10–100 ns inside one process; an event loop avoids switching altogether.

15CPU throttling

Kubernetes and Docker CPU limits are enforced by cgroup bandwidth control in the scheduler: over quota, a container is descheduled, not killed.

16Thrashing

So many runnable threads that the machine spends its time switching instead of working. 200 threads on 8 cores can be slower than 16.

The scheduler is shared hardware, too

By timing its own work, one process can infer what another is doing — the basis of cross-tenant attacks on shared cloud machines — and every switch writes the outgoing thread's registers, secrets included, into kernel memory that can end up in a crash dump. Use constant-time comparison for secrets and cgroup limits for neighbours. This is the same lesson as sheet 1, seen from the other side: the machine is fast and shared, and both facts leak.
