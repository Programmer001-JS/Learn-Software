Atlas of the Runtime

The program you write is never the thing the CPU runs. Between the two sit a translation strategy and a runtime: code you did not write, living inside your process, deciding how fast you start, how you wait, and how much memory you burn before handling a single request. Sheet 1 is the route source code travels to the silicon; every other sheet magnifies one stop on it. The runtime's concurrency model, garbage collector and startup cost shape your architecture more than the language syntax ever will.

Sheet 1

The Translation Line

Transit diagram Covers · Compiled vs Interpreted Languages · Bytecode

A CPU executes machine code and nothing else, so every language needs a way to get there. There are only two basic answers (translate everything first, or translate as you go) and a very popular third that does both. Compilation is translation; interpretation is simulation. On the interpreted route the CPU is not running your program at all. It is running the interpreter, which is pretending to be your program.

Step key — every stop on this sheet, and what it does

01Source code

What humans can write and read. A CPU cannot run a single byte of it, so every file has to take one of the three routes before anything happens.

02Compiler

GCC, Clang, the Go toolchain. It can spend seconds on the whole program (inlining functions, deleting dead code, allocating registers) because nobody is waiting for the result.

03Native binary

Machine code for exactly one OS and one CPU family. An x86-64 Linux binary will not run on ARM macOS. You get one self-contained file per target.

04OS loads it

No interpreter or VM needs to start first, so startup is about 1 ms. This is why Go dominates CLIs and containers: a static binary in a ~10 MB image.

05Compile once

javac, Roslyn or CPython's internal compiler translate source into bytecode, not machine code. The work happens once, for every platform at the same time.

06Bytecode

Instructions for a machine that does not exist: .class, .dll (CIL), .pyc, .wasm. It is stack-based and compact, which makes it easy to interpret, verify and later translate. It runs nowhere without a VM.

07Load + verify

The VM loads the artifact and checks that it is well-formed before running any of it. Bytecode verification in the JVM and CLR is a real security control, not a formality.

08Interpret

Fetch an opcode, decode it, execute it, repeat. Every opcode runs C code inside the VM, which is why an interpreted operation costs 10–100× more than a native one.

09Hot?

The runtime counts how often each function or loop runs. Cold code stays interpreted. Code called thousands of times is worth the cost of compiling. The loop back to 08 is the normal case for most of your code.

10JIT compile

Hot bytecode is compiled to machine code while the program runs, using the types and branches it has actually seen. This is how the JVM and V8 reach near-native speed. Sheet 3 opens it up.

11Transpile

A source-to-source compiler: TypeScript becomes JavaScript. Types are checked here and then erased, so nothing about them survives to run time.

12Interpreter starts

The interpreter itself must boot before your first line runs, typically ~50–500 ms. Serverless bills that time, and your users feel it on a cold start.

13Read, decide, run

The interpreter must decide what to do next, right now, thousands of times a second. It has no time for the whole-program analysis a compiler does at stop 02.

14CPU runs the interpreter

The machine code executing belongs to the interpreter, which simulates your program. That indirection is the entire performance difference, and also where the flexibility comes from: eval, hot reload, introspection.

15The CPU

It runs only machine code, on every route. The routes differ only in when the translation happens (before shipping, while running, or never) and in who pays for it.

Raw speed is rarely the deciding axis

Most web applications are I/O-bound, so choosing a compiled language "for performance" while the real bottleneck is a missing database index gains nothing. Measure first. With modern JIT runtimes blurring the line, the choice is usually about ecosystem, startup and deployment: shipping an interpreted service means shipping a specific runtime version, its dependencies and a container to hold them.

Sheet 2

The Runtime, Cut Open

Cutaway section Covers · Runtime Explained · CPython · Virtual Machines

Everything that must exist while your program runs but that you did not write. On the left, the layer stack every service sits in; on the right, the runtime layer opened up. A runtime is a long-running service inside your process. It starts before your code, keeps working behind it, and when it pauses to collect garbage, every request in flight pauses with it.

Step key — the layers, the machinery, and one request

01Application code

The only layer you wrote, and usually the only one in the stack trace. It asks for things (a list, a file, a socket) and assumes they simply exist.

02Framework

FastAPI, Express, Spring. Routing, middleware, serialisation. It runs on the runtime's model and cannot escape it: an async framework on a blocking call is still blocked.

03Standard library

Strings, collections, dates, JSON, HTTP. The runtime's reason to exist is that this work is identical for every program, so it was factored out once.

04Runtime

CPython, Node.js, the JVM, .NET, the Go runtime. It sits between your code and the operating system. Even a compiled Go binary embeds one for goroutine scheduling and GC.

05System calls

The only door into the kernel. open("file.txt") becomes a file descriptor, an epoll registration and a buffered read, and the runtime makes those calls for you.

06Kernel

Owns processes, memory and sockets. When a request is slow, the time may be here, not in the runtime or your code, which is why you need to know which layer is which.

07Hardware

CPU, RAM, disk, network card. On a cloud instance this is itself virtual hardware (sheet 5), but the runtime cannot tell the difference.

08Memory manager / GC

Allocates every object and frees the unreachable ones. It is the reason you never call free(), and the reason some requests take ten times longer than their neighbours.

09Scheduler / event loop

Decides what runs next: OS threads, an event loop, goroutines. Matching this model to your workload is the most important runtime decision you make. Sheet 4.

10JIT compiler

Compiles hot code to machine code while the program runs. It explains why the JVM gets faster after start-up, and why CPython, which has none, never does. Sheet 3.

11I/O subsystem

Buffering, async and socket handling. It parks a coroutine that is waiting on a database and wakes it when the kernel reports completion, so waiting costs almost nothing.

12Error handling

Exceptions, stack traces, panics. Useful to you and to attackers: stack traces leak internal paths and library versions, so never return them to users.

13Interop

Calling native C libraries through a foreign function interface: the C API, JNI, P/Invoke, N-API. It is why NumPy and PyTorch can be C and CUDA underneath a Python surface.

14Startup

Load modules, initialise the heap, start the scheduler. It takes ~1 ms for Go, ~50 ms for CPython and Node.js, and 1–3 s for the JVM, which decides whether serverless is viable.

15Allocation

Every x = [1,2,3] puts an object on the heap. In CPython every value is a heap object; an int costs ~28 bytes before it holds anything.

16Reachability

An object is live while anything can still reach it. CPython counts references on every object; tracing collectors walk the graph from the roots when they decide to.

17Freeing

Reference counting frees an object the instant its last reference goes, plus a cycle collector for objects that point at each other. Generational collectors free young garbage cheaply and often.

18The pause

Sometimes the collector must stop your program to work. It is invisible in averages and obvious at p99, so if the worst 1% of requests is terrible, check GC logs first.

R1Packet to socket

The kernel receives the packet and delivers it to the listening socket. Nothing in your process has run yet.

R2Loop wakes

asyncio's event loop sees the socket is readable and resumes the coroutine that was waiting for it.

R3Routing

The framework matches the path and method and calls your handler with a parsed request.

R4Your code

The handler runs. Each object it creates is allocated on the runtime's heap, which is memory the GC now has to track.

R5Suspend on I/O

The database call becomes a syscall. The runtime suspends the coroutine instead of blocking the thread.

R6Others proceed

While this request waits, the same thread serves other requests. This is the whole point of an event loop.

R7Write back

The result returns, the response is serialised, and the bytes go back to the socket and the kernel.

R8Reclaim later

The request's objects become unreachable. The runtime frees them whenever it chooses, possibly in the middle of somebody else's request.

Sheet 3

The Warm-Up Circuit

Closed circuit Covers · PyPy · JVM · dotNET Runtime · Bytecode · Compiled vs Interpreted Languages

Stops 08 to 10 of sheet 1, opened up. A JIT does not compile your program. It watches it, bets on what it has seen, and compiles only the parts that earned it. That bet is why a "slow interpreted language" powers banks and Netflix, and also why the same service is slow for its first thousand requests and why a short-lived script never sees the benefit at all.

Step key — the circuit and the runtimes that run it

01Interpret

Every piece of code starts here, executed one opcode at a time. Startup is fast because nothing has to be compiled, and each operation is slow for the same reason.

02Profile

While interpreting, the runtime counts calls and loop iterations and records what it sees: which types arrive, which branches are taken. Bytecode's analysable format is what makes this cheap.

03Threshold crossed

A method called thousands of times, or a loop run about a thousand times in PyPy, is declared hot. Only then is compilation worth its CPU cost.

04Compile, specialised

Machine code is generated for the case that actually happened, not every case the source allows. This is where a JIT can produce faster code than a static compiler.

05Run native

The hot path now runs at near-native speed. Each assumption baked into it is checked by a guard, which costs almost nothing while it holds.

06Deoptimise

An unexpected type arrives and a guard fails. The specialised code is discarded, execution falls back to the interpreter, and the circuit starts again with the new information.

07CPython

No JIT: every iteration is interpreted, every time, at roughly 50–100 machine instructions per simple operation. Speed comes from moving loops into C (NumPy), not from warming up.

08PyPy · tracing JIT

Interprets and traces a loop for its first ~1,000 runs, then compiles that trace: often 4–10× faster on pure Python with no code changes. C extensions go through cpyext and are often slower than on CPython.

09JVM · tiered

Interpreter first, then C1 for a quick compile, then C2 for aggressive optimisation of what stays hot. It explains the 1–3 s start and the near-native steady state.

10.NET · first call

RyuJIT compiles each method the first time it is called, quickly, and re-optimises it if it stays hot. Startup is faster than the JVM's and peak throughput arrives sooner.

11V8 · Node.js

JavaScript starts in the Ignition interpreter and hot functions move to the TurboFan optimiser, specialised on observed types and deoptimised when those change.

12Guard

The check that keeps speculation safe. When it holds, you get code tuned to your real data. When it fails, you pay a deoptimisation and a retrace, so type-unstable hot code stays slow.

13Warm-up

The period before hot paths are compiled. It costs CPU and memory and produces unrepresentative latency. Measure the first 100 requests and requests 10,000–10,100 separately, and never publish the first number.

14Ahead-of-time native

GraalVM native images (~50 ms start) and .NET Native AOT (~10 ms) skip the circuit entirely. The trade is lower peak throughput and no runtime code generation.

Never benchmark a cold runtime

The first thousand iterations of a JVM, .NET, V8 or PyPy program measure the interpreter and the compiler, not your code. Warm up, then measure. And if the process will never live long enough to warm up (a CLI, a serverless function, a short script), that cold number is the only one that matters, so choose a runtime that is fast from the first call.

Sheet 4

Who Holds the Thread

Timing chart Covers · CPython · Node.js Runtime · dotNET Runtime · JVM · Runtime Explained

Four runtimes, the same few seconds of a busy server, one row per thread. Solid blocks are code running; outlines are waiting. Every runtime is good at one of two things (waiting cheaply or computing in parallel), and almost every production incident on this sheet is a workload of one kind placed on a runtime built for the other.

Step key — the scheduling vocabulary

01The GIL

CPython's Global Interpreter Lock lets one thread per process execute Python bytecode at a time. It exists to make reference counting safe without locking every object. Four CPU-bound threads give roughly single-core speed plus switching overhead.

02Released on I/O

A thread waiting on a database, network or disk gives up the GIL, which is why threads and asyncio still help I/O-bound Python.

03Native code releases it

NumPy and PyTorch drop the GIL during heavy C and CUDA computation, so they genuinely use multiple cores. Python orchestrates; the native code computes.

04Processes, not threads

CPU-bound Python scales horizontally: Gunicorn workers, Celery processes, Instagram's fleet. Every worker has its own memory, so too many workers exhaust the machine.

05Event loop

Node.js runs your JavaScript on one thread. I/O is registered with the OS (epoll, kqueue) and the thread moves on immediately. libuv drives the loop through its phases.

06Callback queue

When the OS reports that I/O has finished, the callback is queued. It runs only when the thread is next free, never earlier, however long that takes.

07Blocking the loop

Any long synchronous computation (a 2-second loop, readFileSync, image processing) freezes every other request in the process. Health checks time out and the container is restarted.

08libuv thread pool

Four threads by default for work the OS cannot do asynchronously: file system, DNS, compression, crypto. Your JavaScript is single-threaded; Node.js as a whole is not.

09Cluster and workers

To use more than one core, run several Node.js processes (cluster, PM2) or move CPU work to worker threads: separate V8 isolates that communicate by message passing.

10async/await state machine

The C# compiler rewrites an async method into a state machine. Waiting costs a small object rather than a whole blocked thread, which is why ASP.NET Core handles high concurrency with a small pool.

11Thread released

While the query runs, no thread is held. The pool hands that thread to another request, so the same few threads serve many times their number of in-flight requests.

12Continuation

When the I/O completes, the rest of the method is scheduled on whichever pool thread is free, often a different one from the thread it started on.

13Sync over async

Calling .Result or .Wait() on async code blocks a real thread until the task finishes. Under load this starves the pool and can deadlock a web request. It is the classic .NET concurrency bug.

14Real threads

The JVM and .NET have no GIL: threads run in parallel on every core and share one heap. JVM services take a thread from the pool per request and return it afterwards.

15Stop-the-world pause

Periodically the collector halts application threads to reclaim garbage. G1 keeps pauses moderate, ZGC and Shenandoah keep them tiny, Parallel accepts long ones for throughput.

16Thread per connection

The traditional model: each connection gets a thread with megabytes of stack and a context switch whenever it blocks. 10,000 mostly idle connections cost ~10 GB, against ~50 MB for an event loop.

async is about waiting, not computing

Making a handler async does not make CPU work faster in any runtime. It only stops waiting from holding a thread. CPU-bound work needs real parallelism: processes for Python, worker threads or more processes for Node.js, or a runtime with real threads. Expecting parallelism from Python threads or putting a CPU loop on Node's main thread are the two most common versions of the same mistake.

Sheet 5

Three Kinds of Virtual

Stacked section Covers · Virtual Machines · Runtime Explained · JVM · CPython

"Virtual machine" names two genuinely different things, and the container sits between them without being either. A process VM is a CPU made of software; a system VM is a whole computer made of software. A VM virtualises the hardware, a container virtualises the operating system. Everything else about isolation, boot time and density follows from that single missing layer: the guest kernel.

Step key — the layers of virtualisation

01Bytecode artifact

The .jar, .dll or .pyc a process VM executes. The same file works on a server and a phone because the VM, not the file, knows the hardware.

02Process VM

A program that executes bytecode as if it were a CPU: execution with a JIT, memory management with GC, safety through type verification and bounds checks, and one API over many operating systems.

03Host operating system

Under a process VM, the kernel is real and shared with every other process. Startup costs 100 ms to several seconds, and speed is near-native once warm.

04Physical hardware

The one real machine. Every layer above it, however many there are, eventually borrows these CPUs and this RAM.

05Containerised app

An ordinary process with its own view of the filesystem and network. Often the app inside is itself a process VM, so layers 02 and 05 stack.

06Libraries

Everything the app needs, packaged into the image. That is megabytes, not gigabytes, because no operating system kernel is inside.

07No guest kernel

The defining absence. Containers share the host kernel, so they start in milliseconds, add near-zero overhead, and can only run software for that same kernel.

08Container runtime

Starts and isolates processes on the shared kernel. It gives the feel of a separate machine without the cost, and without the boundary.

09Shared kernel

Every container on the host calls the same kernel. A kernel vulnerability is therefore a vulnerability for every tenant at once: a shared attack surface.

10Guest apps

Applications inside a system VM, unaware that the machine is not real. They can run on a completely different operating system, for example Windows on Linux.

11Guest libraries

A full userland per VM, installed and patched separately. This is part of why a VM is measured in gigabytes.

12Guest kernel

Each VM boots its own kernel, which costs 30–60 seconds and a full OS worth of memory. It is also the strongest practical isolation short of separate hardware.

13Virtual hardware

Emulated CPU, memory, disks and network cards. Hardware assistance keeps the overhead to about 5–15%, and snapshots and live migration come almost free.

14Hypervisor

Type 1 (KVM, Xen, ESXi) runs directly on hardware and is what clouds use. Type 2 (VirtualBox, VMware Workstation) runs as an app on a desktop OS. Keep it patched: a compromise exposes every guest.

15Request arrives

The packet reaches the physical machine, which may be hosting dozens of customers' VMs.

16Hypervisor routes

It delivers the packet to the correct VM's virtual network card. This is the first layer of software your request crosses.

17Guest kernel receives

The VM's own kernel handles the packet as if the network card were real.

18Container runtime routes

If the app is containerised, the packet is routed into the right container on that kernel.

19Process VM executes

The JVM or CPython runs your application bytecode, bringing warm-up and GC behaviour with it.

20Handler and return

Your code runs and the response travels back down the same stack. When latency appears, the question is which of these six layers added it.

A container is not a small VM

Calling a container a VM hides the one fact that matters: there is no guest kernel. So do not rely on container isolation for genuinely hostile multi-tenant workloads, and do not go the other way and run a full VM per microservice, paying gigabytes of memory and a minute of boot for isolation you probably do not need. When you need both speed and a hard boundary, micro-VMs (Firecracker) and user-space kernels (gVisor) exist precisely for that.

Sheet 6

Choosing the Runtime

Decision tree Covers · Runtime Explained · Compiled vs Interpreted Languages · CPython · PyPy · JVM · dotNET Runtime · Node.js Runtime

You choose a runtime whenever you choose a language, usually without noticing. Make it deliberate: describe what the process spends its life doing, then follow the questions. Match the runtime's concurrency model and startup cost to the workload. A runtime you have to fight is the wrong runtime, however much the team likes the syntax.

Step key — the questions and where they lead

01What does it spend its life doing?

Profile before choosing. The bottleneck in most web applications is the database or the network, not the interpreter, and no runtime fixes a missing index.

02Lives for milliseconds?

Serverless functions, CLI tools and short scripts pay startup on every run. Cold starts are billed and user-visible, so this question outranks every other one.

03Mostly waiting on I/O?

APIs and gateways spend their time waiting on other services. What matters is how cheaply the runtime waits, not how fast it computes.

04Must it stay in Python?

Often yes, for good reasons: the data and AI ecosystem, the team, existing code. Then the question becomes where the CPU time goes inside Python.

05Hot loop already in C?

If NumPy or PyTorch already do the heavy lifting, the interpreter is not the bottleneck and changing runtime gains nothing. Profile with py-spy to find out which case you are in.

06Long-running, high-throughput?

Services that stay up for weeks amortise slow startup and memory overhead to nothing and collect the JIT's steady-state speed every second of the day.

07Start instantly

Go (~1 ms), .NET Native AOT (~10 ms), GraalVM native images or Node.js (~50 ms). The JVM's 1–3 s start is fatal for a function billed by the millisecond, and PyPy never warms up.

08Wait cheaply

Node.js, Python asyncio and .NET async/await all keep thousands of connections alive on a few threads. The one rule: never block the loop with synchronous work.

09CPython + processes

The default for Python. Native extensions release the GIL, and worker processes use the remaining cores. Under PyPy's cpyext those same extensions can run slower.

10Pure-Python hot loop

PyPy gives 4–10× on long-running pure Python with no changes. Alternatively keep CPython and compile only the hot path with Cython or Numba, vectorise with NumPy, or rewrite the hot 5% in Rust or C.

11JVM or .NET

Real threads, sophisticated collectors, tiered JIT and outstanding tooling. The JVM brings Kafka, Spark and Spring; .NET brings faster startup and the best-integrated async. Both need explicit memory limits in containers.

12Compiled ahead of time

Go, Rust or C when you need low memory, fast startup and a single artifact. You give up the managed runtime's JIT-level optimisation and, for Go, some of its ecosystem.

Choosing a language is choosing a runtime

CPU-bound Python threads will not use multiple cores. Blocking calls inside a Node.js event loop stall every other request. A JVM in a serverless function spends its budget starting up. None of these can be fixed by writing the code more carefully, because each is the runtime doing exactly what it was designed to do. When the workload and the model disagree, change the runtime, not the workaround.
