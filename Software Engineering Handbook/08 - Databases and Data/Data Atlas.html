Sheet 1

The Query Line

Transit diagram Covers · Database Fundamentals · SQL · PostgreSQL · Cache · ORM

One request, one route, seventeen stops. The database proper is six of them. Two stations can end the journey before the engine ever runs, stop 07 decides whether the answer takes a millisecond or four seconds, and the loop over the top is how one page quietly becomes a hundred and one queries.

Step key — every stop on this sheet, and what it does

01You ask

A request arrives for data: the pending orders of user 42. Everything downstream is shaped by two facts about it — the disk is slow, and other requests are changing the same rows right now.

02The service

The service layer is the transaction boundary: one use case, one transaction. A controller does not know which writes belong together, and a repository is too fine-grained to decide.

03The ORM

Method calls become parameterised SQL and rows become objects. It prevents SQL injection by default, and hides the one detail that matters most: how many queries it is about to send.

04The pool

Connections are expensive — a whole process each in PostgreSQL — so they are borrowed from a pool, never opened per request. Total demand is pool size × workers × replicas, and that product must fit the database limit.

05The cache

Cache-aside: check Redis before the database. A hit answers in about a millisecond and nothing to the right ever runs. A miss pays the full journey and writes the result back at stop 14.

06Parse

The SQL text is checked and every table and column name resolved. This is also where a query built by string concatenation has already lost: the input became code before anything could stop it.

07The planner

SQL says what, never how. The planner uses table statistics to choose an index or a sequential scan, a join order and a join method. Stale statistics mean bad plans on perfect indexes.

B1Statistics

Is the index selective enough to be worth it? A boolean over 50/50 data is not. ANALYZE keeps these numbers current; without them the planner is guessing.

B2Root page

The top of the B-tree. One page read narrows the whole table's range of values to a fraction of it.

B3Internal page

Each level narrows again. Three or four levels are enough to cover millions of rows, which is why an index lookup costs three or four page reads.

B4Leaf page

Sorted values with pointers to the rows. Because the leaves are already in order, ORDER BY created needs no sort at all — the executor just reads the next 20 entries.

08The executor

Runs the plan: fetches pages, applies filters, performs the join by nested loop, hash or merge — whichever the planner chose. EXPLAIN ANALYZE shows what it actually did.

09Buffer pool

Hot pages held in RAM — shared_buffers in PostgreSQL, the InnoDB buffer pool in MySQL. A hit costs roughly 100 nanoseconds, and most reads on a healthy database never go further.

10Disk

A miss reads the page from SSD at around 100 microseconds — a thousand times slower. Indexes, the buffer pool and the write-ahead log all exist to avoid or reshape exactly this cost.

11MVCC filter

Rows are stored as versions. Only the versions visible to this transaction's snapshot are returned, which is why readers never block writers and writers never block readers.

12Rows

LIMIT is applied last in the logical order of a SELECT. A query with no LIMIT on a growing table is a memory problem waiting for the table to grow.

13Map to objects

Rows become objects. The identity map guarantees the same row fetched twice is the same object — a free, request-scoped cache. Touching an unloaded relation here is what starts the N+1 loop.

14Write back

On a miss, the application stores the result with a TTL: SET … EX 300. Every identical request for the next five minutes takes exit B instead of the whole line.

15Commit, close

The session or DbContext is closed and its connection returned to the pool. A session that is never closed holds a connection and an open transaction — exits A and the vacuum hazard, both at once.

16Build a DTO

The response is built from a purpose-made object, never the entity. Entities serialise every column — including ones added next year — and can trigger lazy loads mid-serialisation.

17The ledger

pg_stat_statements records calls and total time per query shape. It is how you find the slow stop on this line from measurement instead of from intuition — sheet 6, rung 1.

The two exits are not free

Exit B only exists while the cache is warm: a restart or a flush sends every request down the full line at once, and a missing index that the cache was hiding appears at the worst possible moment. Exit A is not an exit anyone chooses — it is what "the database is slow" usually means when the queries themselves are fast and the requests are queuing for a connection.

Sheet 2

Inside the Engine

Cutaway section Covers · PostgreSQL · MySQL · Database Fundamentals · Transactions

Stops 09 to 11 of sheet 1, cut open — this time for a write. On the left, the whole path one UPDATE takes through the engine; on the right, the four mechanisms it passes through, magnified. Durability is an ordering rule, not a feature: the log reaches the disk before the commit is acknowledged, and the page itself follows whenever it is convenient.

Step key — the engine, step by step and band by band

01The statement

Written as qty = qty − 1 rather than a value computed in application code, so the database does the arithmetic under its own lock. Sheet 4 shows why that one choice prevents a lost update.

02Parse and plan

Exactly the read path of sheet 1: the text is parsed, and the planner picks an index to find row 42. A write without a usable index scans the table to find what it must change.

03Find the page

The page holding row 42 is located through the index and served from shared buffers if it is hot, or read from disk and cached if it is not.

04Lock the row

The UPDATE takes a row lock. Any other writer to row 42 waits until this transaction ends — which is why a long transaction is somebody else's latency.

05Write a new version

MVCC: the old row version is marked dead, a new one written beside it. Readers already running keep seeing the old version; nobody is blocked.

06Append to the WAL

The change is described in the write-ahead log first. Appending to a log is a sequential write, far cheaper than updating pages scattered across the disk.

07Flush the WAL

The log is forced to durable storage. This is the precise instant the change becomes crash-proof, and the reason commit latency tracks disk flush latency.

08COMMIT acknowledged

Only after step 07 returns does the client hear "committed". From here, the change survives a power cut; before it, the transaction never happened.

09Checkpoint

Modified pages in memory are written to their real place on disk later, in bulk. If the server crashes first, replaying the log rebuilds them.

10Stream to replicas

PostgreSQL streams WAL; MySQL writes the binlog and replicas pull it. Both are asynchronous by default, so a replica is a slightly older copy, not a mirror.

11Autovacuum

Dead versions from step 05 are reclaimed once no snapshot can see them. When it falls behind, tables bloat and queries slow gradually, with no single cause in any log.

AMVCC

Multi-Version Concurrency Control. Each transaction reads a snapshot, so concurrent reads and writes proceed together. InnoDB does the same with undo logs. The price is cleanup — and an idle-in-transaction connection stops it.

BConnections

A process per connection in PostgreSQL (default limit 100), a thread in MySQL. Pool size × workers × replicas must fit under the limit; PgBouncer in transaction mode is the standard fix, not a higher limit.

CBuffer pool

RAM is about a thousand times faster than SSD, so the pool holding hot pages is the engine's real speed. Size shared_buffers near 25% of RAM, or the InnoDB pool near 70–80%.

DReplication

Copies for read scaling and failover. Lag is a correctness concern: a read that must reflect the user's own last write goes to the primary.

EInherited defaults

utf8 instead of utf8mb4, strict mode off, MyISAM tables, non-transactional DDL. MySQL 8 fixed the defaults — but a database you inherited may never have been upgraded to them.

Sheet 3

The Index

Exploded parts Covers · Indexes · SQL · Database Optimization

The branch below stop 07 of sheet 1, taken apart. An index is a second, sorted copy of a few columns that lets the engine read three pages instead of every page. It is the highest-leverage change in this whole folder — and it only works if the query is shaped the way the index is sorted, which is where most of them silently fail.

Step key — the parts on this sheet

01Root page

The single entry point of a B-tree. Its keys split the whole range of values, so one read discards most of the table from consideration.

02Internal pages

Each level narrows the range again. Three to four levels cover millions of rows, which is why lookup cost barely moves as the table grows.

03Leaf pages

The indexed values in sorted order, each with a pointer to its row. Sorted leaves are what let one index serve equality, ranges and ORDER BY.

04The heap

The table itself. An ordinary index scan finishes by fetching the row from here — unless the index already holds every column the query needs.

05Seq Scan

Reading every page of the table. Perfectly fine on a small table; ten million rows and about four seconds on a large one, and the buffer pool fills with useless pages.

06Index Scan

Descend the tree, read the matching leaves, fetch those rows. Roughly three pages and fractions of a millisecond — 10 to 10,000 times faster on large tables.

07EXPLAIN ANALYZE

Runs the query and reports what the database actually did. "Seq Scan" on a big table is the answer to most slow-query reports. Read it before and after every change.

08Statistics

The planner's estimates of how many rows each condition matches. ANALYZE refreshes them; when they are stale the planner picks the wrong plan with a perfect index in place.

09Composite index

Several columns, sorted left to right. Usable for any leading prefix of its columns and nothing else. Equality columns first, range next, sort last.

10Partial index

An index over only the rows a condition selects — say the 2% of orders that are pending. Smaller, faster, and cheaper to maintain on every write.

11Expression index

Indexes the result of an expression such as lower(email). The fix when the query must apply a function, since a function on a plain indexed column disables the index.

12Covering index

INCLUDE adds non-key columns, so the query is answered from the index alone — an index-only scan. SELECT * makes this impossible by definition.

13Write cost

Every INSERT, UPDATE and DELETE updates every index. Indexes also take 10–30% of table size and compete for the buffer pool. Unused ones (zero scans in pg_stat_user_indexes) are pure overhead.

14Logical order

FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY, LIMIT. It explains why aliases fail in WHERE, why HAVING exists, and why a LEFT JOIN condition belongs in ON rather than WHERE.

15Parameterised query

The input is sent as data, never spliced into the SQL text. The only reliable defence against SQL injection; ORMs do it by default until someone writes raw SQL with string formatting.

Sheet 4

The Commit

Timing diagram Covers · Transactions · PostgreSQL · MySQL · Database Fundamentals

Sheet 2 showed what a single write guarantees. This sheet shows what happens when two of them overlap in time. A transaction makes a group of writes all-or-nothing, but it does not stop two requests from reading the same value and both acting on it — that bug lives in the gap between the read and the write, and you must close it explicitly.

Step key — the transaction vocabulary

01A reads

Buyer A's transaction reads stock = 10 into application memory. From this instant the value in memory can go stale, and nothing in the database knows A intends to change it.

02B reads

Buyer B reads the same row a moment later. A has not written yet, so B also sees 10. At READ COMMITTED this is entirely correct behaviour.

03A writes 9

A computes 10 − 1 in code and writes the literal 9. The row lock taken now protects the write — but not the decision, which was made from an old read.

04B writes 9

B waits for A's lock if A has not committed, then writes its own 9, overwriting A's work with the same number. No error is raised anywhere.

05Both commit

Two items sold, stock decremented once. Durable, consistent with every constraint, and wrong. This is the most common real transaction bug and it costs real money.

06Atomic update

qty = qty − 1 WHERE qty > 0. The read, the check and the write happen inside one statement under the row lock. Best whenever the logic fits in SQL.

07SELECT … FOR UPDATE

Pessimistic locking: the row is locked at the read, so the second transaction blocks until the first commits and then reads the new value. Keep it short.

08Optimistic locking

A version column checked in the WHERE clause. Zero rows affected means a concurrent change won; re-read and retry. Cheap when conflicts are rare.

09Read uncommitted

Can see other transactions' unfinished writes — dirty reads. Essentially never used on purpose.

10Read committed

Sees only committed data, but a row may change between two reads in the same transaction. PostgreSQL's default.

11Repeatable read

The same query returns the same rows throughout the transaction. MySQL's default. Stronger — and still not a cure for application-side read-modify-write.

12Serializable

Behaves as if transactions ran one at a time, preventing phantom rows too. Safest, slowest, and the level that produces the most retries.

13BEGIN

Opened by the service method for one use case. Frameworks do it for you — Spring's @Transactional, a SQLAlchemy session, EF Core's SaveChanges — which is why an exception rolls back every write.

14Lock the stock

SELECT … FOR UPDATE on the items being bought, so no concurrent order can sell the same units. If stock is short, raise: the rollback writes nothing.

15Insert the order

The parent row. On its own it is meaningless, which is exactly why it must commit together with its items or not at all.

16Insert the items

Anything spanning two tables must be atomic. Batch the item inserts inside this one transaction rather than committing each separately.

17Decrement stock

An atomic qty = qty − n, under the lock taken at step 14. The inventory invariant is now enforced by the database, not by hope.

18COMMIT

The write-ahead log is flushed first, then the commit is acknowledged. Everything inside the bracket becomes durable and visible to everyone at the same instant.

19After commit

Publish OrderCreated and send the email only now. Done inside the bracket, a rollback would have announced an order that never existed.

20Deadlock

Two transactions waiting on each other's locks. The database resolves it by killing one participant; retrying that transaction is ordinary, required error handling.

21Saga

ACID does not cross service boundaries. A saga is a chain of local transactions, each with a compensating action for when a later step fails — eventual consistency by design.

22Outbox

An event row committed atomically with the business write, then published by a relay. The honest way to "write and publish" when the broker is a separate system.

Short, local, and inside the database

Keep transactions to milliseconds: a long one holds locks, blocks writers, holds a pooled connection and stops PostgreSQL's autovacuum from cleaning anything newer than it. Never include an external API call, a file upload or a queue publish. And never assume a transaction spans two services — it does not, however it looks in the code.

Sheet 5

The Mapping Layer

Closed circuit Covers · ORM · SQLAlchemy · Hibernate · Entity Framework · Prisma

Stop 03 of sheet 1, opened up. Every ORM — in Python, Java, C# or TypeScript — runs the same six-step circuit once per request, under a different name. The circuit is what makes an ORM safe and short; the spur off step 3 is what makes it slow, and it is invisible in the source code until something counts the queries.

Step key — the mapping vocabulary

01Open a session

The unit of work is created per request by dependency injection or a context manager. It is not thread-safe and must never be global, singleton or shared.

02Build the query

select(), LINQ, a repository method or findMany is translated into parameterised SQL. This is where loading strategy — eager or lazy — is decided, explicitly or by default.

03Materialise

Rows become objects. The identity map guarantees one object per row within the session: a free per-request cache, and the reason the same entity fetched twice is the same instance.

04Mutate

Business logic changes objects; the change tracker records it and no SQL is sent. In Hibernate, modifying a managed entity issues an UPDATE even without a save() call.

05Flush and commit

Tracked changes become UPDATE and INSERT statements inside one transaction — sheet 4's bracket, drawn for you by the framework.

06Close, map to DTO

The connection returns to the pool and the response is built from a purpose-made object. Returning entities serialises every column and can trigger lazy loads after the session is gone.

07N+1

One query for the list, then one per row for each lazy relation touched in a loop. The near-universal ORM performance bug, fixed with eager loading and caught with a query counter.

08Active Record

The model knows how to save itself. Fast to write and simple to read; the price is a domain model welded to the persistence layer.

09Data Mapper

A separate layer moves data between plain objects and tables. More ceremony, cleaner separation — the style of SQLAlchemy, Hibernate and Doctrine.

10The spectrum

Full ORM, query builder, micro-ORM, raw SQL. Query builders are underrated: composable and parameterised without hiding the query shape. Drop to SQL whenever the query is the point.

11SQLAlchemy

Core expression language underneath, ORM on top, both in one Session. selectinload for collections, joinedload for many-to-one, lazy="raise" to make N+1 fail loudly. Alembic for migrations.

12Hibernate

The JPA reference implementation under Spring Data JPA. Mark relations LAZY, fetch explicitly, map to DTOs inside the transaction, and disable spring.jpa.open-in-view. Flyway, not hbm2ddl.auto.

13EF Core

LINQ compiled to SQL, lazy loading off by default. DbContext scoped per request, AsNoTracking() for reads, AsSplitQuery() against cartesian Include chains, Dapper beside it for reports.

14Prisma

schema.prisma generates a typed client, so a missing include is a compile error and N+1 cannot happen by accident. Use select to avoid leaking fields such as passwordHash; plan pooling for serverless.

15Migrations

Versioned, reviewable schema changes applied in order in every environment. The most underrated ORM feature — and the most dangerous when applied unread, or bypassed with db push or EnsureCreated().

The protection ends at the string

Every ORM on this sheet parameterises by default, which is its strongest argument. The moment someone formats input into raw SQL, or binds a request body straight onto a model and lets a caller set is_admin, that protection is gone. Bind to an explicit input schema, and let the runtime database user hold no DDL rights at all.

Sheet 6

The Optimisation Ladder

Ladder plate Covers · Database Optimization · Indexes · Cache · PostgreSQL · Database Fundamentals

Nine ways to make a slow data layer fast, drawn in the order you should try them. Each rung is roughly ten times the effort of the one below it and ten times less likely to be needed — so measure, fix the N+1, add the index, and stop the moment it is fast enough.

Step key — the rungs and the instruments

01Measure

Enable pg_stat_statements and list queries by total execution time; then EXPLAIN ANALYZE the top offenders. Nothing else on this sheet is allowed to happen before this.

02Fix the N+1

Usually the largest single win in an ORM application: a page issuing hundreds of queries becomes a handful with eager loading. A query counter in development makes it visible immediately.

03Add indexes

The second largest win, and cheap. Index foreign keys and the columns in WHERE, JOIN and ORDER BY; order composite columns equality, range, sort; drop indexes with zero scans.

04Rewrite queries

Select only needed columns, replace date(created) = … with a range, and use keyset pagination instead of deep OFFSET. Small edits, often large effects.

05Cache

Only after the query itself is reasonable. A cache over a slow query hides a missing index that the cold cache, the restart and the next scale-up will each reveal.

06Tune configuration

Defaults assume a small machine. Size the buffer pool, keep work_mem sane because it multiplies across concurrent sorts, and keep max_connections low behind a pooler.

07Read replicas

Scale reads horizontally. Replica lag turns into user-visible bugs wherever a request must read its own recent write, so those reads stay on the primary.

08Denormalise

Duplicate data to avoid joins, deliberately, with a written reason and a measured read pattern. Partitioning a huge table by time usually comes first and costs less.

09Shard

Split data across machines. Breaks joins, complicates transactions, forces a shard key into every query and is extremely hard to undo. Instagram deferred it for years by indexing and caching properly.

10The realistic session

4 s and 340 queries; eager loading to 900 ms; one concurrent index to 120 ms; named columns to 90 ms. Then stop — the discipline is refusing to climb further once it is fast enough.

11Total, not mean

A 5 ms query called 200,000 times costs 1,000 seconds; a 2 s query called twice costs 4. Sort pg_stat_statements by total_exec_time or you will optimise the wrong one.

12Keyset pagination

OFFSET 100000 must read and discard 100,020 rows, getting linearly slower with depth. WHERE id < :last_seen ORDER BY id DESC LIMIT 20 costs the same on every page.

13Configuration

shared_buffers near 25% of RAM, the InnoDB buffer pool near 70–80%, work_mem per operation, effective_cache_size to tell the planner about the OS cache.

14Guard rails

statement_timeout, capped page sizes and rate limits turn an unoptimised query from an availability vulnerability into a slow request. Connection exhaustion is often misdiagnosed as slowness.

Sheet 7

The Fast Copy

Sorting line Covers · Redis · Cache · Session Store

Stop 05 of sheet 1 and the trip back, drawn in full — plus the other job Redis does on every request. A cache is a copy of an expensive answer kept somewhere cheap; a session store is a copy of "who is logged in" kept where every server can see it. Both trade the guarantee that data is current for speed, and both need a source of truth behind them: Redis with nothing behind it is not a cache, it is a fragile database.

Step key — the fast copy, stop by stop

01Single thread

Commands run one at a time on one thread, so each is atomic with no locking. The same design means one slow command such as KEYS * stalls every client.

02Hash table in RAM

All data lives in memory, so a lookup is O(1) and well under a millisecond. The speed comes from avoiding the disk, not from parallelism — and RAM cost caps the dataset.

03Persistence

RDB snapshots and the AOF log run in the background as a safety net. Unless carefully configured, a crash can still lose recent writes — never make Redis the only copy.

04Cache layers

CPU cache, application memory, Redis, CDN: the same idea at scales from bytes to terabytes. HTTP Cache-Control is the most widely deployed and most underused of them.

05What to cache

Read often, changes rarely, costly to compute, shared across users, tolerant of staleness. Never balances, stock levels or permissions that must be exact.

06The request

A read arrives for product 42. Redis is always reached by the backend, never by the browser.

07Check the cache

GET product:42. A hit returns in about a millisecond and PostgreSQL never sees the request. The code must also handle nil — assuming the value is always there crashes on the first miss.

08Miss, then query

The first request, or the first after expiry, pays full price: a query of around 40 ms against the source of truth.

09Store with a TTL

SET product:42 … EX 300. Every entry gets an expiry, turning "possibly wrong forever" into "wrong for at most five minutes".

10Return

The response goes out; for the next five minutes every identical read takes the dashed shortcut over the line.

11Write the database

Writes go to PostgreSQL first — the source of truth. Write-behind (cache now, database later) is fast and loses data on a crash.

12Delete the key

Invalidate rather than update. Deleting is safe under concurrency; writing the new value can be overtaken by a slower concurrent writer and stay stale indefinitely.

13Next read misses

The following read takes the miss path, fetches fresh data and repopulates. Plan for a cold cache too: a restart sends every request to the database at once.

14Hit rate

At 95% the database sees 5% of reads; at 10% you added a system, a failure mode and a staleness risk for nothing. Measure it — above 80% is the usual bar.

15TTL

Seconds for fast-moving data, minutes for pages, hours for reference data. A key without a TTL fills memory with data nobody reads.

16Eviction

When memory is full something goes: least recently used is the sensible default, least frequently used suits stable popularity.

17Login

HTTP forgets everything between requests, so the server issues a ticket after checking credentials once instead of receiving them on every request.

18Verify

The password is checked with a hashed comparison. Only now does the server create any state for this user.

19Regenerate the ID

A new session ID on login. Otherwise an attacker who planted a known ID before login inherits the authenticated session — session fixation.

20Store the session

A small record — user id, roles, CSRF token — under a cryptographically random ID with a 30-minute TTL. Not the full user object, and nothing sensitive in plaintext.

21Set the cookie

HttpOnly so script cannot read it, Secure so it never travels in plaintext, SameSite against CSRF. All three are required; each missing one has caused real breaches.

22Every request

The browser sends the cookie automatically. Because the store is shared, any server behind the load balancer can answer — no sticky sessions needed.

23Look it up

One Redis GET, well under a millisecond. Missing or expired means 401; found means the request proceeds as user 42 and the idle timeout is refreshed.

24Logout

DEL session:<id> — effective immediately, everywhere. Invalidate all of a user's sessions on password change too, or a compromised account stays compromised.

25Session or JWT

The deciding question is revocation. Sessions revoke instantly; JWTs need a blocklist, which reintroduces the lookup. JWTs fit many independent services and non-browser clients.

26Failure modes

A down store logs everyone out, a compromised one hands over every session, and a personalised response under a shared key leaks data between users. Bind Redis privately, with ACLs and TLS.

Sheet 8

Messages and Locks

Timing diagram Covers · Pub Sub · Distributed Lock · Redis · Transactions

Once the same code runs on several servers, two new problems appear: telling every instance something, and making sure only one instance does something. Redis offers a primitive for each. Both are fast, simple and honest about one thing people skip — a broadcast can be missed and a lock can expire while you still hold it — so neither may carry anything that must not be lost or done twice.

Step key — coordination, message by message and second by second

01Persist first

Server 1 validates the chat message, authorises it and writes it to the database before anything else. Durability lives here, never in the broadcast.

02PUBLISH

The message goes to the room:42 channel. The publisher does not know, or care, who is listening — which is exactly why adding a consumer never touches the producer.

03Delivered

Server 2 holds user B's WebSocket and pushes the message down it. Without this bridge a chat app works on one server and breaks the moment a second is added.

04Ignored

Server 3 has nobody in room 42 and discards the copy. Cost grows with subscribers × message rate, but nothing is stored.

05Missed

Server 4 was restarting. Classic Redis Pub/Sub has no acknowledgement, no retry and no replay: the message is gone for that subscriber, permanently.

06Catch up

Its users reconnect and load recent history from the database. The design assumes broadcasts can be missed and recovers from the system of record.

07Acquire

SET lock:job <random token> NX EX 30 — set only if absent, expire on its own. Atomic acquisition and a TTL are both non-negotiable; check-then-set races by construction.

08Expiry

A has stalled past its TTL. The lock expires exactly as designed, so a crashed holder cannot block the job forever — and a merely slow holder is now unprotected.

09B acquires

From the lock store's point of view the key is free, so B takes it with its own token and starts the same work A believes it is still doing.

10A wakes and deletes

A finishes and calls DEL unconditionally, deleting B's lock. Now the key is free while B is mid-job.

11C acquires

C sees a free key and starts. Two workers run the "exclusive" job at once, and no step along the way raised an error.

12Release by token

Delete only if the stored token is still yours, checked and deleted atomically in a Lua script. Fixes step 10; cannot fix step 08.

13Watchdog

The holder renews its TTL periodically while working — every 60 s on a 300 s lock, as Redisson does. It narrows the window; a pause longer than the renewal interval still breaks it.

14Efficiency or correctness

If a duplicate run is merely wasteful, a Redis lock is fine. If it is a bug — double charges, overselling, duplicate accounts — the lock is the wrong tool, and the job must be idempotent regardless.

15Stronger tools

Idempotency keys with unique constraints, row locks, unique indexes, queues, and SELECT … FOR UPDATE SKIP LOCKED for job claiming. Each is enforced by a system that cannot be paused out of its guarantee.

Channels and lock keys are not access control

Any client connected to the broker can subscribe to user:42:private, and any client that can write to the lock store can take a critical lock and never release it. Keep Redis on a private network with authentication, let browsers talk only to your servers, publish identifiers rather than sensitive payloads, and use unpredictable lock tokens.

Sheet 9

Choosing the Store

Decision tree Covers · Database Fundamentals · PostgreSQL · MySQL · MongoDB · Redis

The decision every other sheet quietly assumed. Five questions, four destinations, and one strong default. Start with PostgreSQL unless a question below gives you a specific, measured reason not to — most "we need NoSQL" decisions are made before anyone knows the access patterns.

Step key — the questions and where they lead

01Source of truth?

If losing the data means losing it for good, it needs durable, ACID storage. If it can be recomputed or re-fetched, a faster, losable store is on the table.

02Redis

An in-memory key-value store for cache, sessions, locks and pub/sub. Wrong when data must never be lost, when the dataset exceeds RAM, or when every request is unique and nothing would be hit.

03Relational?

Joins, foreign keys, constraints, money, anything spanning two tables in one transaction. The two families differ exactly here: tables with enforced schemas and ACID, or documents and key-value with flexible schemas.

04MySQL demanded?

Ecosystem and team experience are real advantages. WordPress, an existing PHP stack or deep MySQL replication skills justify it; for a new project without them, PostgreSQL is usually the better default.

05Document-shaped?

Read whole, written whole, bounded in size, with genuinely varying structure per record. If not, PostgreSQL's JSONB stores documents with real indexes while keeping joins and transactions.

06Horizontal writes?

Built-in sharding is MongoDB's strongest argument — but only for a measured need. A single well-indexed PostgreSQL handles far more than most teams assume.

07MySQL

The most widely deployed relational database: fast simple reads, lightweight threads per connection, very mature replication. InnoDB and utf8mb4 always; YouTube's Vitess shows how to scale it without replacing it.

08PostgreSQL

Correct, extensible, and capable of absorbing documents, search, geospatial, vectors, time series and job queues. Run it behind PgBouncer with a healthy autovacuum and it is the only datastore most projects need.

09MongoDB

Documents in collections, stored in the shape the application uses. A replica set in production, explicit write concern, bounded embedding, and a shard key chosen as if it can never change — because in practice it cannot.

10Embed or reference

Embed bounded data read together for one read and an atomic update; reference unbounded or shared data. Unbounded embedded arrays are the classic MongoDB failure, ending at the 16 MB document limit.

11Write concern

How many replica-set members must acknowledge a write before it is "done". w: 1 is fast and can vanish in a failover; w: "majority" is slower and survives it. A correctness decision, not a tuning knob.

12Breached defaults

Unauthenticated MongoDB and Redis on public interfaces, databases reachable on their default ports, applications connecting as superuser. Every one of these has been a real, repeated incident — and every restore you have not tested is another.

A database is a library, not a warehouse

Whatever you choose, the shape on sheet 1 does not change: a catalogue so you never walk every shelf, a lending record so two people cannot borrow the same book, and a reading room holding what is in use right now. Choosing the store picks the building. The indexes, transactions and buffer pool are still the work.
