Software Engineering Handbook · 13 DevOps and Delivery · seven sheets

Atlas of Delivery

One change, from a new branch on a laptop to a share of real traffic — and, when it goes wrong, back again. Sheet 1 is the route a commit actually travels; every other sheet magnifies one stretch of that route or the ground it lands on. None of it exists to make shipping fast. It exists to make every change small enough to review, identical everywhere it runs, and reversible in minutes — speed is what you get as a side effect.

Sheet 1

The Delivery Line

Transit diagram Covers · CI CD · Git · GitHub · GitHub Actions · Docker · Deployment Strategies

One 60-line change, fourteen stops out and five back. Git, GitHub, Actions, Docker and the rollout are each a few stations on the same line. The orange ring at stop 06 sends a change back in 25 seconds; the red ring at stop 13 undoes it in 90. Everything between them exists so that those two numbers stay small.

Step key — every stop on this sheet, and what it does

01New branch

A branch is a 40-byte file holding one commit hash, so making one per task costs nothing. That one implementation detail is what made pull requests, review and CI on every change possible. Sheet 2.

02Stage hunks

git add -p stages the coherent parts of your edits and leaves the rest. The index exists for exactly this, and it is the habit that produces commits a reviewer can follow.

03Commit

An immutable snapshot identified by the hash of its content. The branch label moves to it; nothing old is edited. Loop A returns here when a check fails.

04Rebase, push

Replay your unpushed commits onto the latest main (new hashes, safe because nobody else has them), then push with --force-with-lease, which refuses if someone else pushed in the meantime.

05Pull request

The unit of collaboration: a proposed change with discussion, checks and review attached before it reaches main. A template asks what changed, why, and how it was verified. Sheet 3.

06Fast checks

Lint, format and type check run first because they fail in seconds. Order every stage by how quickly it can prove you wrong; eight minutes of build before a formatting error wastes attention.

07Parallel jobs

Unit tests sharded four ways with cached dependencies, dependency and secret scanning, integration tests — all on fresh runners at once. Caching plus a matrix routinely takes twenty minutes to five.

08Review, merge

CODEOWNERS routes the review, one approval and green required checks unlock the merge, and a squash lands one clean commit on protected main. Small diffs are what make this stop quick.

09Build once

The artefact is built a single time and tagged with the commit SHA. Rebuilding per environment means staging and production run different bytes, which is how "it worked in staging" happens. Sheet 4.

10Scan and sign

Trivy fails the build on a critical CVE; cosign signs the image; it is pushed to the registry. Only what the pipeline built and signed should be allowed to run anywhere.

11Staging

Deployed automatically with staging's environment variables — the image is unchanged. Smoke and end-to-end tests, the slow suite, run here rather than blocking every pull request.

12Approve

The production environment waits for a required reviewer, then the job exchanges an OIDC token for a one-hour cloud role scoped to this repository and branch. No key is stored anywhere to leak.

13Canary 5%

One new pod takes 5% of real traffic, and its error rate, p99 and business metrics are compared with the stable version over the same ten-minute window. Sheet 7.

14Promote

Healthy, so traffic steps to 25%, 50%, then 100%. Old pods are drained: they stop accepting new connections, finish in-flight requests, and exit.

AThe loop back

A failed check returns the change to the laptop in seconds. The line stops on a defect instead of carrying it forward — a line that keeps running while producing defects only makes the problem larger.

C1up --wait

docker compose up -d --wait blocks until every health check passes, which is what makes Compose usable in CI and removes the sleep 15.

C2Migrate

Migrations run as an explicit step. Implicit migrations on container start race each other the moment a service is scaled beyond one instance.

C3Test against the real thing

Integration tests hit real PostgreSQL and Redis from the same definition developers use locally, instead of mocks that agree with whatever the code assumes.

C4down -v

Everything, volumes included, is torn down. The next run starts clean, so yesterday's data cannot make today's test pass.

BAutomatic rollback

Canary analysis fails, traffic returns to N, the canary is removed — no human decision in the loop. It is only possible because the previous image still exists and N+1 was backward compatible.

FFeature flag

Deploy is a technical event; release is a business decision. A flag separates them, lets unfinished work live on the trunk, and is the only rollback that takes effect in seconds without a pipeline.

15Release by flag

Product turns the feature on for internal users, then 1%, 50%, everyone. Nothing is deployed at any of those steps, so nothing can fail to deploy.

16Watch it

Error rate, p99 latency and the business metrics that tests cannot see. An automated deployment is only as safe as the monitoring that would tell you it went wrong.

17The record

The environment's history records which SHA was deployed, when, by which workflow and with whose approval. The running version is traceable to a reviewed commit.

18The next commit

The measure of the whole line is how long a branch lives, in hours. Frequent small changes are the reason high-deploying teams also have the lowest change failure rate.

Two things quietly break this line

A test that fails 3% of the time teaches everyone to re-run stop 07 instead of reading it, until a real failure is re-run away — quarantine it the day it flakes, give it an owner, fix or delete it. And never automate stops 11 to 14 before exit B has been rehearsed in staging: without a tested rollback and monitoring, you have only automated the delivery of outages.

Sheet 2

The Graph Underneath

Exploded parts Covers · Git

Stops 01 to 04 of sheet 1, taken apart. Git looks like a pile of inconsistent commands and is really a small database of immutable snapshots with movable labels on top. Nothing in Git is ever edited — "rewriting history" means taking new snapshots and moving a label, which is why almost every mistake is recoverable.

Step key — the parts of Git

01Working directory

The files as you are editing them. Nothing here is history yet; restore and switch move content back into it from the repository.

02Staging area

The index: exactly what the next commit will contain. Beginners resent it, experienced users rely on it, because it lets one messy afternoon become three coherent commits.

03Local repository

The complete object database and history, on your machine. It is why nearly every operation is fast and works offline, and why every clone is a full backup of history.

04Remote

A shared copy — GitHub, GitLab, or a bare repository over SSH. CI is triggered by what arrives here. Branch protection is a platform feature, not a Git one.

05Blob and tree

A blob is file contents with no name; a tree maps names to blobs and other trees. Identical files are stored once, because identical content has an identical hash.

06Commit

A tree plus parent commits, author and message, identified by the hash of all of that. A snapshot, not a diff: Git computes differences only when you ask to see them.

07Branch and HEAD

A branch is a file containing one commit hash; HEAD says which branch you are on. Committing writes a new snapshot and moves the label — which is why branches are free.

08Merge

Joins two lines with a commit that has two parents. History shows what really happened, and no existing commit changes, so it is safe on any shared branch.

09Rebase

Replays your commits onto a new base, creating new commits with new hashes. Linear and readable — and harmful the moment someone else has built on the originals.

10--force-with-lease

A force push that refuses if the remote has moved since you last fetched — exactly the situation in which a plain --force silently discards other people's work.

11Reset versus revert

Not alternatives. Reset moves a label and rewrites local history — fine for unpushed work. Revert adds a commit undoing an old one — the only safe option once others have pulled.

12Reflog

Every position HEAD has held, kept for weeks. A bad reset, a lost commit after a rebase, a deleted branch: the commits still exist. Learn it on a calm afternoon, not during a panic.

13Bisect

Binary search through history: mark a good and a bad commit, test the midpoints Git checks out. About ten steps across a thousand commits finds the change that broke it.

14Trunk-based development

Short-lived branches merged within a day or two, main always deployable, unfinished work behind feature flags. Git Flow suits scheduled versioned releases, not a continuously deployed service.

15Shallow clone

--depth 1 on a single branch is all most CI builds need. A full clone of a long-lived repository can dominate a fast pipeline's runtime.

16Committed secret

Compromised the moment it is pushed. Rotate the credential first; scrubbing history is optional and second. Scan with gitleaks before a commit exists, and never commit .env.

What Git is not

Not a place for secrets — history is permanent. Not a store for large binaries — every version is kept in full and every clone grows forever; use LFS or object storage. Not a deployment mechanism — build an artefact instead of pulling on a server. And not a backup of your machine: a repository is a history of what you chose to commit, nothing more.

Sheet 3

The Checkpoint

Floor plan Covers · GitHub · GitHub Actions · CI CD

Stops 05 to 12 of sheet 1, drawn as rooms and doors. Git manages history; GitHub manages the human process around it, and Actions runs code on every door. Each door is a rule, each rule has a bypass someone will ask for on a Friday night, and the pipeline behind them can deploy to production — which makes it one of the most valuable targets you own.

Step key — the rooms, doors and traps

01PR template

Three prompts — what changed, why, how it was verified — turn vague descriptions into useful ones without anybody nagging. The diff already says what; the description must say why.

02CODEOWNERS

Routes review automatically by path. Ask one named owner plus a team, not five individuals: diffused responsibility produces slow, shallow reviews.

03A reviewable size

Review quality collapses with size. Reviewers find defects in 50 lines and approve 500 on trust. If a change cannot be small, split it into a stack of sequential pull requests.

04Jobs and runners

A workflow is YAML in .github/workflows; each job gets a clean runner; jobs run in parallel by default. Split lint, test and build so they fail independently — a handful of jobs, not thirty.

05needs and artifacts

needs: sequences jobs. Nothing persists between runners, so files move only as artifacts. The build job runs once everything it depends on is green.

06Read-only token

Set permissions: contents: read at the top of every workflow and escalate per job. A compromised step inherits whatever the token can do.

07Concurrency

Cancels superseded runs on the same branch, so five outdated pipelines do not finish anyway. Together with the read-only token, the two highest-value lines in any workflow.

08Push protection

Secret scanning that rejects a push containing a recognisable credential. It prevents the rotate-and-scrub exercise instead of reporting it afterwards. Turn it on today.

09Branch protection

Require a PR, named passing checks, an approval, an up-to-date branch; dismiss stale approvals; block force pushes. And include administrators — the setting people skip. A check that exists but is not required means nothing.

10Environments

Scoped secrets, required reviewers and a deployment history for production. The deployment pauses at the door until a named person approves it.

11OIDC

The workflow presents a short-lived token that the cloud trusts for one repository and one branch, and gets a one-hour role. It removes the largest class of CI credential risk.

12pull_request_target

Runs the base branch's workflow with secrets and a write token in the context of an untrusted fork. Combined with checking out the PR head, it is remote code execution into your repository.

13Pin to a SHA

uses: action@v3 is a mutable tag executing inside a job that holds your secrets. A full commit SHA cannot be moved; Dependabot updates pins deliberately. The single most important Actions practice.

14Script injection

Interpolating a PR title into run: turns shell metacharacters into commands. Pass untrusted values through env: so they arrive as data, and lint workflows with actionlint.

15Runners

Hosted runners are fresh VMs with no network access to you. Self-hosted runners reach internal systems and keep warm caches — and must be ephemeral, never persistent on a public repository.

16Making it fast

Cache dependencies, shard the slowest suite, add concurrency, filter by path — in that order, stopping under ten minutes. Job startup is 10–30 s, so do not shard into dozens.

The pipeline is production

It holds credentials, runs third-party code, and its output is trusted by your infrastructure. A compromised pipeline is worse than a compromised server: it ships a backdoor through every control you have, signed off as a normal release. Protect workflow files with the same review as production code, and keep untrusted code away from any job that can see a secret.

Sheet 4

The Sealed Box

Cutaway section Covers · Docker · Docker Compose

Stops 09 and 10 of sheet 1, cut open. Namespaces and cgroups already existed; Docker's contribution was the image — a layered, cacheable, shareable filesystem with a one-file build definition. The artefact is the part that matters: one immutable image, tagged with a commit, that runs the same bytes on a laptop, in CI and in production.

Step key — the parts of an image and a stack

01Layer cache

Each instruction is cached by content; a changed layer invalidates every later one. COPY . . before npm ci reinstalls all dependencies on any edit — the most common Dockerfile mistake.

02.dockerignore

Without it, .git, node_modules and .env are sent into the build context and can end up in a layer. Write it before the first build.

03Build stage

Has the compiler, SDK, dev dependencies and source. It produces the build output and is never shipped, so none of it reaches production.

04Runtime stage

A slim base, production dependencies, the built output copied from stage 1, a non-root USER. Everything a running service needs and nothing an attacker would like.

05Base image

Prefer -slim by default and distroless where you can. Alpine's musl libc causes hard-to-diagnose native-module and DNS problems; the saving is rarely worth the afternoon.

06Namespaces

The kernel feature that gives a process its own view of the filesystem, network and process tree. Isolation of what it can see — not a separate kernel.

07cgroups

Limits on how much CPU and memory a process may use. The same mechanism an orchestrator uses to enforce requests and limits on sheet 5.

08Container versus VM

Megabytes and milliseconds instead of gigabytes and tens of seconds, because the kernel is shared. Which is exactly why a kernel bug can cross the line: use a VM, Firecracker or gVisor for untrusted code.

09depends_on and health

Start order is not readiness order. A health check on every stateful service plus condition: service_healthy removes most "Compose is flaky" complaints; the app should still retry.

10Volumes

Named volumes for data — fast everywhere, survive down. Bind mounts for live-reloaded source — slow on macOS and Windows. Mask /app/node_modules so the host's build does not hide the container's.

11Stateless container

State lives in volumes, managed databases and object storage; configuration comes from the environment. One image promoted unchanged, so rollback is starting the previous tag.

12Compose in CI

up -d --wait, run the tests against real services, down -v. The same definition developers use locally, torn down completely afterwards.

13Single host

No rescheduling, no rolling updates, no secret management, no autoscaling. A legitimate trade for small internal workloads, as long as nobody pretends it is high availability.

14Container hardening

Containers run as root by default. Add a USER, drop capabilities, use a read-only filesystem, never bake secrets into layers, never mount the Docker socket, and rebuild regularly to pick up patches.

Sheet 5

The Thermostat

Control loop Covers · Kubernetes · Deployment Strategies

Where the artefact from sheet 4 actually runs. Kubernetes never starts a container because you asked; you declare that three should exist, and a controller notices whenever that is untrue. Self-healing, rolling updates, autoscaling and rescheduling are the same loop pointed at different objects — and most mysterious behaviour is a requests, limits or probe setting that the loop is faithfully obeying.

Step key — the loop and the objects it moves

01Desired state

A declaration — this image, this many replicas, reachable at this address — stored through the API server. With Argo CD or Flux the declaration lives in Git, and the commit history is the deployment history.

02Observe

Kubelets report pod and node health continuously. A node that stops reporting is marked NotReady; nothing waits for a human to notice.

03Compare

Each controller diffs the declaration against reality for its kind of object. Any difference — a lost pod, a new image tag, a changed replica count — is work to do.

04Act

Create or delete pods, start a new ReplicaSet for a rolling update, add nodes when pods are Pending. Then observe again. The loop never finishes.

05Control plane

api-server, etcd, scheduler and controllers. Use a managed one: running etcd yourself is a specialised skill with no product value, and etcd dislikes large objects and churn.

06Pod and Deployment

A pod is one or more containers sharing a network namespace; you rarely create one. A Deployment manages identical pods and their rolling updates. With Service, Ingress, ConfigMap and Secret, it covers most workloads.

07Ingress

One load balancer with host- and path-based routing and TLS termination. Gateway API is the successor and where the ecosystem is moving.

08Service

A stable virtual IP and DNS name in front of a changing set of pods. Pod IPs are ephemeral; only Ready pods are in its endpoints.

09NetworkPolicy

Which pods may talk to which. The default is everything, across namespaces. Adopt default-deny per namespace and allow explicitly — the usual gap between a working cluster and a defensible one.

10Requests and limits

CPU over the limit is throttled in 100 ms periods; memory over the limit is OOMKilled. Set memory request equal to limit, CPU requests honestly, and be wary of tight CPU limits on latency-sensitive services.

11Probes

Startup protects slow boots, readiness controls traffic, liveness controls restarts. Liveness answers "is this process broken?" only; dependency awareness belongs in readiness, carefully.

12Rolling update

New pods are added one at a time and old ones removed only once the new one is Ready. A release whose readiness never passes stops by itself, with the old version still serving.

13Secrets

Base64 in etcd, readable with get secrets. Use an external store, sealed-secrets or SOPS — and better, pod identity (IRSA, Workload Identity) so there is no secret to leak. Never mount service account tokens that are not needed.

14Fit

Transformative for many services, many teams and a platform team; a persistent tax for a small team. The failure mode is rarely the technology — it is an unowned cluster nobody upgrades.

The defaults are permissive

A service account token mounted into every pod, all-to-all pod networking, Secrets readable across a namespace, no resource limits. Assume an application compromise will happen and configure the cluster so it stays inside one namespace: least-privilege RBAC with no cluster-admin for apps or CI, default-deny networking, the restricted Pod Security Standard, and audit logs shipped off-cluster.

Sheet 6

Blueprint and Inventory

Process plant Covers · Terraform · Ansible · CI CD

The ground everything else lands on: networks, databases, clusters, machines. It changes rarely, and it must change through the same reviewed route as code. Terraform's plan is the feature — a diff of infrastructure before it happens — and its state file is both the reason it works and the source of nearly every incident. Ansible's equivalent promise is idempotence: run it twice, change nothing.

Step key — the plant and its vocabulary

01Edit the code

Infrastructure is declared in HCL and lives in Git. OpenTofu is the open-source fork after the 2023 licence change; everything here applies to both.

02fmt and validate

Canonical formatting and syntax and type checking, with no API calls. Cheap, fast, and the first gate on every pull request.

03Plan to a file

plan -out=tfplan with a read-only role shows exactly what would change. Being able to see "this will destroy the database" before it happens is why Terraform won.

04Scan and comment

Checkov or tfsec catch public buckets and open security groups before they exist; the plan is posted as a PR comment so reviewers read the effect, not just the code.

05Review the plan

Read every plan for -/+ before anything else. A long plan hides a replacement easily, and review is where it is cheapest to catch.

06Apply the reviewed plan

CI assumes a scoped per-environment apply role via OIDC, takes the lock and applies the saved file. What was approved is exactly what happens.

07State updated

Written back to a versioned, encrypted bucket, then the lock is released. Versioning is what lets you recover from a corrupted state.

08Code, state, reality

State maps resource addresses to real IDs. Without it Terraform cannot tell "create a new one" from "this already exists". Drift is reality disagreeing with state: codify the change or revert it, deliberately.

09Plan symbols

+ create, ~ update in place, - destroy, -/+ destroy and recreate. A plan on unchanged code should say no changes; anything else is drift worth investigating.

10prevent_destroy

A lifecycle rule that makes apply fail rather than destroy the resource. Put it on databases, state buckets and anything whose replacement would be catastrophic.

11moved blocks

Renaming a resource in code looks like destroy plus create. A moved block (or state mv) tells Terraform it is the same object, and the plan goes empty.

12Remote locked state

Remote, locked, versioned, encrypted, treated as secret — from day one. Local state on a laptop is the beginning of every Terraform horror story: two engineers, two states, one environment.

13Separate states

One state per environment and blast radius, in separate directories with separate backends. Workspaces share configuration and make applying staging's plan to production easy.

14Terraform's job

Anything with a provider and a lifecycle: networks, clusters, databases, DNS, IAM, even GitHub branch protection. Not the inside of servers, and not application rollouts.

15Ansible's job

Agentless configuration over SSH — only Python on the target. Bare metal, on-premises, network devices, self-managed databases, compliance baselines, and building images.

16Idempotence

Modules describe a state ("nginx present"), so a second run changes nothing and reports changed=0. Shell tasks describe actions, so they cannot tell whether anything needed doing.

17Role defaults

defaults/ is low precedence and meant to be overridden; vars/ sits near the top. Putting overridable settings in vars/ causes most "why is my variable ignored" confusion.

18Speed settings

An SSH round trip per task per host dominates everything. pipelining, a higher forks than the default 5, and smart fact gathering with a cache routinely halve playbook time.

19Immutable images

Packer runs the same role to produce a tested image; the launch template changes and the group rolls. Boot-time configuration makes every scale-out depend on a playbook succeeding at the worst moment.

20Control node

Holds SSH access with root escalation to the fleet. Run from CI with a dedicated key, pin Galaxy roles, use Vault and no_log, run --check --diff before production, and log every run.

Creating implies destroying

Terraform credentials are usually the most powerful in the organisation, because a role that can create an environment can delete it. Scope the apply role to what the configuration manages, separate roles per environment so a staging apply cannot reach production, and keep the state bucket in an account the pipeline cannot administer.

Sheet 7

Crossing the River

Decision tree Covers · Deployment Strategies · CI CD

Stops 13 and 14 of sheet 1, and exit B, as a choice. Every strategy is a way of limiting how many users see a bad release and for how long. The numbers that matter are time to detect and time to revert — a plain rolling deployment with good alarms and a one-command rollback beats an elaborate canary pipeline that has no idea what "healthy" looks like.

Step key — the choices and their costs

01Compatibility

In any rolling or canary rollout N and N+1 run at once, so both must work with the same schema, queue message shapes, cache entries and API contracts. Most deployment incidents live in that overlap.

02Recreate

Stop everything old, start everything new. Downtime, and the simplest possible procedure — sometimes acceptable for an internal tool at 3 a.m.

03Instant full rollback

The question that separates blue/green from the rest: must a whole environment revert in one step, rather than instance by instance?

04Blue/green

Two full environments; traffic moves in one switch and the old one stays warm. Double infrastructure during the overlap, a shared database that must serve both, connections to drain — and switch at the load balancer, because DNS TTLs make cutover and rollback take hours.

05Trustworthy metrics

Canary analysis is only as good as the signals it compares. Without reliable error rate, latency and business metrics — and enough traffic — you are deploying slowly and calling it safety.

06Rolling

Replace a few instances at a time, gated by health, with automated rollback on error rate. The default nearly everywhere, and enough for most teams. Keep surge headroom; capacity dips during the roll.

07Canary

A small share of real traffic goes to N+1 first, then 25%, 50%, 100% if healthy. The smallest blast radius, provided the judgement is automated.

08A/B testing

Routes by user attribute to compare behaviour. It answers a product question, not an operational one, and must not be mistaken for a safety mechanism.

09Shadow traffic

Real requests duplicated to N+1 and responses discarded. Tests real load without user impact — and doubles charges and emails unless every side effect is suppressed.

10Canary analysis

Compare N+1 against N over the same window, not against a fixed threshold, and include business metrics. Argo Rollouts and Flagger automate the decision a human watching a dashboard would miss.

11Expand, migrate, contract

Add the new column and write both; backfill and switch reads; stop writing the old; drop it last. Removals lag additions by at least one release, so rolling back one release is always safe.

12The vicious circle

Large rare releases are risky, so teams release less often, which makes each release larger and riskier. The fix is counter-intuitive and the whole argument for CI/CD: smaller, far more often.

13Pipeline order

Cheapest, fastest checks first; parallelise anything independent. Under ten minutes people stay in flow; past twenty they context-switch, batch changes and let reviews go stale.

14Reversibility first

Health checks, a one-action rollback, monitoring and compatible migrations come before automated deployment. Deployment speed is worth nothing without rollback speed.

Cold caches and night deploys

Replacing every instance at once empties every in-process cache and hands the database the full load — the classic "successful" deployment followed by a latency spike. Roll gradually and warm caches before readiness passes. And deploy during the day: the point of small, reversible releases is that the people who can fix a problem are awake when it happens.
