Sheet 1

The Request Line

Transit diagram Covers · Backend Fundamentals · Web Servers · Nginx · Backend Frameworks

One request, one route, eighteen stops. Your business logic is one of them. Six exits end the journey early — three at the edge that save your workers, three in the framework that save your data — and stop 14 is drawn with a loop because a backend spends most of its life waiting, not computing.

Step key — every stop on this sheet, and what it does

01You send

A request arrives from a browser, a mobile app, another service — or a script that has never seen your UI. Everything the client sends is hostile until proven otherwise, including from your own frontend.

02TLS ends

Nginx or a cloud load balancer terminates TLS, so certificates live in one place. Behind it, traffic is plain HTTP over the private network — acceptable only if you still trust that network.

03Location match

The request is matched against server and location blocks. A block that accidentally serves the application directory is a full source-code disclosure.

04Rate limit

limit_req counts requests per client and refuses the excess. The cheapest defence against brute force and scraping — and it only works if the proxy sees the real client IP.

05Proxy cache

If a cacheable response is already stored, Nginx returns it. No worker, no framework, no database query was involved.

06Buffer, pick upstream

Nginx reads the whole request body first, then chooses a healthy upstream by round robin or least connections. The buffering is what stops a slow mobile client holding a worker for seconds.

07A worker

The Gunicorn master owns the listening socket; the kernel hands the connection to one worker process. That worker has its own memory, its own cache and its own database pool.

08Route + middleware

The framework finds the handler for this URL and runs the middleware chain — logging, CORS, compression, a request id. Order matters: middleware registered too late never runs.

09Authentication

Who is this? A token or session is verified and an identity attached to the request. Identity only — it says nothing yet about what they may touch.

10Validation

Is the input well-formed? Body, query and headers become typed objects, or the request is rejected with per-field errors. Validation checks shape, never permission.

11Authorisation

May THIS user do THIS to THIS object? Checking that someone is logged in but not that order 42 is theirs is the single most common serious backend vulnerability.

12Business logic

The rules that make it your product — ideally in a service, not the controller, so it can be tested and reused. About 2 ms of the request's life.

13Data access

Cache first (Redis), then the database through this worker's connection pool. Most backend performance work is here: fewer queries, cached reads, no N+1.

14The database

Where the truth lives. A typical request waits ~40 ms here — which is why async models and pooling matter more than language speed, and why "rewrite it in a faster language" disappoints.

15Serialise

Objects become JSON or HTML. Only declared fields should leave — a response_model, a DTO, an @Exclude — or a column added next year leaks through an endpoint nobody reviewed.

16Errors → status codes

Exceptions are mapped to clean status codes by error middleware, exception filters or @ControllerAdvice. Stack traces and exception details never reach the client.

17Compress, cache

On the way out Nginx applies gzip or brotli and stores the response if it is cacheable — without a line of application code.

18Keep-alive

The response returns to the client and the connection is kept open for reuse, saving the next request its TCP and TLS handshake.

AStatic file

A location /static/ block serves from disk, often 10–100× faster than through a framework. Serving static files through the app while Nginx sits idle is a classic waste.

B429 Too Many Requests

The rate limiter refused. Cheap for you, expensive for an attacker — but useless if X-Forwarded-For is missing and every client appears to have the proxy's IP.

CProxy cache hit

A stored response goes straight back. Stack Overflow served vast traffic from a handful of servers largely because caching removed most database work.

D401 Unauthorized

No valid identity. Raised by an auth dependency, guard, filter chain or middleware before the handler runs.

E422 / 400

Malformed input, returned with per-field errors — 422 from Pydantic or a Laravel Form Request, 400 from Nest pipes and ASP.NET model binding. Rejecting early keeps garbage out of your logic.

F403 Forbidden

Known user, wrong object. A policy, @PreAuthorize or an explicit ownership check in the handler. Frameworks check roles; object ownership is almost always yours to write.

Steps 09 and 11 are different

Authentication is identity; authorisation is permission. A route that checks "is logged in" and then loads /orders/{id} by id alone lets any customer read any order by changing a number. No framework on sheet 6 prevents this by default — every one of them leaves the ownership check to you.

Sheet 2

The Edge

Cutaway section Covers · Web Servers · Nginx

Stops 02 to 06 of sheet 1, opened up. On the left, the eight things Nginx does to every request, in order; on the right, why it can do them for tens of thousands of connections on a few megabytes. The reverse proxy is not an optional speed-up — it is the component that keeps slow clients, bots and TLS handshakes away from the processes that run your code.

Step key — the edge, step by step and panel by panel

01Accept the connection

A worker's event loop registers the new TCP connection and moves on. Nginx holds tens of thousands per worker because none of them gets a thread.

02Terminate TLS

Decrypt once, at the edge, with certificates in one place. TLS is Nginx's main CPU cost, and it is hardware-accelerated. Remember to reload after a certificate renewal.

03Match a location

server_name selects the site, location blocks select the behaviour. Declarative and fast — and very hard to test once it grows conditionals and rewrites.

04Static file

Anything under /static/ is read from disk with long expires headers. Often 10–100× faster than the same file through a framework.

05Proxy cache

Stored responses are returned without contacting an upstream. Rate-limit checks come before it, so a cached endpoint still cannot be hammered.

06Pick an upstream

Choose a healthy application server from the upstream block by round robin or least connections, and remove failing backends from rotation.

07Buffer, compress, add headers

The full request is buffered before forwarding; the response is compressed with gzip or brotli, given security headers, and cached if allowed.

08Return, keep alive

The response goes back and the connection is kept open for reuse. Configuration reloads happen without dropping any of these connections.

AC10K

The classic Apache model gave each connection a process or thread: 10,000 connections, 10,000 threads, gigabytes of stacks. An event loop per worker handles the same load in megabytes.

BX-Forwarded-For / -Proto

Not optional. Without them the application sees the proxy as every client and believes it is on HTTP — breaking logging, rate limiting, redirects and cookie security.

CBuffering

The proxy absorbs slow uploads so a worker only sees a complete request. It is the standard defence against Slowloris and the reason an app server must never face clients directly.

DTLS termination

At a cloud load balancer, at Nginx, or end to end. The first two mean plaintext inside your network, which zero-trust architecture no longer accepts by default.

EServer interface

WSGI, ASGI, Servlet, Kestrel's pipeline, FastCGI: the contract by which an application server hands a request to your framework. It decides which servers can run which apps.

FHardening

Body size limit, rate limiting, version hidden, security headers set centrally, X-Forwarded-For overwritten rather than appended. Internet-facing C code: keep it patched.

Two timeouts that must agree

proxy_read_timeout 30s in Nginx and --timeout in Gunicorn are the same deadline seen from two sides. When they disagree, one kills the request while the other is still waiting, and the client sees a 502 that neither log explains. Decide which is longer on purpose — sheet 7 draws the whole ladder.

Sheet 3

The Worker Floor

Process plant Covers · Runtime Explained · Gunicorn · Uvicorn

Stop 07 of sheet 1, drawn as a plant: one master, N identical workers, and the shared stores they all lean on. How many workers you run is not a tuning preference — it follows from the runtime's concurrency model, and it is almost always capped by memory and database connections before it is capped by CPU.

Step key — the parts of the plant

01Reverse proxy

Nginx hands over complete, buffered requests. Gunicorn has no TLS, no static files and weak protection against slow clients, so it is never exposed directly.

02Gunicorn master

A pre-fork process manager. It binds the listening socket, forks workers and supervises them. It never handles a request itself, and systemd, Docker or Kubernetes keeps it alive.

03Worker process

A full copy of the interpreter, the app and every library, with its own memory and its own database pool. Worker classes: sync, gthread, gevent, or UvicornWorker for ASGI apps.

04Crash recovery

When a worker dies, the master forks a replacement. One bad request kills one worker, not the service.

05--timeout

A worker stuck longer than the timeout is killed and replaced. Blunt — the worker dies, not just the request — but without it one hung request holds a worker forever.

06SIGHUP

Graceful reload: workers are replaced one at a time, so a single machine can deploy with no dropped connections.

07--max-requests

Recycle each worker after N requests, with jitter so they do not all restart together. Caps the damage from slow memory leaks.

08Shared state

Workers share nothing, so sessions, caches and counters that must be consistent live in Redis or the database. Keeping app servers stateless is what makes scaling and rolling deploys easy.

09Connection pooler

PgBouncer multiplexes many client connections onto fewer real database connections — the fix once workers × pool × replicas outgrows the database.

10max_connections

PostgreSQL's default is 100. It is a fleet-wide budget, and it is usually the first hard wall a horizontally scaled backend hits.

11Process-based

One request per process at a time; parallelism comes only from more processes. CPython and PHP-FPM work this way, which is why they multiply memory.

12Thread-based

A pool of real threads inside one process, parallel across all cores. The JVM and .NET run as a single process with a large heap — set -Xmx explicitly in containers.

13Event loop

One thread juggling thousands of waits: excellent for I/O, useless for computation. Node, asyncio and Uvicorn; scale across cores with one loop per process.

14Memory per worker

The usual binding constraint. Measure one worker under load, multiply by the count, and compare with the limit before the kernel does it for you with exit code 137.

15Total connections

Pools are sized per worker but consumed fleet-wide. Doubling replicas doubles connections — which is why the outage arrives during the scale-out meant to prevent one.

16Worker count

2 × cores + 1 for sync Python, cores for async Python and Node, one process for JVM, .NET and Go. Derived from the concurrency model, then trimmed to fit memory.

Sheet 4

The Event Loop

Closed circuit Covers · Uvicorn · FastAPI · Runtime Explained · Express.js · ASP.NET Core

Stops 13 and 14 of sheet 1, from inside one worker. A request's life is six steps around a loop, and the loop runs thousands of these circuits interleaved on a single thread. It works only because every request gives the thread back at each await — one call that refuses to yield freezes every circuit in the worker at once.

Step key — the lap, and what breaks it

01Request arrives

The process manager has already picked a worker; inside it, Uvicorn's event loop receives the request. Nothing is waiting on a thread yet.

02Coroutine scheduled

The loop assigns the request to a coroutine. FastAPI routes it, resolves dependencies such as the DB session and current user, and validates the body with Pydantic.

03await

At await db.fetch() the coroutine suspends. Its pending state costs a few kilobytes — versus megabytes for a thread — which is how one worker holds thousands.

04The loop serves others

While the database works, the loop runs every other ready coroutine. A 50 ms query becomes 50 ms of serving others instead of 50 ms blocked.

05Resume

The database answers, an I/O readiness event fires, and the coroutine continues exactly where it stopped, on the same thread.

06Response written

The result is filtered through response_model, serialised and sent. The loop immediately picks up the next ready coroutine.

07Concurrency, measured

WSGI occupies a worker for the whole request: concurrency equals worker count. ASGI frees the worker during I/O: thousands of concurrent requests per worker, still one core each.

08The blocking call

time.sleep, requests, a synchronous driver like psycopg2 — any call that never yields stalls the loop and every request on it. The single mistake that removes the reason for running Uvicorn.

09Escape hatches

Declare the handler as plain def and FastAPI dispatches it to a thread pool; wrap a sync-only library in run_in_executor; move CPU work to a background worker.

10Node's loop

Express and NestJS sit on the same single-threaded model. NestJS's structure does not change it: a blocking handler stalls every concurrent request, and cores are used via cluster or PM2.

11Express 4 rejections

An unhandled promise rejection in an async handler never reaches error middleware; the client simply times out. Wrap every async handler, or move to Express 5.

12Sync-over-async in .NET

ASP.NET Core's await returns the thread to the pool during I/O. .Result and .Wait() undo that: a pool thread blocks waiting on work that needs a pool thread.

13Async end to end

Every I/O library in the path must be async: asyncpg or psycopg 3, httpx, redis.asyncio, SQLAlchemy's async engine. Do not mix sync and async sessions in one codebase.

14What only ASGI can do

WebSockets, server-sent events and long-lived streams. Django gains WebSockets by running under Uvicorn with Channels; WSGI cannot express them at all.

Sheet 5

The Framework Choice

Decision tree Covers · Backend Frameworks · FastAPI · Django · Express.js · NestJS · Laravel · Spring Boot · ASP.NET Core

The decision that fixes what stops 08 to 16 look like, made before any request exists. Seven frameworks, five questions, asked in a deliberate order. The team's existing knowledge usually settles it at question one, and benchmarks come last — because a request spending 40 ms in the database does not care whether the framework takes 2 ms or 1.

Step key — the questions and the leaves

01Team knowledge

What the team already knows usually decides the framework outright. Productivity and correct defaults come from familiarity, not from a feature matrix.

02Ecosystem

AI and ML point to Python because the models live there. Enterprise integration points to Java or .NET. The libraries you need outrank the syntax you prefer.

03Workload shape

I/O-bound services gain from async runtimes; CPU-bound ones need real threads or processes. Sheet 4 shows why this changes more than raw speed.

04Lifespan and maintainers

A three-endpoint service and a decade-long system with thirty developers need different amounts of structure. Heavy frameworks on tiny services are ceremony; minimal ones on huge teams drift.

05Benchmarks

The last question, not the first. The database owns the latency of most requests, so a framework twice as fast rarely moves the total by more than a few percent.

06Django

Batteries included: ORM, migrations, auth, templates, and an admin generated from your models. Its performance ceiling is set by ORM query patterns — N+1 — far more than by the framework.

07FastAPI

Type hints drive validation, serialisation and OpenAPI docs from one declaration. The best Python API layer, and the default for ML services — provided nobody blocks the loop.

08Express / Fastify

Routing and an ordered middleware chain, nothing else. Its minimalism made it universal; for new Node APIs, Fastify adds schema validation, better async handling and speed.

09NestJS

Modules, providers, dependency injection, guards and pipes on top of Express or Fastify, so any developer opening any module finds the same layout. Overhead for small services.

10Laravel

Eloquent, queues, scheduler, mail, auth and Blade in one PHP framework with excellent ergonomics. Each request boots fresh — no leaks, but a poor fit for persistent connections.

11Spring Boot

Auto-configuration over the Spring ecosystem on the JVM: very high throughput once warm, the deepest enterprise ecosystem — and a 1–3 s start with a 200–500 MB baseline.

12ASP.NET Core

Spring Boot's sibling in C#: built-in DI, middleware pipeline, Kestrel, and async designed into the language. ~100 ms startup, ~10 ms with Native AOT.

AMinimal vs batteries-included

The most useful comparison axis is not language but how much the framework decides. Minimal trades speed-to-first-feature for freedom; batteries-included trades freedom for enforced consistency.

BThe 42 ms request

2 ms of framework and code, 40 ms waiting on I/O. Halving the first saves one millisecond. This is why "we rewrote it in a faster framework" so often disappoints.

CWhat frameworks leave out

Architecture, domain modelling, authorisation logic and operational readiness. Keep business rules in services, not controllers — the tutorial layout is where regret starts.

Sheet 6

Seven Pipelines

Parallel sections Covers · FastAPI · Express.js · NestJS · Spring Boot · Django · Laravel · ASP.NET Core

The framework stretch of sheet 1 — stops 07 to 16 — cut through seven frameworks side by side. Every column runs the same anatomy in the same order; only the names change. Read across row 06 and the columns stop differing: no framework on this sheet checks that the object belongs to the caller, and each one has a signature trap that comes from switching a safe default off.

Step key — the rows, then the columns

01Server and runtime

What actually executes the framework: an event loop (Uvicorn, Node), a pre-forked process (Gunicorn, PHP-FPM) or a thread pool (Tomcat, Kestrel). It fixes the concurrency model from sheet 3.

02Startup and memory

Matters for autoscaling and serverless. Spring Boot's 1–3 s cold start disqualifies it for short-lived work without a native image; Laravel pays a boot on every request.

03Middleware

Cross-cutting concerns in registration order — logging, CORS, sessions, CSRF, HSTS. In Express everything is middleware, including routes, so order is behaviour.

04Authentication

Establish identity and attach it to the request, or return 401. A dependency in FastAPI, a guard in NestJS, a filter chain in Spring, middleware elsewhere.

05Validation

Turn untyped input into typed objects or reject it with 400 or 422. Built in almost everywhere except Express. Apply it globally and strip unexpected properties.

06Authorisation

Object-level permission. Laravel's Policies and Spring's @PreAuthorize give it a home; everywhere, the ownership check itself is your code, and it is the most commonly missing one.

07Handler

Controller, view, route handler or minimal API endpoint. It should translate HTTP into a call to a service and back — nothing more.

08Data access

ORM or driver. In Django, Laravel, JPA and EF Core the dominant performance risk is N+1 queries, fixed by eager loading, not by tuning the framework.

09What leaves

Declared output only: response_model, @Exclude, DTOs, JSON resources. Returning an ORM entity serialises every column, including ones added long after the endpoint was reviewed.

10Error mapping

Exceptions become status codes in one place. Debug pages and stack traces — DEBUG=True, APP_DEBUG=true, the developer exception page — expose settings and secrets.

11FastAPI

Starlette + Pydantic on ASGI. One declaration yields validation, serialisation and OpenAPI docs at /docs — disable it in production if the API is not public.

12Express.js

Almost no security defaults: add helmet, a rate limiter and a body size limit such as express.json({ limit: "100kb" }), and wrap async handlers on v4.

13NestJS

Middleware → guards → interceptors → pipes → controller → service → repository → exception filters. The shape is enforced; the ownership check inside the guard is not.

14Spring Boot

Security filter chain, controllers, @Transactional services, JPA repositories, @ControllerAdvice. Restrict Actuator, set -Xmx, and never benchmark without warm-up.

15Django

The best security defaults in the section — CSRF, auto-escaping, parameterised ORM — so incidents come from turning them off. Run manage.py check --deploy before going live.

16Laravel

Form Requests validate, Policies authorise, Eloquent loads with with(). Keep .env out of the repository and the web root, and define $fillable.

17ASP.NET Core

Kestrel, a middleware pipeline where authentication must precede authorisation, DI-resolved controllers and EF Core. Bind requests to DTOs, never to entities.

Sheet 7

The Failure Ledger

Hazard map Covers · Backend Fundamentals · Runtime Explained · Backend Frameworks · Django · Laravel · Spring Boot · ASP.NET Core · Nginx

What runs under every other sheet: releases, restarts, timeouts and defaults. Almost nothing here is exotic — a signal nobody handled, two timeouts nobody compared, a debug flag nobody reset. Backends rarely fail because a framework was weak; they fail because a safe behaviour was available and somebody switched it off, or never switched it on.

Step key — the ledger

01Deploy starts

A new version rolls out and old instances must stop. How they stop decides whether users notice.

02SIGTERM

The orchestrator's polite request to shut down. One signal handler is the difference between a clean release and a burst of errors.

03Stop accepting

Close the listener and fail readiness so the load balancer stops routing new requests here.

04Finish in-flight

Let running requests complete inside the grace period. This is the step that makes a rolling deploy invisible.

05Close the pool

Return database connections cleanly instead of leaving the server to time them out against max_connections.

06Exit

A clean exit before the deadline. Nothing was dropped, nothing retried.

07SIGKILL

The grace period expired on a process that ignored SIGTERM. It is killed immediately, with no chance to finish anything.

08Mysterious 502s

In-flight requests die mid-response on every deploy. One of the most common causes of intermittent release-time errors — and fixed by handling one signal.

09Cold start

Go ~1 ms, Node ~50 ms, Python ~50 ms plus imports, .NET ~100 ms (~10 ms AOT), JVM 1–3 s (~50 ms GraalVM native). It governs serverless fitness and how fast autoscaling can respond.

10Timeout ladder

Client, proxy, app server and outbound calls each have a deadline. Mismatched, they produce 502s nobody can explain; missing on outbound calls, one slow dependency hangs everything.

11SQL injection

ORMs parameterise queries by default. Raw SQL built with string formatting — or DB::raw() with user input — walks straight past that protection.

12XSS

Django templates and Blade escape output automatically. |safe and {!! !!} turn it off for exactly the content that most needs it.

13CSRF

Token middleware protects form posts in Django and Laravel. csrf_exempt added while debugging and never removed is a classic. Express ships none at all.

14Debug mode

DEBUG = True or APP_DEBUG=true in production exposes settings, environment variables and credentials on any error page. It has caused real breaches, repeatedly.

15Leaked fields

Returning an ORM entity serialises every attribute, including a password hash added next quarter. Declare output with response_model, DTOs or @Exclude.

16Mass assignment

Binding a request body straight to a model lets a caller set is_admin. Define $fillable, use whitelist: true, bind to DTOs.

17Exposed internals

Spring's /actuator/env can leak configuration and secrets; the Django admin grants direct database access; FastAPI's /docs maps an internal API. Restrict all three.

18Fingerprinting

server_tokens off in Nginx and app.disable('x-powered-by') in Express cost nothing and stop advertising exact versions to scanners.

19Stateless servers

Push sessions and shared state into Redis or a token. This one decision is what makes horizontal scaling, rolling deploys and crash recovery straightforward.

20Request ids

A request id attached at the edge and logged by every layer turns "something failed around 14:02" into one traceable request.

21Secrets

The backend exists partly to hold secrets a client never may. Keys in source control, or a .env readable from the web root, undo that purpose entirely.

The closing loop

Sheet 5 chose a framework; sheet 6 showed its defaults; this sheet listed how those defaults get switched off. Sheets 2 to 4 sized the processes that run it, and sheet 1 is what a user experiences when all of that holds. Every incident on this atlas starts as a line on this sheet — which is why the cheapest review you can run is a search for the strings in its ledger.
