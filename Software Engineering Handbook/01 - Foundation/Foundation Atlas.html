Atlas of the Foundation

Nine lessons, one argument: software is a sequence of decisions, and most of the craft is knowing which ones are expensive. Sheet 4 is the lap every change takes, from a need to running code and back again; every other sheet is either a decision made on that lap or a discipline that keeps the lap honest. None of it is about a specific technology — which is exactly why none of it goes out of date.

Sheet 1

The Load-Bearing Walls

Cutaway section Covers · What Is Software Architecture

Architecture is not a diagram, a folder structure or a framework — those are its outputs. It is the set of decisions behind them, and one test sorts every decision you make. If changing it later would be painful, slow or risky, it is a load-bearing wall; everything else is paint.

Step key — what architecture is made of

01Components

The parts that exist: frontend, API, worker, cache, database. Listing them is the easy part of architecture and the part everyone already does.

02Responsibilities

What each part is allowed to know and do. A component with no clear responsibility becomes the place every awkward piece of logic ends up.

03Communication

How parts talk — HTTP, a queue, a direct call, an event. The choice fixes latency, coupling and what happens when the other side is down.

04Data ownership

Who owns which data and who may write it. Two writers for the same data is how two systems end up disagreeing about the truth.

05Boundaries

What is inside a component and what is forbidden to cross. A good boundary keeps a change inside one box; a bad one lets it ripple out.

06Cross-cutting rules

Auth, logging, error handling and validation, applied the same way everywhere. Decided once, or re-decided badly in every module.

07The defining test

Is this decision painful, slow or risky to change later? Naming style: minutes, not architecture. Database model, service split, auth, public API: months, or every client broken — architecture.

08Quality attributes

Performance, scalability, availability, security, maintainability, cost. Architecture is chosen mostly for these, and you cannot maximise all six — so "what is the best architecture?" is answered with "best at which?"

09Levels

System (services, databases, queues), application (one service's layers) and code (modules and classes). Bad code architecture is annoying; bad system architecture is expensive.

10Position

Requirements and constraints above, technology and code below. Choosing React or PostgreSQL before this step is choosing answers before the question.

11The decay line

Without explicit architecture every local decision is reasonable alone, and together they make everything depend on everything. One change breaks three unrelated things, nobody dares touch it, and the ending is a rewrite.

12Who may call whom

The arrows, and the arrows you forbid. Netflix split into hundreds of services so "recommendations" failing never stops "play video" — an architectural decision, not a coding one.

Netflix's architecture solves Netflix's problems

Instagram ran an enormous user base on plain Django and PostgreSQL for years, because its bottleneck was images, not application logic. Copying a big company's design imports its costs without its constraints. Make the expensive decisions consciously, write down why, keep them as few as possible — and remember architecture evolves, or it dies.

Sheet 2

The Architect's Instruments

Instrument panel Covers · How Software Architects Think

A developer starts from the feature. An architect starts from what is not allowed to change, then reads a handful of gauges before drawing a single box. They think in constraints, consequences and failure — and the goal is never to be right about the future, only to be cheap to be wrong.

Step key — the gauges, and what each one reads

01Constraints first

Budget, team size, deadline, traffic, compliance, latency — what is not allowed to change. Put them on the table and the realistic options usually drop to two.

02And then what?

Push each proposal forward in time until it breaks. Disk uploads meet a second server; a cache meets changing data; a direct payment call meets a 10-minute outage.

03Failure first

The happy path is the easy part. Attention goes to the unhappy ones, because a system without answers to them has unknown behaviour, not simple behaviour.

04Down

The dependency is unavailable. The easier case: it fails fast, callers get an error, and you can decide what the user sees instead.

05Slow

The dependency answers — eventually. Slow is worse than down, because every caller waits with it and the delay spreads upstream until the whole system stalls.

06Twice

The same message arrives again: a retry, a double-click, a queue redelivery. If processing it twice charges twice, the design is not finished.

07Halfway

The process dies mid-operation. What state is left behind, and does a restart repair it or compound it?

08Hostile

The input was written by an attacker. Assume it at every boundary, rather than discovering it in an incident.

09Numbers of the machine

Cache ~1 ns, RAM ~100 ns, SSD ~100 µs, same-DC call ~0.5 ms, query 1–10 ms, internet 50–150 ms. A network hop costs about a million memory reads.

10Quantify

"Fast", "a lot of users" and "scalable" are not engineering terms. Peak requests per second, data volume in a year, acceptable latency, downtime and staleness are.

11Reversible or not

Easy to undo: decide fast and move on. Hard to undo — data model, service boundaries, auth, public API, SQL versus documents: slow down, compare, write an ADR.

12The whole system

A change that makes one service 20% faster and three others harder to change is a loss. The question is never "where does this function go?" but "who is allowed to know this?"

13Optionality

Nobody knows what the product needs in two years, so do not predict it. Keep boundaries clean, avoid cheap-to-avoid vendor coupling, and decide at the last responsible moment.

Refusing to decide is also a decision

Endless analysis is a choice, and usually a bad one. So is treating every decision as equally important — the big ones get the same ten minutes as the small ones. And architecture designed alone will not be implemented: if the team does not understand the reasoning, the code will quietly follow a different design.

Sheet 3

The Decision Tree

Decision tree Covers · Engineering Decision Making · Problem First Technology Second

Technology is an answer; if you cannot state the question, you cannot evaluate the answer. This sheet is the route from a vague symptom to a decision you can still defend when it turns out badly. Two exits let most decisions finish early — and the step nearly everyone skips, writing down why, is the only one that makes the decision revisitable.

Step key — every step on the decision line

01The symptom

"The app is slow", "we need microservices". A feeling or a solution, never yet a problem. Nothing can be evaluated at this station.

02State the problem

One sentence, not the solution, with a number in it if possible: "the same query runs 10,000 times a minute". Found by measuring and locating, not by guessing.

03What if we do nothing?

If the honest answer is "nothing much", stop. Doing nothing is a real option with a real gain — no new complexity — and it is often correct.

04Name the family

Business problem → engineering problem → family of solutions → specific technology. Skipping the middle two is how projects acquire technology nobody can justify.

05List the constraints

Budget, team, deadline, traffic, existing skills. They delete options before any comparison begins, and they are what makes "Redis, because we already run it" a real reason.

06Which door?

Two-way doors — a library, a convention, a CI tool — can be walked back through. One-way doors — data model, service boundaries, auth, public API — cannot.

07Generate 2–4 options

Always including "do nothing" and the simplest thing that solves it. One option compared against nothing is not a decision; it is a preference.

08Fix criteria first

Fit to constraints, team knowledge, operational cost, failure behaviour, cost to reverse, licence and vendor risk — chosen before looking, or you will pick criteria that favour your favourite.

09Check for bias

Résumé-driven, novelty, sunk cost, authority, availability. If you cannot argue the rejected option convincingly, you have not understood it well enough to reject it.

10Decide

At the last responsible moment: too early is deciding with the least information you will ever have, too late blocks the team.

11Write down why

The entire value of the process. A decision without a written reason cannot be re-evaluated later — it can only be inherited and resented.

12Review trigger

"Revisit if traffic exceeds X." Without one, an outgrown decision stays forever, because nobody knows the condition under which it was right.

AThe do-nothing exit

The cheapest outcome on the sheet. Every component you do not add is one you never deploy, monitor, back up, secure, upgrade, document or explain to a new hire.

BThe two-way shortcut

Reversible decisions skip the ceremony and are made in an hour. Treating one like a one-way door is how teams spend three weeks choosing a logging library.

Prescribing before diagnosis is malpractice

"We should use microservices" is not a plan — it is a solution looking for a problem, and if the real problem is one slow query, it makes things worse. Instagram stayed on plain Django and PostgreSQL because its bottleneck was media delivery; Stack Overflow ran on a handful of servers with heavy caching because its load was reads. Learn new technology in a side project, where being wrong costs nothing.

Sheet 4

The Lifecycle Circuit

Closed circuit Covers · Software Development Lifecycle · Documentation Driven Development

Seven stations, and an arrow from the last back to the first. Every team runs this circuit whether it names it or not, and each station owes a document written before the work, not after. Skipping a station does not remove its work — it moves that work to a later station, where it costs ten times as much.

Step key — the stations and the paperwork

01Requirements

What problem, for whom, and how will we know it worked? Owes a problem statement and a README. Starting to code before this is clear is the most expensive mistake in software.

02Design

Architecture, data model, interfaces. Owes an ADR, an architecture diagram and the API contract — the station where mistakes still cost about five times the minimum.

03Implementation

Writing the code, with inline comments that explain why the strange line exists. The code already says what.

04Testing

Does it do what we said, and what happens when it does not? Something written alongside the code, not a phase that starts when coding ends.

05Deployment

Getting to production safely. An automated, repeatable process rather than an event — and the runbook is written before launch, not during the first outage.

06Operation

Monitoring, alerting, incidents, backups. The station most often forgotten, which produces software nobody can monitor, back up or debug.

07Maintenance

Bug fixes, dependency updates, improvements — and updating the documents where reality disagreed. Then back to station 01.

08The cost curve

Requirements 1×, design ~5×, implementation ~10×, testing ~20×, production ~100×. The entire economic argument for design and code review.

09Waterfall and agile

Waterfall is one lap with feedback at the end; right for regulated or hardware-bound work. Agile is many thin laps — which means designing the architecture early and the details continuously, not skipping design.

10Documentation first

README at project start, ADR before an irreversible decision, API contract before the endpoint, diagram before a new component, runbook before production, changelog at release.

11API-first

Write the contract, agree it, build both sides in parallel against it, integrate without surprises. OpenAPI makes the document checkable by machine.

12Worth writing

Why, contracts, constraints and assumptions, failure behaviour, rejected alternatives. The knowledge that exists only in people's heads — and leaves the company with them.

13Documentation that rots

Comments restating the code, tutorials for a UI that changes every sprint, generated docs nobody maintains, wikis nobody opens. Anything duplicating the code line by line drifts within weeks.

Documentation written after shipping is a photograph

By then the reasoning is already forgotten, and what gets written describes what happened rather than what was intended. Amazon replaced slide decks with six-page narratives for exactly this reason: a coherent paragraph exposes weak reasoning that bullet points hide. If you cannot explain the design clearly in writing, you do not yet understand it well enough to build it.

Sheet 5

The Verification Line

Process plant Covers · AI Driven Development Workflow · Documentation Driven Development

For fifty years typing code was the slow part, so processes were built to make typing faster. That constraint is largely gone; deciding what to build and being accountable for whether it is correct are not. AI removes the cost of writing code, not the cost of being wrong — so the time it saves belongs at the two ends of this line.

Step key — the line, stage by stage

01Describe, in writing

The problem, the constraints and the acceptance criteria, before any prompt for code. Vague requests produce vague systems, at machine speed.

02Ask for the design

Not the code. The single step that separates useful AI work from expensive mess: it makes the model a thinking partner rather than a fast intern with no context.

03Challenge it

"What breaks?", "what did you assume?", "what is the simpler option?" — the questions from sheet 2, asked of a proposal that sounds certain whether it is right or not.

04Generate in small pieces

Code sized to be reviewed. Five hundred lines arrive in seconds; the review of them does not get faster because they arrived quickly.

05Read every line

If you cannot explain it, do not merge it. Reading code fast and critically is now one of the most valuable skills an engineer has.

06Run it, test it

Especially the failure paths. The engineer decides what "correct" means; generated tests only check what the generator thought you meant.

07Record the reasoning

An ADR or a commit message that says why. Tomorrow it is documentation; next month it is the context that makes the next AI session useful.

08The verification problem

Generating 500 lines takes seconds, verifying them takes as long as ever. Defend with small reviewed changes, understood tests, static analysis, type checking and security review.

09Strengths and limits

Good at boilerplate, explanation, first drafts and cheap exploration. Unreliable on your constraints, long-lived architecture, security, recent APIs, and knowing you do not need the thing at all.

10Beside, not instead

AI clarifies requirements, proposes designs, generates code, drafts tests, helps debug. The engineer decides, reviews, defines correctness, and is accountable in operation.

11The moved bottleneck

Design to code became fast. Idea to design is still slow, and generation to verified code is now slow — so value concentrates in precise definition and rigorous verification.

12Context

"Add caching" gets a generic answer; "~2000 identical queries a minute, hourly changes, Redis already running, 5 minutes stale is fine" gets real options. Written architecture is that context.

Never let AI make the architectural decision

It does not know your traffic, budget, team or what broke last month, and it will not tell you when the honest answer is "you do not need this". Ask it for options; decide with your constraints; skip neither the security review for code that "looks professional" nor the docs check on confident claims about recent library versions.

Sheet 6

The Price of Principles

Ledger plate Covers · Architecture Principles

Principles are defaults, not laws: they let a team make consistent decisions without re-arguing every choice from first principles. Each one is bought at a price, and every one can be broken. Breaking one should be a conscious decision with a reason attached — never an accident, and never a matter of morality.

Step key — the eleven defaults

01Separation of concerns

Each part has one reason to exist: the controller knows HTTP, the service knows the domain, the repository knows storage. Bought: independent change. Paid: more files and indirection.

02Single source of truth

Every piece of data has exactly one authoritative home; copies must be clearly derived and rebuildable. Reconciling two owners afterwards is among the most expensive work there is.

03Loose coupling, high cohesion

Coupling is how much one component must know about another — less is better. Cohesion is how strongly the insides of a component belong together — more is better.

04Explicit over implicit

Magic saves typing and costs debugging. Invisible auto-wiring and configuration from three places with unclear precedence are quick to write and painful to diagnose.

05DRY, carefully

Applies to knowledge, not text. Code that looks identical but changes for different reasons stays separate — premature abstraction is costlier than duplication.

06Fail fast and loudly

Validate at the boundary and reject immediately with a clear error. A silently accepted bad value corrupts data later, somewhere with no visible connection to the cause.

07Design for failure

Every dependency will be unavailable or slow at some point. Every remote call gets a timeout, a defined retry policy and defined behaviour when it finally fails.

08Statelessness

A server with no per-user state in memory lets any server handle any request, making horizontal scaling and restarts simple. State goes to Redis, the database, or the token.

09Idempotency

Applying an operation twice has the same effect as applying it once. Networks retry, users double-click and queues redeliver, so repetition is a certainty, not an edge case.

10Least privilege

Every component, service and user gets the minimum access its job needs. A service that only reads should not hold write credentials.

11KISS and YAGNI

Do not build for an imagined requirement: the cost is paid now and with certainty, the benefit is speculative. Complexity is a permanent tax on every future change.

Principles are trade-offs, not morality

The common failures come in pairs: applying every principle everywhere, or ignoring them all; DRY-ing code that is only accidentally similar; building abstractions for flexibility nobody asked for. Check each design choice against the ledger, note which principle it breaks and why — and the result is either a consistent system or a documented, deliberate exception.

Sheet 7

The Engineer's Route

Transit diagram Covers · Software Engineering Mindset

Programming is one stop on this line — the one where it works on this machine, today. Engineering is the whole route, because the job is not writing code that works but being able to explain why it will keep working. "It works on my machine" is the boundary between the two, and everything to the right of it is still yours.

Step key — every stop on the engineer's route

01Understand

The problem, and constraints you may not like. Complex solutions are usually a sign the problem is not yet understood.

02Design

Anyone can build something complicated. The simple version needs enough understanding to know what can be left out — it arrives after understanding, not before.

03Write the code

It runs, on this machine, today. Programming is a part of engineering the way laying bricks is part of building a house.

04Test

Does it run under load, under failure, and under new people? The first station past "it works on my machine".

05Deploy

How it ships and how it rolls back, owned by the person who wrote the change rather than handed over the wall.

06Monitor

Would anyone be able to tell if it stopped working? Caring about that question is the practical definition of ownership.

07The next person

Has none of your context, and is very often you. Clear names, small functions and a comment explaining why the strange line exists let a system survive its authors.

08One layer below

Most hard bugs are explained a level down: a slow endpoint is a missing index, a leak an unbounded cache, a random failure a race. Know enough of each layer to pick which to inspect.

D1–D5Debugging method

Reproduce reliably; read the whole error and stack trace; form one hypothesis; test it by changing one thing; if wrong, return to the hypothesis with new information. A method, not a talent.

M1–M4Measure first

Measure with a profiler, timing, logs or EXPLAIN; find the real bottleneck, usually one query or one N+1 loop; fix only that; measure again. Performance intuition is reliably wrong.

09Programming vs engineering

Make it work versus make it keep working; this machine today versus many machines for years; code versus code, tests, docs, deployment and monitoring.

10Read more than you write

You will read far more code than you write, so reading is the higher-leverage skill — and it is trainable on any small open-source project.

11Honesty about knowledge

"I don't know, I'll check" costs three seconds; a confident guess costs someone a day. Pretending to know is a common mistake with a compounding price.

12The slow layer

HTTP, TCP, relational databases, caching, queues and operating systems have been the same for decades while frameworks come and go. Learning there compounds; framework knowledge depreciates.

The whole atlas, in one sentence

Engineering is accountability for the whole life of the system, not authorship of the code that started it. Every earlier sheet — the expensive decisions on sheet 1, the gauges on sheet 2, the written reasons on sheet 3, the lap on sheet 4, the verification on sheet 5, the priced defaults on sheet 6 — is a way of taking that accountability seriously when other people depend on the result.
