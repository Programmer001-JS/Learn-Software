Atlas of a Personal Knowledge Base

Four files the handbook cannot write for you: what you do not understand yet, what you might build, what you learned the hard way, and what your systems actually look like. Sheet 1 is the route a single snag travels, from the moment you notice it to a note in the handbook; sheets 2 to 5 open up one file each. None of this is storage — every file exists to be re-read, pruned and promoted, and a file that is only ever appended to has stopped working.

Sheet 1

The Capture Line

Transit diagram Covers · Questions · Ideas · Technology Notes · Diagrams

Four files drawn as four lines. Each station is a section of its file, and every line runs left to right through the same four zones: capture, review, record, promote. Every line has a station where material is deliberately deleted or rejected, and every line ends at the same bar — nothing in this folder is meant to stay in it forever.

Step key — every station on this sheet, and what it does

01Notice it

Write the question the moment you notice it, even badly phrased. A rough question captured is worth ten good ones forgotten; you can sharpen it later, you cannot recover it.

02Phrase it precisely

"I don't really get databases" is unanswerable and demoralising. "Why does an index on a foreign key sometimes make writes slower?" is a twenty-minute answer. The phrasing is most of the work.

03Blocking or background?

Blocking means today's work cannot finish without it: answer now. Background means you would understand your systems better if you knew: answer deliberately, one a week.

04Answer in your own words

Not a pasted quotation. If you cannot compress the answer into two sentences, you found it without understanding it — which is a different question, and goes back to 02.

05The Answered record

ANSWERED, ANSWER, SOURCE, LINK. The Answered section is evidence of what you have learned, and it is worth re-reading.

06Thought I understood

A table of I believed / Actually / Found out when. A corrected misunderstanding outranks a new fact, because the wrong belief was already shaping decisions.

07A handbook note

The review asks which answered question deserves a handbook note. When one does, update the note and fill in the LINK field so the trail runs both ways.

08Capture

Any idea, one line, unjudged, newest at the top, no structure. Written down, it stops interrupting you at work and returning at 2 a.m.

09The monthly read

Read the list once a month and delete freely. An idea you have not wanted to start in three months is not one you want — deleting it is information, not failure.

10Worth a second look

Promote at most one or two per review. Each gets three lines: why it keeps coming back, the smallest version, what would make it worth it. Sheet 3.

11A real task

Anything you actually intend to do moves out of this file into a task built from the Task Template, with acceptance criteria.

12Started

Ideas you acted on, with outcome and verdict. Keep the failures — they are the more useful half.

13Deliberately rejected

An idea you decided against, with the reason and the date. This section exists to stop you re-litigating the same idea every year.

14Handbook fixes

"Improvements to this handbook": notes to write, links to add, sections that turned out wrong. Kept apart from product ideas, and usually resolved with a link rather than a new note.

15Write it the same day

The detail that makes a note useful — the exact error string, the wrong first assumption, the search that finally worked — is the detail you forget by tomorrow.

16The five-line entry

DATE, CONTEXT, SYMPTOM, CAUSE, FIX, LESSON. Often five lines is the whole note. Sheet 4 cuts one open.

17Snippets I re-type

Commands, queries and configuration you have looked up more than twice. Put them here instead of looking them up a fourth time.

18Version notes, dated

Things true only for one version on one platform. The fastest-rotting section in the folder, and the one that is actively harmful when neglected.

19Stack defaults

Small personal defaults, each with its reason. Anything that is a real architecture decision belongs in an ADR instead.

20Still true?

The occasional review: delete what is no longer true, and notice which entry has now come up for the third time.

21Three times → a note

An entry that keeps recurring belongs in a handbook note; a snippet that keeps being typed becomes a script, an alias, or a template in folder 16.

22Draw it from memory

Reading a diagram is recognition and feels like understanding. Drawing one from memory is recall, and it stops exactly where your understanding does.

23The four diagrams

Request path, data stores, trust boundaries, failure domains. The fourth is the one nobody draws and the one that changes decisions. Sheet 5.

24Annotate the constraint

"DB primary" tells a reader nothing. "DB primary ◄── all writes; the real ceiling" tells them what the diagram is for. The labels should carry the argument.

25My systems

One section per system, stamped LAST UPDATED, with a NOTES block. Update it in the same pull request that changes the system, or it drifts.

26Redraw after three months

Redraw the same system from memory and compare it with the stored version. The genuine test of whether the understanding stuck.

27What I got wrong

The column that is the whole exercise. Not knowing where something sits is a gap; believing it sits somewhere it does not is a defect in your mental model.

28The review prompt

Which diagram is out of date? What exists exactly once? Which of the four is missing? Did what you could not draw reach Questions?

ADiagrams → Questions

The point where a drawing stops — where TLS terminates, which component holds the session — goes straight into Questions. The stopping point is worth more than the finished drawing.

BQuestions → Technology Notes

A blocking question is deleted once answered, but only after the answer is written somewhere permanent. For a flag, an error or a config, that place is a Technology Notes entry.

Capture is not commitment

The value of every line on this sheet comes from writing things down without deciding anything about them. Deciding happens later, calmly, at the review stations. Collapse the two — capture only what you already intend to act on — and you have built a backlog, which does not free your attention the way an honest inbox does.

Sheet 2

The Question Circuit

Closed circuit Covers · Questions · Technology Notes · Diagrams

The Questions file is a map of your own edges. One question travels six stations and ends as evidence; the circuit then starts again, because the list is never supposed to be empty. The expensive failure is not a wrong answer — it is the question that was never written down, and quietly turned into an area of the system you avoid.

Step key — the stations and sections of Questions

01Notice it

Capture the question the instant you notice it, however rough. The moment of noticing is unrepeatable; the phrasing can always be fixed later.

02Phrase it precisely

Convert "I don't get X" into a question with a specific answer. This conversion is most of the value of the file, and it is why the file matters more than any note you will read.

03Which kind is it?

Sort into blocking or background. The two lists have different clocks and different endings, so they must not share one.

04Answer it

Read, test, trace the code, or ask. Faster-to-ask questions go to the batched list at 11 rather than becoming interruptions.

05Compress it

Two sentences, in your own words. If it will not compress, you have found the answer without yet understanding it — write that down as a new question.

06Record it

Move the question to Answered with its date and source. The Answered section is evidence, and re-reading it is a cheap form of revision.

07Blocking

You cannot finish today's work without it. Answer now, write the answer somewhere permanent, then delete the question. Watch for the ones you worked around instead.

08Background

Questions that would deepen your understanding of your own systems, each with a note on why it matters. Answer one a week. This list should never be empty.

09The Answered record

ANSWERED date, ANSWER in one or two sentences, SOURCE where you found it, LINK to the handbook note you updated — if you updated one.

10Thought I understood

I believed / Actually / Found out when. Deliberately uncomfortable, and the most useful section here: someone who tracks what they got wrong argues from evidence rather than confidence.

11Ask someone else

Questions for a colleague, a maintainer, an issue tracker or a model, batched by person or place. Asking is a legitimate answer route, not a failure to research.

12The review

Every couple of weeks: the worked-around blockers, the oldest background question (answer it or delete it honestly), the answers that deserve notes, and whether the list has gone empty.

The most valuable file in the handbook

Every other file on this atlas feeds this one: a diagram that stops, an error whose cause you never really understood, an idea you could not write a smallest version for. If you keep only one file in folder 17, keep this one — it is the only document anywhere that records where your own understanding ends.

Sheet 3

The Idea Sieve

Decision tree Covers · Ideas · Questions

Ideas enter at the top-left without judgement and are filtered on a monthly clock. Each gate removes most of what reaches it, and that is the design working. The one gate that matters is the smallest version: an idea with no afternoon-sized test is not ready to start, and finding that out costs one line instead of one month.

Step key — the gates and sections of Ideas

01Capture

Anything, in one line, unjudged, newest at the top. The only rule is that nothing is decided here — capture exists to free your attention, not to plan.

02The monthly read

Read the whole list once a month. Delete what no longer interests you, leave what you are unsure of, promote at most one or two.

03Delete it

An idea you have not wanted to start in three months is not one you want. Most ideas look worse after a month, which is exactly what you needed to find out before spending a weekend.

04Worth a second look

Ideas that survived at least one review, each written up as WHY IT KEEPS COMING BACK, SMALLEST VERSION and WHAT WOULD MAKE IT WORTH IT.

05The smallest version

Almost every idea has a version that takes an afternoon and answers the interesting question. If you cannot name one, the idea is not understood well enough to start.

06A real task

Anything you actually intend to do leaves this file and becomes a task, written from the Task Template in folder 16, with acceptance criteria.

07Started

A table of Idea / Started / Outcome / Verdict for everything you acted on. Keeping the failures is the point; they are the more useful half.

08Did it work?

Decide the verdict honestly, against the "what would make it worth it" condition written at 04 — not against how much effort went in.

09It worked

Record the verdict. When the result is a design choice other people must live with, the reasoning belongs in an Architecture Decision Record, not here.

10Record the wall

Write down what stopped it. Without that sentence you will have the same idea in eighteen months and rediscover the same wall.

11Deliberately rejected

"<idea> — rejected because <reason>, <date>." A decision recorded once, so it is not re-litigated annually.

12Improvements to this handbook

Missing notes, missing links, sections that turned out wrong — kept apart from product ideas. The most valuable improvement is almost always a link, not a new note.

Sheet 4

Anatomy of a Note

Cutaway section Covers · Technology Notes · Questions · Ideas

The handbook holds the reasoning; this file holds the things you can only learn by doing — the flag, the error string, the version that breaks. Specifics are worth the most on the afternoon they are discovered and rot fastest afterwards, so the whole design of this file is: write it immediately, date it, and move it out the moment it stops being specific.

Step key — the fields and sections of Technology Notes

01Date

When the entry was written. Makes its age visible at a glance, which matters because specifics expire and nobody re-verifies an undated note.

02Context

What you were trying to do. Without it, a fix is unreadable six months later — you cannot tell whether your situation is the same one.

03Symptom

What happened, including the exact error text. The exact string is what makes the note findable by search the next time it appears.

04Cause

What it actually was — usually not what you first assumed. Writing down the wrong first assumption is part of the value.

05Fix

The command, flag or config that worked, precisely enough to paste. "Changed the Dockerfile" is not a fix; the reordered instructions are.

06Lesson

The general form, if there is one, with a pointer to the handbook note it belongs to — such as the Docker note in 13 DevOps and Delivery.

07This file vs the handbook

Handbook notes explain what a technology is, where it sits and its trade-offs; they age slowly. This file holds the flag, the platform quirk and the error meaning; it ages fast and saves the most time.

08Write it the same day

The detail that makes the note useful is the one gone by tomorrow. A note written a week later is a summary; written the same afternoon, it is a solution.

09Snippets I keep re-typing

Commands, queries and configuration looked up more than twice, each with what it does and when. Candidates for a script, an alias or a template.

10Version and environment notes

Technology, version, note, date. The fastest-rotting section: date every row, and delete any note about a version you have upgraded past.

11My stack defaults

Small personal defaults with their reasons. Not architecture decisions — anything with that weight belongs in an Architecture Decision Record.

12The review

Delete what is no longer true; promote an entry seen three times to a handbook note; turn a re-typed snippet into a script or folder-16 template; add a generalising lesson to its note and link back.

A stale note is worse than no note

A note claiming a bug exists in a version you upgraded past a year ago will cost someone — probably you — an hour of confusion, and it will be believed precisely because you wrote it. Undated specifics are the one thing in this folder that does active harm.

Sheet 5

Drawing From Memory

Survey plate Covers · Diagrams · Questions

Your own drawings of systems you actually work on, in plain text, kept next to the code they describe. Drawing from memory is the fastest way to discover what you do not understand, and the diagram that changes decisions is the one nobody draws: everything that exists exactly once.

Step key — the parts of this survey

01Recall, not recognition

Reading a diagram feels like understanding. Drawing it from memory reveals every gap immediately, and the place you stop — where TLS terminates, who holds the session — belongs in Questions.

02Request path

What happens to one user request, end to end. The base drawing that the other three are usually annotations of.

03Data stores

What holds state, and which store is the source of truth. Everything else is a cache or a copy and should be drawn as one.

04Trust boundaries

Where untrusted input enters and where credentials are used. The drawing a security review starts from.

05Failure domains

What exists only once, and what dies together. The one nobody draws and the one that changes decisions: circle the singletons and you have your availability work in priority order.

06Flow direction

Arrows show which way requests and data move. Consistent direction lets a reader follow the path without reading any labels.

07Sync / async boundary

The double line marks where a request stops waiting — here, between the queue and the worker. Failures on either side of it look completely different.

08A component you own

A square box: something you deploy, operate and get paged for.

09Someone else operates it

Round brackets: a CDN, a managed service, a vendor API. You depend on it but cannot fix it, which changes what "mitigation" means.

10Single point of failure

The warning sign: exists once, and takes something important down with it. In the example, sessions die with the Redis node and the queue silently backs up behind one worker.

11Annotate the constraint

Label what a reader could not guess — "all writes; the real ceiling" — rather than what the box obviously is. The labels should carry the argument.

12LAST UPDATED

Every system section carries its date and is updated in the same pull request that changes the system. An undated diagram cannot be trusted.

13NOTES

Beneath each diagram: the constraint a newcomer would not guess, what exists only once, and what you are unsure about — with that last line copied into Questions.

14Drawn from memory, the log

System / Date / What I got wrong. Re-drawing the same system three months later is the real test; the "what I got wrong" column is the whole exercise.

15Plain text

ASCII in Markdown diffs in Git, reads anywhere and is fast enough to edit that it stays current. A beautiful diagram that is six months stale loses to an ugly correct one.

A wrong diagram is worse than a missing one

Architecture diagrams are almost always wrong because updating them is friction. If a diagram here is out of date, fix it or date-stamp it as unverified today — a confident, stale drawing will be believed in exactly the design discussion where it does the most damage.
