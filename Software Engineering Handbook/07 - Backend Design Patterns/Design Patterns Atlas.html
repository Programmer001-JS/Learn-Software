Sheet 1

The Request Line

Transit diagram Covers · Middleware · Routing · Validation · Controllers · Services · Repository Pattern

One order, twenty stops, seven layers. The business logic is one station of twenty. Seven red spurs end the journey early with a status code, and each is cheaper the further left it sits — a request refused at stop 04 costs microseconds; the same request refused at stop 12 has already cost a database round trip.

Step key — every stop on this sheet, and what it does

01POST /orders

A method, a path, a body and a bearer token. Treat all four as hostile — including requests from your own frontend, because anyone can send the same bytes with curl.

02Request ID

A correlation id generated before anything else runs and attached to the request, every log line and every error body. Registered first so nothing downstream logs without it.

03Logging and CORS

Method, path, status and duration — never whole bodies or headers, which carry passwords and tokens. CORS decides which browser origins may call the API at all.

04Rate limit · 429

Throttle abusive callers before authentication, or brute-force login attempts are never slowed. Check how X-Forwarded-For is trusted, or a forged header resets the counter.

05Parse the body

JSON into an object, with a size limit enforced before parsing — 100 KB here. A limit applied after parsing has already paid the cost it was meant to avoid.

06Authenticate · 401

Verify the token and attach the identity (req.user, HttpContext.User). Everything downstream relies on it, and nothing downstream re-checks it.

07Authorise the route · 403

A coarse check: may this user create orders at all? It must come after 06 — authorising an unknown user always fails or always passes.

08Route match · 404 / 405

Walk registered routes in order, first match wins. No path matched is 404; the path matched but not the method is 405. Sheet 2 shows why /users/me must be registered before /users/:id.

09Convert params · 400

"42" becomes the integer 42; if conversion fails the handler never runs. The router has chosen a handler — it has decided nothing about permission.

10Validate · 422

The body is checked against an explicit allow-list schema: shape, types, ranges, lengths, with every field error returned at once. Past this line the object is typed and trusted.

11Controller

Extract parameters, call one service method, map the result, pick the status. Five lines, no branching, no queries. If a cron job could not reuse this endpoint's logic, logic is stuck here.

12Service · 409

Object-level authorisation (is this account theirs?), then business rules: stock, pricing, discounts, limits. A violation raises a domain exception such as OutOfStockError — never an HTTP error.

13Begin transaction

One use case, one transaction, opened by the service through a unit of work. Persisting the order and reserving the stock either both happen or neither does.

14Repository

order_repo.add(order): the only layer that knows SQL. Queries are parameterised, eager loading is applied in one place, and rows come back as domain objects.

15Commit

The transaction closes. Database constraints act as the last line of defence here, catching anything validation and business rules let slip through.

16Publish event

OrderCreated goes to the event bus after the commit, so no listener ever reacts to an order that was rolled back. Publish identifiers, not sensitive payloads.

17Map to DTO

The domain Order becomes an OrderDto listing exactly the fields that may leave. Returning the ORM entity leaks every column anyone ever adds, and can trigger lazy loads mid-serialisation.

18201 Created

The status code and headers such as Location: /orders/42 are chosen on the HTTP side of the boundary. The service returned an object and knows nothing about either.

19Reverse pipeline

The same middleware crossed again, outward: response headers, compression, and the timing log that measured everything between the way in and the way out.

20Error handler · 500

Registered outermost so it wraps everything. Maps domain exceptions to status codes centrally and turns anything unexpected into a clean 500 carrying the request ID — never a stack trace.

The route is not the permission

Stops 06 to 09 establish who the caller is and which function will run. None of them checks that order 42 belongs to this caller. That object-level check lives at stop 12 or nowhere — and its absence is the single most common serious API vulnerability there is.

Sheet 2

The Gatehouse

Cutaway section Covers · Middleware · Routing

Stops 02 to 09 of sheet 1, opened up. Above, middleware drawn as what it really is — rings around the handler, crossed once inward and once outward. Below, the router drawn as what it really is — a lookup table. Middleware order is a security decision, not a formatting one; and a route existing is never permission to call it.

Step key — the rings and the routes

01Error handler

Outermost ring, so it catches exceptions from every layer inside. Maps them to status codes and must never send a stack trace to the client.

02Request ID

First inner ring. A correlation id every downstream log line and error response can carry, which is what makes a production incident traceable at all.

03Logging

Method, path, status, duration. Never request bodies or headers wholesale — passwords and tokens end up in log storage with far weaker access control than the database.

04CORS

Declares which browser origins may call this API. It restricts browsers only; curl and servers ignore it, so it is never a substitute for authentication.

05Rate limiting

Before authentication, so login brute force is throttled. Before body parsing too — a cheap rejection placed after expensive work saves nothing.

06Authentication

Identifies the caller and attaches the identity for everything downstream. Registered globally; routes that need no auth opt out explicitly, never the reverse.

07Authorisation

Decides whether this identity may proceed — which is meaningless until 06 has run. Only coarse, role-level checks can live here; object ownership needs the loaded object.

08Handler

The only business-specific code inside the onion. Business rules must not migrate outward into middleware, where they become invisible to anyone reading the handler.

09Method

The action: GET, POST, PUT, PATCH, DELETE. Together with the path it is the key the router matches on — the same path with two methods is two routes.

10Version prefix

/v1/, /v2/: routing used to keep an old contract alive while a new one exists beside it. An API gateway routes on prefixes like this to entirely different services.

11Resource

A plural noun naming a collection. Verbs in paths (/getUser) and inconsistent singular-plural naming are the conventions most often broken.

12Path parameter

A required identifier, extracted and converted. Validate it before it builds a file path (traversal), and prefer UUIDs where sequential ids let attackers walk your data.

13Nested resource

At most one level. /users/1/orders/2/items/3/comments couples the URL to a hierarchy that will change; /items/3/comments survives it.

14Query string

Optional filtering, sorting, pagination. Never tokens or secrets: URLs are written to server logs, proxy logs and browser history.

15404 Not Found

No registered path matched. Also the right answer for a resource that exists but whose existence is itself sensitive — a 403 would confirm it.

16405 Method Not Allowed

The path matched but not the method: DELETE on a route registered only for GET. A different fault from 404, and worth distinguishing for clients.

17400 Bad Request

Parameter conversion failed — "abc" where an integer id was declared. Rejected before the handler runs, so the handler never defends itself against it.

18Handler call

getUserOrders(id=42, status="pending"): a function call with typed arguments. What it is not is an authorisation decision — that happens after this, or not at all.

Silent by design

In Express, a security middleware registered after a route never runs for that route — no error, no warning. The same router that shadows /users/me gives no warning either. Write the chain and the route table out in order once, check the four rules against them, and verify that a brand-new route gets authentication without anyone remembering to add it.

Sheet 3

The Boundary Checkpoints

Decision tree Covers · Validation · Controllers

Stops 10 to 12 of sheet 1, drawn as the questions they ask. "Is it well-formed?", "may this user do it?" and "does the domain allow it?" sound like one check and are three — asked in different layers, failing with different codes. Validate once at the edge with an allow-list, then trust your own types; everything the controller does beyond translating HTTP is logic nobody else can reuse.

Step key — the checkpoints and their vocabulary

01Untrusted input

Every trust boundary, not just HTTP: queue messages, webhook payloads, file uploads, environment variables and responses from third-party APIs all get validated.

02Size limit

Strings, arrays and whole bodies are capped before parsing. Without limits a single request is a memory-exhaustion attack.

03Parse

Malformed syntax is a 400. Keep it distinct from 422, which is a well-formed request whose content is invalid.

04Schema check

Shape, types, ranges, lengths and allowed values, declared once. Beware catastrophic regexes (ReDoS), validate uploads by content not extension, and validate URLs before fetching them (SSRF).

05Trusted object

Past the boundary, code stops defending itself. Internal layers do not re-validate the same shape — duplicated rules drift apart.

06Controller

Receives typed input and an authenticated user, calls one service method. Also called handler, resource, view or endpoint depending on the framework.

07Object authorisation

order.user_id != user.id → PermissionDeniedError. Middleware knew who you were; only code holding the object can know whether it is yours. Most often forgotten in controllers.

08Business rule

Not enough stock, a shipped order cannot be cancelled. Needs the domain and usually the database, so it can never live in the validation schema.

09Repository write

Happens inside the service's transaction, through a repository — never a query written in the controller.

10Database constraints

Unique keys, not-null, foreign keys: the last line of defence. If they are the first thing to reject bad data, the checks above them are missing.

11Map to DTO

An explicit response object with declared fields. Mapping tools (MapStruct, AutoMapper, Pydantic) help; copying every field automatically defeats the purpose.

12201 Created

Status code, Location header and body chosen in the controller: 200, 201, 204 or 404 are HTTP decisions the service never makes.

13Three kinds of checking

Validation (400/422, boundary), business rules (409/422, service), authorisation (403, middleware or service). Separating them tells you exactly where each rule belongs.

14Schema-driven validation

Pydantic, Zod, class-validator, FluentValidation, JSON Schema. Better than hand-written ifs because the schema is also the type and the documentation.

15Error response

All field errors at once, a machine-readable code and a request_id. A client that must submit five times to find five problems is using a bad API.

16Allow-list

Define what is acceptable and reject everything else. Every filter built by blocking known-bad patterns has eventually been bypassed.

17Client vs server

Browser validation is a user-experience feature. curl, mobile apps and other services never saw your form, so every rule is enforced again on the server.

18Fat controller

The version every tutorial writes because it fits on one slide. Its logic cannot be tested without an HTTP server, reused by a job, or read without wading through parsing.

19Exception mapping

NotFound 404, PermissionDenied 403, Validation 422, Conflict 409, RateLimit 429, anything else 500. One central handler, not a try/except per endpoint.

20Mass assignment

Binding a request body straight onto a model lets the caller set is_admin, role or account_balance. Bind to an input schema listing exactly the accepted fields.

21Response DTO

The most common accidental data-leak path is returning an entity. Validation is not sanitisation either: output escaping, not input checks, prevents XSS.

The honest counter-argument

For a genuinely trivial endpoint — one insert, no rules — a service that only forwards to a repository is ceremony, and a thin controller calling the repository directly is honest. Judge by whether there are business rules to protect. Validation at the boundary, however, is never optional.

Sheet 4

The Rulebook and the Archive

Process plant Covers · Services · Repository Pattern

Stops 12 to 16 of sheet 1, drawn as a plant. Four intakes feed one rulebook; the rulebook asks an archive for objects and never learns how they are shelved. The service is the only layer that knows which writes belong together, and the repository is the only layer that knows SQL — swap either responsibility into the other and both become untestable.

Step key — the plant and the archive

01Four intakes

HTTP, CLI, queue consumer, cron. If a rule can only be reached through an HTTP request, it will eventually be reimplemented — differently — in one of the other three.

02Authorise

In or above the service, never only in the controller: the consumer that also cancels orders has no controller. The service raises PermissionDeniedError; HTTP maps it.

03Load

Everything needed, through injected repositories — never concrete database code. Load collections in one call; a repository call inside a loop is a hidden N+1.

04Apply rules

Stock, pricing, discounts, limits, in domain language. Violations raise domain exceptions like OutOfStockError, which sheet 3 maps to 409.

05Begin

The transaction opens in the service. A controller does not know which writes belong together; a single repository is too fine-grained to decide.

06Persist the order

orders.add(order) participates in the ambient transaction. The repository writes; it does not decide.

07Reserve stock

A second repository in the same unit of work. "Check stock, then reserve" as two unguarded queries lets two buyers take the last item.

08Commit

Both writes succeed or neither survives. Without a clear boundary, a failure between them leaves a partial write in production.

09Publish event

OrderCreated after commit, so nothing reacts to a rolled-back order. This is also where audit logging belongs: the service knows what happened; a controller only knows a request arrived.

10Return a domain object

Not a DTO, not a status code. Mapping to the response shape is the caller's job, because a CLI and an HTTP endpoint want different shapes of the same result.

11Service as dependent

Takes the repository interface in its constructor. Beware services calling services calling services: if A always needs B, they may be one use case, or B may be a domain object.

12Repository interface

Collection-like — get, add, pending_for — and defined by the domain. The dependency points from storage toward the business: the core idea of Clean Architecture on sheet 7.

13SQL implementation

The one place SQLAlchemy, Prisma or Entity Framework appears. Parameterised queries only — the layer allowed to write raw SQL is exactly where injection is most likely.

14Cached decorator

Wraps the SQL repository and satisfies the same interface, so adding a cache or a read replica changes no caller at all.

15In-memory implementation

The payoff: the same service, handed a dictionary-backed repository, runs its tests with no database in milliseconds instead of seconds.

16Unit of Work

Coordinates several repositories inside one transaction and commits them together. Spring's @Transactional puts the boundary on the service method itself.

17One query, one place

Scattered ORM syntax means the same query written four ways, one without eager loading. A repository method fixes the N+1 once. Never expose raw query builders, or the encapsulation is gone.

18Active Record, DAO, Repository

order.save() couples the object to storage; a DAO is table-shaped; a repository is collection-shaped and domain-typed. One repository per aggregate, not per table.

19Anemic or rich

Both schools are defensible. Rules in services is simpler; rules in entities scales. Repetition of one invariant across services is the signal to move it.

20The honest objection

An ORM is already a repository. The pattern earns its place for complex domains, fast tests, reused queries and tenant filtering — and is pure ceremony in a small CRUD app. Write down which you have.

Sheet 5

The Wiring Diagram

Wiring diagram Covers · Dependency Injection · SOLID Principles

Sheet 4 said the service receives its repository. This sheet shows who hands it over, how long each part lives, and the five class-level rules that make the swap possible. A chef handed ingredients can cook anywhere; one sent shopping can only cook near the usual shop. Every principle here buys that flexibility with indirection — worth it only where things actually vary.

Step key — wiring, lifetimes, and the five principles

01Composition root

Application startup: the one place that names concrete types and wires the object graph. Keeping that knowledge in one file is most of the benefit of DI.

02Concrete implementations

SqlOrderRepository, SmtpEmailSender — anything touching the outside world: databases, HTTP clients, email, clocks, random numbers, file systems. Exactly what tests replace.

03The injected service

Declares what it needs in its constructor and never builds it. Without DI, OrderService hard-wires PostgreSQL and SMTP, and its tests send real email.

04The injected controller

Receives the service the same way. The chain Controller ← Service ← Repository ← connection is assembled outside all three.

05Test doubles

InMemoryOrderRepo and FakeEmailSender through the same constructor. They must never be reachable in production — a profile that swaps in a no-op authoriser should fail loudly.

06Constructor injection

The default: dependencies are visible in the signature and fixed for the object's life. A constructor needing six of them is a design signal — the class does too much; DI only made it visible.

07Method injection

A dependency passed to the one method that needs it, for something a single operation uses.

08Property injection

Set after construction. Avoid it: between construction and assignment the object exists in an invalid state.

09Container

Reads type declarations and wires the graph. Useful for large graphs; errors surface at startup or, worse, first use. Dagger and Micronaut resolve at compile time; Spring pays at boot.

10Singleton scope

One instance for the application's lifetime: stateless services and configuration. The DI-registered replacement for the Singleton pattern's global state.

11Scoped

One instance per request: the database session, the current user. Disposed when the request ends.

12Transient

A new instance on every resolution: lightweight, stateful helpers. Do not inject value objects at all — a Money is simply constructed.

13Captive dependency

A scoped dependency injected into a singleton captures the first request's session and reuses it forever — data leaking between users under concurrency. Inject secrets as a config object, not strings scattered across classes.

14Single Responsibility

One reason to change, meaning one stakeholder. Vague enough that two engineers will disagree in good faith; not "one method per class".

15Open/Closed

Open to extension, closed to modification: a new payment provider is a new class. It assumes you can predict the variation — guess wrong and you built the wrong extension point.

16Liskov Substitution

Any subtype must work wherever its base does, without the caller knowing. Square inheriting Rectangle compiles and breaks the area promise.

17Interface Segregation

Many small interfaces beat one large one. Python Protocols, Go and TypeScript interfaces give much of this for free through structural typing.

18Dependency Inversion

High-level policy depends on abstractions; low-level detail implements them. The principle behind DI, repositories and Clean Architecture — the one with the largest structural consequences.

Indirection hides where checks happen

SOLID taken to its extreme yields one method per class, interfaces with one implementation, and a request you can only follow by opening nine files. Apply it where code actually changes — and keep security controls explicit and shallow, because a question like "where is this authorised?" that needs five interfaces traced is a question nobody audits.

Sheet 6

The Pattern Ladder

Ladder plate Covers · Design Patterns · SOLID Principles

Seven levels of structure for one problem — charging a customer — drawn in the order a codebase should reach them. Every rung adds a file, an interface or a layer that every future reader pays for. Refactor into a pattern; do not design into one. The pattern's benefit is only collected if the variation it anticipated actually arrives.

Step key — the rungs and the catalogue

01Inline code

One provider, called directly. Correct for as long as there is one — structure here is speculation about a future that may never arrive.

02A function

Name the step. The cheapest abstraction there is, and in Python or TypeScript often the entire Strategy pattern already.

03An if / elif

Two variants in one visible place. Every future provider edits this function and risks breaking the others — tolerable at two, a smell at eight.

04Strategy

PaymentMethod with StripePayment and PayPalPayment behind it, injected into Checkout. Adding a provider adds a class. Open/Closed made concrete, and dependency injection by another name.

05Strategy + Factory

The implementation is chosen at runtime from configuration or input. Justified once several exist; a factory producing one type is ceremony, and a misread config can pick an insecure variant.

06Stacked decorators

Each layer adds behaviour without touching the class. In a very hot path the nesting costs cycles; everywhere it costs the ability to see where checks happen.

07Pattern as decoration

Patterns applied to demonstrate knowledge: an interface with exactly one implementation, forever. Complexity paid on every change, benefit never collected.

08Creational

How objects are made — Factory, Builder, Singleton, Prototype. In a DI codebase, the container absorbs most of this family.

09Structural

How objects compose — Adapter, Decorator, Facade, Proxy, Composite. The family backend code uses most, usually without naming it.

10Behavioural

How objects interact — Strategy, Observer, Command, Template Method, State.

11Strategy

Swap an algorithm at runtime: payment providers, sorting, pricing rules. The most useful pattern in the catalogue.

12Factory

Create objects without naming the concrete class: parsers by file type, drivers by configuration.

13Adapter

Make an incompatible interface fit. Wrapping a third-party SDK is what makes replacing the vendor possible later.

14Decorator

Add behaviour without changing the class: middleware, or a cache around a repository that no caller notices.

15Observer

Notify many listeners of one event: domain events, pub/sub, UI reactivity — and the basis of event-driven architecture.

16Facade

One simple interface over a complex subsystem — a service over several repositories is the everyday example.

17Repository

Abstract data storage behind a collection-like interface. Sheet 4 draws it in full, including when it is ceremony.

18Builder

Construct complex objects step by step: query builders and test fixtures.

19Patterns already present

Middleware is Chain of Responsibility plus Decorator, the service a Facade, the payment method a Strategy, the cached repository a Decorator, the domain event an Observer.

20Singleton

Global mutable state, hidden dependencies, order-dependent tests and trouble under concurrency. Need one instance? Register it as a singleton in the container instead.

21Language-shaped patterns

Many classic patterns patch limits of 1994-era languages. Read real implementations — Django middleware, SQLAlchemy, Spring — and Fowler's enterprise patterns, closer to backend reality.

Sheet 7

The Concentric Plan

Ring plan Covers · Clean Architecture · Domain Driven Design

Sheets 1 to 6 arranged as a building. Business rules at the centre, plumbing on the outside, every dependency pointing inward; and inside the centre, a model drawn with the locals rather than from a satellite. This is the heaviest machinery in the folder: its language and value objects are nearly free everywhere, and its rings and aggregates are worth their cost only where the rules genuinely are the product.

Step key — rings, ports, contexts and aggregates

01Frameworks and drivers

The web framework, ORM, database, queues and external APIs. The parts most likely to change, deliberately kept at the edge where replacing them touches nothing inside.

02Interface adapters

Controllers, presenters and repository implementations: translation between the outside world's shapes and the use cases' shapes.

03Use cases

Application operations such as CreateOrderUseCase. They authorise, so every delivery mechanism is subject to the same rules, and they define the repository interfaces they need.

04Entities

Core business objects and invariants, knowing nothing at all. No entity imports a framework — that single violation is the clearest sign the architecture is only folder names.

05Driving adapters

Things that call the application: HTTP, CLI, queue consumers, cron. Each converts its input into a use-case call.

06Ports

Interfaces defined by the inside — a Python Protocol, a Go or TypeScript interface. Dependency inversion from sheet 5 is the mechanism that makes the arrows point inward.

07Driven adapters

Things the application calls: PostgreSQL, Redis, email, S3. Swapping REST for gRPC or Postgres for DynamoDB touches only these.

08The cost question

The most over-applied architecture in the handbook. Worth it for complex, long-lived domains with several delivery mechanisms; for CRUD apps and prototypes it is paying for optionality you will never exercise.

09Enforcement

ArchUnit, import-linter and dependency-cruiser turn "inner rings import nothing outer" from a convention into a failing build.

10Bounded context

A boundary inside which one word has one meaning. "Customer" in Sales, Billing and Support are three models linked by identity — and the best guide to service boundaries.

11Anti-corruption layer

Translates an external or legacy model into yours so its concepts do not leak in, and stops untrusted external data entering the domain unchecked.

12Context map

How contexts relate — shared kernel, customer and supplier, anti-corruption layer. EventStorming is the workshop technique for discovering them.

13Aggregate root

The only entry point to a cluster of objects and the enforcer of its invariants. An order total that may not exceed the credit limit, enforced here, cannot be bypassed by any controller, job or script.

14One transaction per aggregate

Cross-aggregate consistency travels by domain event, after commit, eventually. Aggregates that are too large load enormous graphs for one field; CQRS often appears to separate reads.

15Ubiquitous language

One vocabulary in conversation, docs, code, tables and endpoints. The moment someone says "what the business calls a lapse, we call status 3", knowledge has started leaking.

16Value object

Defined by its values and immutable: Money(10, EUR), Address, AccountId. Cures primitive obsession with no framework — dataclass(frozen=True) is enough.

17The honest split

Language and value objects everywhere; aggregates, bounded contexts and the full tactical toolkit only where complexity justifies them; anemic entities with every rule in services is not DDD.

The closing loop

POST /orders on sheet 1 enters through a driving adapter on this sheet; the checkpoints of sheet 3 sit in the adapter ring; the rulebook of sheet 4 is the use-case ring; the wiring of sheet 5 is what lets its ports receive adapters; the patterns of sheet 6 are the joints between rings. Build the rings only as thick as the domain demands — the goal was always code that is cheap to change, never code that looks architected.
