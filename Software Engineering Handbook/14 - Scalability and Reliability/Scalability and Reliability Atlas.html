Software Engineering Handbook · 14 Scalability and Reliability · six sheets

Atlas of Scalability and Reliability

One production system, asked two questions. Can it carry ten times the load? And what happens when a part of it — or all of it — is gone? The first three sheets answer the first question, the last three the second. Both answers start in the same place: find the thing that exists only once, because that is your ceiling and your single point of failure at the same time.

Sheet 1

The Scaling Stack

Cutaway section Covers · Scalability Fundamentals · Vertical Scaling

A system cut open from the edge down to the disk, with the price of scaling each layer written beside it. The top layers scale by configuration; the bottom one scales by architecture. Scalability is not speed — it is the shape of the curve as load rises, and that shape is set by the one part of the system that cannot be copied.

Step key — every layer and stage on this sheet

01CDN / edge

Static and cacheable responses served from many locations, before a request ever reaches you. Scales for free, and the right place to rate limit per client and per tenant.

02Load balancer

One stable address in front of a changing fleet. Required by any horizontal tier, and scales horizontally itself. Drawn in full on sheet 2.

03Stateless app tier

Identical copies holding nothing unique, each run at about 60% at peak. "Make the application layer stateless" is the highest-leverage sentence in the chapter.

04Cache

The cheapest capacity you will ever add. An 85% hit ratio is the difference between a database that copes and one that does not. Keys must include the authorisation context.

05Queue and workers

The pressure valve: the user waits for the essential part, the rest happens behind. Converts a capacity problem into a latency-of-completion problem. An unbounded queue is a delayed outage.

06Database primary

Usually one writer, where ordering and consistency matter — the bottleneck, almost always. Writes cannot be cached; they can be batched, queued, partitioned or relaxed.

07Replicas and pooling

Read replicas take reporting and analytics off the primary. Connection pooling guards the ceiling people meet unexpectedly: instances × pool size against the database's limit.

08Amdahl's law

If 5% of the work is serial, the maximum speed-up is 20× with infinite resources; 25% gives 4×. Find the serial part, because no hardware raises that ceiling.

09Utilisation cliff

Queueing theory: latency rises non-linearly beyond roughly 70–80% and heads to infinity at 100%. Target 50–70% at peak. A system at 85% is not efficient, it is on a cliff edge.

10State

Stateless things scale by adding copies; stateful things scale only by partitioning. Sessions to Redis or a signed token, uploads to object storage, the truth to the database.

11Measure

Before adding anything, find out what everything is waiting for. If adding app servers changed nothing, the bottleneck is below them. Compare p50 with p99, never averages.

12Add the index

One missing index removed 40% of database CPU. Costs nothing, and often removes the need for scaling work entirely. Never scale to fix an inefficient query.

13CDN the static assets

Moving static bytes to the edge removed 60% of requests before they reached the application. Configuration, not engineering.

14Cache the hot path

A read-through cache on the hottest queries reached an 85% hit ratio and took database CPU to 35%. Adds staleness and invalidation bugs — accept them knowingly.

15Go stateless

Sessions moved from process memory to Redis, uploads from local disk to S3. Any server can serve any request, and sticky sessions come out.

16Queue it

Transcoding and email moved off the request path: 3 s became 180 ms. Workers autoscale on queue depth — with a cap, so load cannot become an unbounded bill.

17Read replicas

Reporting and analytics moved to replicas. Scales reads without touching the write path, which is still one primary.

18Scale up

A larger primary: 4× headroom for one afternoon. The only strategy with no architectural change, and very often the correct next move. Adjust memory settings for the new size.

19Shard

Only when writes genuinely exceed the largest primary. Partition by tenant id; cross-shard joins, transactions and unique constraints become application problems. Expect the biggest project of the year.

20One modern machine

Up to ~192 vCPU, ~24 TB of RAM, hundreds of thousands of IOPS and 100 Gbit/s. Stack Overflow served enormous traffic from a handful of servers; most databases are never sharded.

21The saturated resource

Buy only what is actually saturated. Doubling CPU on a disk-bound system changes only the bill. Check t-family credits and gp3 IOPS defaults first — throttling looks like load.

22Vertical plus standby

Up for capacity, out for redundancy. A bigger machine is still one failure domain, so pair it with a same-size Multi-AZ standby; the resize becomes a ~60-second failover.

Scalability is not availability

Everything on this sheet makes the system carry more. None of it keeps the system up when a part fails — a 192-core primary is still one machine. The two are related and share techniques, but a design that scales beautifully can still be a single point of failure. That is sheet 4's question.

Sheet 2

The Fleet and the Front Door

Transit diagram Covers · Horizontal Scaling · Load Balancing

Scaling out means more identical copies and one component that decides which copy gets each request. Nine stops take a request from a DNS lookup to an access-log line; four incidents show what the front door does when a backend dies, drains, sickens or drowns. The health check matters more than the algorithm, and statelessness matters more than either — a copy that holds something unique is not a copy.

Step key — the stations, the incidents and the fleet

01DNS lookup

The name resolves to the load balancer, not to servers. DNS alone cannot help: a dead server keeps its share of traffic and clients cache records for hours.

02Edge rate limit

The last point before you start paying for compute. Limiting inside the application still spends a process, a connection and a lookup on every abusive request.

03TLS termination

One place for certificates, HTTP/2 and compression — and one hop where traffic is briefly plaintext. Re-encrypt to the backend for regulated data.

04Route match

Layer 7 understands HTTP, so /api/* and /* can go to different target groups, with per-route timeouts and header-based canaries. Almost every web system wants it.

05Pick a backend

Only from the healthy set. Round robin by default; least connections when request durations vary widely; consistent hashing where key locality matters.

06Forward

Over a reused keep-alive connection, with X-Forwarded-For added. The application trusts that header only from its own load balancer — clients can forge it.

07An instance

Identical, interchangeable, disposable, spread across zones. Scales close to linearly until a shared dependency saturates. Needs idempotent handlers: retries and duplicates become normal.

08Shared state

Everything unique lives below the instance line: sessions in Redis, the truth behind a connection pool, uploads in object storage. The pool stops N instances exhausting the database.

09Response and access log

Target, latency and status, per request. Often the only complete record of what was asked for — keep it in durable storage.

AA backend dies

Two consecutive failed checks over 10 s remove it from rotation; the scaling group replaces it; nobody was logged out because no session lived there.

BA deployment drains

Old targets stop receiving new requests and in-flight ones complete. With the delay longer than the slowest normal request, a deployment drops nothing.

COverload

Every backend saturated, checks still green, latency climbing. Retries now multiply load and turn a slowdown into a collapse. Retry on connection-refused only, shed load at the edge, add capacity.

DSick, not dead

A backend returning 500s while passing a shallow check stays in rotation. Health checks catch dead backends; per-target error-rate monitoring catches sick ones.

10Failure domains

Three instances in one zone give throughput and no resilience. Size so losing a whole zone still leaves enough capacity for peak — the cost is small cross-zone transfer charges.

11Autoscaling

Always late: the metric crosses, then provisioning, boot and warm-up. Scale workers on queue depth, web tiers on requests per instance; bake images, keep headroom, set min 2 and a bounded max.

12State that breaks

In-process sessions, local uploads, in-memory caches, local logs — and the scheduled job running in every copy, which nothing warns you about. Use a leader, a lock or a scheduler.

13Sticky sessions

Affinity lets a stateful app sit behind a balancer today, and keeps every failover, deployment and uneven-load problem statelessness was meant to solve. Move sessions out, then switch it off.

14Health checks

The load balancer's most valuable function. Keep them shallow and local; 5–10 s interval, 2–3 failures before removal. A deep check can remove the whole fleet at once.

15Algorithms

Random two choices is surprisingly close to optimal and cheap. Outside the mixed-duration case, the choice is a rounding error beside health checks and timeouts.

16Timeouts and connections

Idle timeout above the longest legitimate request, draining above the slowest normal one. Long-lived WebSocket and gRPC streams need a maximum connection age, or new instances sit idle.

Unbounded autoscaling is a financial attack surface

A fleet that grows in response to load grows in response to an attack too — the service stays up and the budget does not. Put a maximum on every scaling policy, rate limit before the load balancer, and watch the in-process cache hit ratio fall as copies multiply: ten instances each caching alone see a tenth of the repeats.

Sheet 3

The Measurement Loop

Closed circuit Covers · Performance Engineering · Load Testing

Two instruments for one question — where does the time go? A profiler answers it for one request; a load test answers it for ten thousand at once. Intuition about where time is spent is reliably wrong, so the loop begins and ends with a measurement, and the answer is usually a missing index, an N+1 or a connection pool — not your code.

Step key — the loop, the numbers and the load test

01Measure

Quantify in percentiles, then trace one slow request end to end. "Slow" with p50 400 ms and p99 6 s is a tail problem, not a speed problem. Without distributed tracing you cannot tell which service spent the time.

02Drill in

pg_stat_statements ordered by total time surfaces the query consuming the most database time overall — often a 12 ms query run 40,000 times a minute that no slow-query log would ever show.

03Diagnose

EXPLAIN ANALYZE shows what the planner actually did: a sequential scan over 4 million rows is a missing index. Run it against production-scale data; the plan changes with volume.

04Fix the largest cost

One change, aimed at the dominant contributor. Optimising something the profile shows as 2% is worse than nothing — it adds permanent complexity for a rounding error.

05Measure again

Confirm the change moved the percentile you care about: p99 from 1.4 s to 90 ms. A fix that is not measured is a belief.

06Ask again, or stop

The bottleneck will have moved — now the external API, so it goes to a queue. Stop when the performance budget is met: "fast enough" is a real destination.

07Where the time goes

Database queries (10–500 ms) and external calls (50–2000 ms) dominate; application CPU is 1–20 ms. The browser often costs more than all of it together.

08Latency numbers

~1 ns cache, ~100 ns memory, ~100 µs SSD, ~1 ms in-region, ~100 ms cross-continent. The ratios explain caching, N+1 disasters and why a moved call beats tuned code.

09Percentiles

999 requests at 10 ms and one at 10 s average 20 ms. p99 is what generates complaints, and in composed systems a component's p99 becomes a page's p50.

10The orders page

380 queries per request from a lazy-loaded association: eager loading took p99 from 6 s to 700 ms, an index to 120 ms, a background job to 45 ms. One day, no new infrastructure.

11The fix ladder

Index, N+1, cache, paginate, queue, batch, CDN, scale up, optimise code, rewrite — roughly ordered by return on effort. The usual suspects are also the usual fixes.

12The knee

The throughput where latency starts climbing faster than load: 400 rps, while errors only arrive at 500 and the ceiling at 550. That number, not the breaking point, is capacity.

13Test types

Load for the SLO at expected peak, stress for the ceiling, spike for autoscaling, soak for leaks, breakpoint for the curve. Each answers one question; the soak finds bugs nothing else does.

14Realism

A scenario mix derived from access logs, many distinct users, think time, a realistic cache hit ratio — and above all production-scale data. A small database tests the wrong query plans.

15Concurrency

Little's law: concurrency = throughput × latency. Rising latency raises concurrency, which raises latency — the feedback loop of collapse. Only an open, arrival-rate model shows it.

16Coordinated omission

A generator that waits for slow responses silently skips the requests it should have sent, deleting stalls from the percentiles. Use tools that correct for it, and keep the generator off the target.

A load test looks exactly like an attack

Warn on-call and silence the alerts for the window, never point a generator at a payment provider or partner API without written permission, make sure the test cannot send real email, SMS or payments, and clean up the orders and accounts it created. Stubbed dependencies no longer contribute their latency — which is often a real part of your p99.

Sheet 4

Surviving Failure

Failure map Covers · High Availability

Every component on this map will fail — a disk, a process, a zone, a certificate, a deployment. High availability is not making them reliable; it is assuming they are not, and deciding in advance what happens without a human. Walk the map and mark everything that exists exactly once: that list, not the diagram full of pairs, is your availability work.

Step key — the map, the arithmetic and the failure modes

01Health-checked DNS

Route 53 failover can move traffic between endpoints when checks fail. For the rare cases that justify it — and only useful if the TTL is already low.

02CDN / edge

Many locations, redundant by design, and the place for DDoS protection and rate limiting — availability is exactly what an attacker attacks.

03Load balancer

Managed and multi-AZ by default, and the detection mechanism for the app tier: a dead instance is out of rotation in about 10 s. Check it spans the zones you think it does.

04App tier

The easy part: stateless, N copies, active-active. Two per zone at 45%, so either zone can carry peak alone; the scaling group replaces failures and nobody is paged.

05Cache

Often a hidden single point of failure — one node everyone forgot. Replicate it and let Sentinel promote, or make a cache miss survivable.

06Database primary and standby

The hard part. Multi-AZ with a synchronous standby and automatic promotion is the highest-value single configuration change available; failover takes 60–120 s and loses nothing.

07Object storage

Already regionally redundant. The redundancy you do not have to build — which is why files belong here and not on instance disks.

08Immutable backups

The one thing replication cannot give you. Corruption, deletion and ransomware replicate perfectly; only an isolated, immutable copy in a separate account survives them.

09The nines

99.9% is 8.8 hours a year, 99.99% is 53 minutes, 99.999% is 5 minutes. Each costs roughly ten times the last; do not buy more than the business needs.

10Series availability

Availability is the product of your dependencies, not the best of them: four at 99.9% make about 99.6%. Adding services quietly lowers it unless each is made non-fatal.

11Capacity, not count

Three instances at 70% cannot lose one — the survivors would need 105%. Across two zones, each must run under 50%. Teams discover this during their first real zone failure.

12Failure domains

Process, machine, rack, zone, region, provider — and humans, the most common cause. Spanning two or three zones is the high-value step; multi-region forces asynchronous design into the application.

13Detection and failover

Detect, decide automatically, act, verify. Failover has its own failure modes — split brain, flapping, untested paths, cascades — so use proper leader election and rehearse it.

14Graceful degradation

A hung dependency must cost one feature, not the service: a timeout shorter than yours, a circuit breaker that fails fast, a fallback, bulkheads and load shedding. Every "return 500" is a decision to revisit.

15Replication trade-off

Synchronous costs 1–2 ms per commit and loses nothing on failover; asynchronous is faster and may lose the last seconds. The owner of the data chooses, explicitly.

Security incidents are availability incidents redundancy cannot touch

A compromised credential or ransomware propagates to every replica immediately, because replication faithfully copies destruction. So do expired certificates — a startlingly common self-inflicted outage — and a standby configured with looser security than the primary. Pairs protect against parts failing; they do nothing against the same mistake arriving everywhere at once.

Sheet 5

The Warning Lights

Instrument panel Covers · Monitoring and Alerting

Monitoring is the whole instrument panel; alerting is the handful of warning lights, and the error budget is the fuel gauge. Seven links run from a measurement to a changed system. The failure mode is not missing data — it is four hundred alerts a day and a channel nobody reads, so the mature move is subtractive: define "working", page on that, and delete the rest.

Step key — the chain, the budget and the incident

01SLI

A service level indicator: a measurement from the user's side, taken as close to them as possible. "Successful checkout requests under 2 s", never "CPU below 80%".

02SLO

The internal objective — 99.9% over 30 days. The SLA is the contract with money attached, and is always looser than the SLO so you get warning before it costs you.

03Error budget

What the SLO lets you spend: 43 minutes a month at 99.9%. It turns "ship faster" against "be reliable" into arithmetic, and gives permission to spend it deliberately.

04Burn-rate alert

Pages on how fast the budget is going, not on a fixed threshold: a 14× fast burn pages, a 2× slow burn opens a ticket. Removes most false pages and catches real outages sooner.

05On-call and runbook

Every page links its runbook, reaches a phone rather than an inbox, and lands on someone with the access to fix things. Paging systems must work when the identity provider does not.

06Incident

Mitigate first — roll back, fail over, shed load — communicate on a cadence through a status page hosted elsewhere, and keep one incident commander whose job is coordination.

07Blameless review

Timeline, contributing factors, and actions with owners and dates. Blameless does not mean causeless: if one person's mistake could break production, the system permitted it.

08The month's budget

A 7-minute fast burn on day 9, then 38 of 43 minutes gone by day 15, so feature deployments pause and the team works on reliability — with no argument, because the rule was agreed first.

09Three tests for a page

Is a user or the business affected? Can a human act right now? Would you want to be woken? Any "no" makes it a dashboard or a ticket. Symptoms page; causes like CPU and disk do not.

10Mitigate, then understand

02:05 deploy, 02:14 fast-burn page, runbook step one finds the recent release, 02:21 rolled back: 7 minutes of impact. Every minute spent diagnosing live is a minute of user impact.

11Review findings

The canary ran 5 minutes and the bug took 8 to manifest; the load test missed checkout's cache state; the runbook saved about 15 minutes. Three actions, three owners.

12Sustainable on-call

Pages per shift is a reliability metric that should trend down. More than one or two actionable pages a week means the system or the alerting needs work — or the result is attrition.

13Pruning and cardinality

Six of nineteen alerts had never led to an action, so they were deleted. And a user id or full URL as a metric label creates millions of series; identifiers belong in logs and traces.

14Outside-in checks

A synthetic check from outside the network sees DNS, TLS and CDN failures internal metrics cannot. Alert too on certificates at 30 and 14 days, backup failures and cost anomalies.

Bad monitoring is worse than none

Four hundred alerts a day manufacture confidence while training everyone to ignore the channel, so the one real page arrives inside the noise and is missed. Monitoring that depends on the system it monitors fails with it. And logs full of tokens and personal data are readable by far more people than the database is.

Sheet 6

The Recovery Ladder

Ladder plate Covers · Backup Strategy · Disaster Recovery

What sheet 4 cannot survive: a dropped table, ransomware, a deleted account, a lost region. Replication faithfully copies destruction, so recovery needs copies in a separate blast radius and a procedure people have actually run. A backup nobody has restored is a hypothesis, and a disaster-recovery plan nobody has rehearsed is a document — the rehearsal is the only part that produces a capability.

Step key — the rungs, the copies and the rehearsal

01Backup and restore

Backups in another region and account, nothing else running. On the day: provision from code, restore data, repoint DNS. RTO hours to days — the honest baseline for most companies.

02Pilot light

The data layer replicates continuously — a cross-region read replica — while compute is defined in Terraform but off. Tens of minutes, provided the recovery region has capacity and quotas.

03Warm standby

A scaled-down but complete environment running in another region, promoted and scaled on demand. Minutes of RTO, and the path is exercised simply by existing.

04Active-active

Both regions serve all the time; a disaster removes one from rotation. Near-zero RTO and RPO, and a different data architecture: partitioned users, conflict resolution, or a global database.

05HA versus DR

HA asks how not to go down when a part fails, and is architecture. DR asks how to come back when everything is gone, and is a documented, rehearsed procedure with named owners.

06RPO and RTO

Recovery point: how much data may be lost, which sets backup frequency. Recovery time: how long you may be down, which sets the restore mechanism. Commercial decisions, written per dataset.

073-2-1-1-0

Three copies, two storage types, one in another region or account, one immutable, and zero errors on a verified restore. The zero is the whole point, and the part almost never done.

08Backup types

Full, incremental (one missing link breaks the chain), differential, continuous log shipping for point-in-time recovery, and snapshots — crash-consistent only, so use the database's own mechanism.

09Retention

Grandfather-father-son: 24 hourly, 30 daily, 12 weekly, 12 monthly, 7 yearly. Set by how long corruption can hide, not how long you expect to need it; thirty days of dailies is the floor.

10A separate blast radius

Copies pushed by a write-only role into an account with different credentials, under Object Lock in compliance mode, then cross-region and to Glacier. Snapshots deletable by production credentials are convenient, not trustworthy.

11The real SPOFs

Encryption keys, DNS, certificates, secrets, credentials, allowlists, quotas and the runbook itself — each one, if it lives only inside the lost environment, stops the recovery.

12Infrastructure as code

The strongest argument for it: "rebuild everything" becomes a command with a known runtime, 22 minutes to an empty but correct environment. Anything created by hand will be missing.

13Rehearsal levels

Read the runbook aloud, run a tabletop, restore to scratch, rebuild in another region against the clock, fail real traffic over. Each level finds a class of problem the one before cannot.

14The timed rehearsal

Run by someone who did not write the runbook. It found a payment-provider allowlist, turned "about an hour" into a measured 2 hours, and made the real event a 1 h 50 m recovery instead of two days.

15Ransomware

The most likely modern disaster is a compromised admin credential. Recovery must not depend on the compromised account: immutable copies it cannot reach, break-glass credentials offline, every secret rotated, evidence preserved first.

The closing loop

The ceiling on sheet 1 is the database primary; sheet 4 gives it a standby; this sheet gives it a copy the standby cannot corrupt. Sheet 3 measured how much load it takes, sheet 5 watches whether it still does, and a rehearsal here proves the whole system can come back. Skip any one and the others quietly stop being true.
